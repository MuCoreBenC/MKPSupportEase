## 1. 需求对齐：几乎一模一样，模型上差一层

它要解决的问题和我们的 B03 是同一个，连决策编号都对得上（它的注释里直接引用 `决策 #1`…`#22`）。逐条比对：

| 议题 | homedemo1 B03 | 我们这一版 | 判定 |
|---|---|---|---|
| 配方本是核心数据，TOML 是产物 | ✅ | ✅ | 一致 |
| 稀疏覆盖：没有这个键 = 继承 | ✅ | ✅ | 一致 |
| 取值层数 | **三层**：出厂默认 → 机型基底 → 版本覆盖 | **两层**：机型基底 → 版本覆盖 | **差一层** |
| 状态判据是快照比对，不看文件时间 | ✅ `sameSnapshotB03` | ✅ 内容 hash | 一致 |

| 未保存编辑要留住 | ✅ 草稿存 localStorage | ✅ 草稿存 `.draft/` | 一致 |
| minClientVersion 要有、但不能瞎填 | ✅ 摆出输入框但 `disabled`，理由写在 title 里 | ✅ 由能力定义算出 | 我们更实 |

那一层的实际意义：它的出厂默认来自参数注册表的 `defaultValue`（74 条全机型共用、只读），所以"机型基底"这一层才能只写 18 项、版本层只写 15 项。我们没有出厂层，于是机型基底被迫承担"全部字段的初值"，`A2L`（基底空）就只能是"未配置"而不是"全部继承出厂默认"。

## 2. 信息架构：一棵树 + 三个视角 + 维护四项

```
┌ 状态条（11px）────────────────────────────────────────┐  结构带 1
├ 文件头（44px：图标 + 名 + 徽章 + 动作）───────────────┤  结构带 2
├──────────────┬───────────────────────────────────────┤
│ 配方本树      │ [参数] [套餐与菜单] [生成 N]           │
│ （常驻）      ├───────────────────────────────────────┤
│ ─────────    │                                       │
│ 维护          │  视角内容（卡片，圆角只在上方两角）    │
│  字段定义     │                                       │
│  仓库盘点     │                                       │
│  应急规则     │                                       │
│  回收站 N     │                                       │
├──────────────┴───────────────────────────────────────┤
│ 底部条（30px）                                        │  结构带 3
└──────────────────────────────────────────────────────┘
```

三条纪律，写在 `AppB03.tsx` 头注释里：

1. **树常驻，不是"当前对象选择器"。** 上一版把「当前机型 + 当前版本」做成全局上下文，等于强迫你一个一个改。
2. **三个视角是视角不是步骤**，随便切，没有前后关系。
3. **维护四项不属于任何机型版本，不受树的选中影响。** 渲染优先级：维护页 > 视角；点第二次同一项取消。

`AppB03` 自己不收 props，只做三件事：算徽章数字、拼动作数组、`renderPane()` 分发。视角组件**一律只收一个 prop `book`** —— 换实现不动外壳。


**颜色语义的三条硬规矩**（散落在各 CSS 注释里，值得照抄）：

- 蓝 `--w-primary` = **草稿描边**，不是底色：`box-shadow: inset 0 0 0 1px var(--w-primary)`，理由是"这样『是什么来源』与『改没改』两条信息都在"。

### 布局骨架（AppB03.module.css）

- 根 `.shell`：`position: relative`（**整稿浮层的包含块**，全部 absolute 不用 fixed —— 因为预览外壳有 transform，fixed 会量错坐标）、`flex column`、`overflow: hidden`
- `.body`：`flex` 两栏，`min-height: 0`
- `.side`：`flex: 0 0 auto; width: 260px`，右侧 1px 线
- `.pane`：卡片，`margin: -1px 16px 16px`（负 1px 让它和选中的页签咬合）、`border-radius: 0 12px 12px`
- **滚动容器只在最内层**（矩阵的 `.scroll`、树的 `.list`），外层一律 `min-height: 0` 不滚

### 响应式：ResizeObserver 量容器，不是 media query

```ts
export type Density = 'ultra' | 'wide' | 'compact' | 'mini'
export const DENSITY_BREAKPOINTS = { ultra: 1600, wide: 1080, compact: 640 }
```
结果写到根节点 `data-density`，CSS 里 `[data-density='mini'] …` 生效。**量的是容器实测宽度**，所以同一个组件放进 400px 的预览窗里也会正确降级。

mini 档的纪律写得很硬：**不许 `display: none` 掉任何一个可用操作**。所以 mini 下是：左右两栏改上下堆叠、侧栏限高 45% 自己滚、维护四项从竖排改横排（注释里记了实测数据：竖排占 154px，侧栏在 400×560 下只有 195px，减掉树头之后列表只剩 8px，六台机型十个版本全被裁在滚动区外，Playwright 报「维护 / mItem 拦截了指针事件」）。

## 4. 数据模型（recipeModelB03.ts，纯函数无 hook）

### 为什么规则层单独一个文件

> 能用 esbuild + node 直接跑真数据实测（B03 还没注册进 registry，界面跑不起来，但"改 A1 基底会影响几个版本"这种事必须在写界面之前验过）

### 三层 + 版本身份

```ts
export interface VersionB03 {
  uid: string          // 前端侧稳定身份，移动归属不改
  id: string           // 契约 id，同机型下唯一，跨机型会重名
  name: string
  machineId: string
  overrides: Record<string, string>   // 只存有值的字段
  bbsOverride?: string[]              // 不给 = 继承机型默认
  builtSnapshot?: Record<string, string>  // 上次成功生成时用的有效值
  builtAt?: string
  archived: boolean
  fresh: boolean       // 这一轮新建的，还没保存
}

export interface MachineB03 {
  id: string
  base: Record<string, string>
  bbsDefaults: string[]
  versions: VersionB03[]   // 含归档的
}
```

**uid 的必要性**（这条我们踩得到）：契约里 `RecipeVersion.id` 不唯一（A1 与 A1_MINI 下都有 `STANDARD`），而"机型 + id"这个组合键会在移动归属后变掉，于是选中、草稿、勾选列会全部指错。所以前端给每个版本一个稳定 uid：加载来的是 `'A1/STANDARD'`（用**加载时**的机型），新建的是 `'new-1'`。uid 不写回后端。

### 写入的唯一载荷

```ts
export type PatchB03 =
  | { level: 'machine'; machineId: string; key: string; value: string | null }
  | { level: 'version'; versionUid: string; key: string; value: string | null }
```

两条语义写死在注释里：

- **必须带 level。** 没有它批量改就只能靠调用方猜，"猜错的后果是静默打破继承"。
- **`value: null` = 删键 = 挂回继承。** 不是"值设成空"—— 空串是合法值（两个 G-code 字段的出厂默认就是空串）。

由此得出一条漂亮的推论：**没有"脱钩"标记，脱钩的载体就是"这个键在不在这一层"，所以它天然是按项算的，不是按版本算的。**

### 草稿：只存"改了什么"

```ts
export interface DraftB03 {
  values: Record<string, string | null>   // 'm:A1:key' / 'v:A1/FAST:key'
  added: VersionB03[]
  renamed: Record<string, string>
  moved: Record<string, string>
  archived: Record<string, boolean>
  bbs: Record<string, string[] | null>    // null = 挂回继承
  purged: string[]
  built: Record<string, { snapshot: Record<string, string>; at: string }>
  seq: number
}
```

理由：**存整本的话，后端数据一变，草稿就会把旧值糊回去。** 这个形状可 JSON 序列化，直接进 localStorage。

`applyDraftB03(saved, draft)` 的顺序有讲究：**先结构（删/改名/移动/归档/新增/生成记录），再值** —— 反过来的话新建版本上的值会因为"那时还没有这个版本"而被丢掉。另有一处容错：移到不存在的机型上就当没移（"那会让这个版本从树上整个消失，比不动更糟"）。

`draftSizeB03` 把**结构操作也各算一处**——它们和改一个值一样要被"保存"。

### 三层取值

```ts
export function effectiveB03(machines, factoryOf, machineId, versionUid, key): EffectiveB03 | undefined {
  // 版本覆盖 → 机型基底 → 出厂默认，第一个命中即返回，并带回 layer
}
```
返回 `undefined` 是"这个机型/版本/字段不存在"，**和"值是空串"分得开**。

### 生成状态四档

```ts
export type BuildStateB03 = 'built' | 'stale' | 'never' | 'unavailable'
export const BUILD_STATE_TEXT = {
  built: '已生成', stale: '待生成', never: '未生成', unavailable: '暂无资源',
}
```

`unavailable` 的判据是 `hasResources`（有没有 MKP 预设或任何 BBS），注释：「A2L 就是这样，是**还没配**不是出错」。

## 5. 数据层 API（useRecipeBookB03 的 `RecipeBookB03` 接口）

这是三个视角 + 四个维护页的**唯一**数据入口，48 个成员。摘关键：

## 6. 视角一：参数矩阵（这一稿的技术核心）

### 6.1 列不是"当前对象"，是一份可以同时看好几个的清单

```ts
export interface ColB03 {
  key: string            // 与树上的勾选同一套（colKeyB03）
  machineId: string
  versionUid: string | null   // null = 这一列是机型基底那一列
  level: 'machine' | 'version'
  machine: string        // 列头第一行 'A1'
  label: string          // 列头第二行 '基底' / '标准版'
  own: number            // 这一层自己写了几项
}
```

六个纯函数，三条判定值得照抄：

| 函数 | 关键判定 |
|---|---|
| `colsOfB03(book, showAll)` | 遍历 `treeMachines`（已过滤归档）→ 每台机型先 push 基底列，再 push 命中勾选的版本列。**顺序照配方本的顺序，不按点击顺序** —— 点击顺序会让同一份数据每次长得不一样 |
| `rowsOfB03(book, cols)` | **取并集不取交集** —— 交集会让"只有 P1S 有的那几条"在勾了 P1S 的时候凭空消失 |
| `matchQueryB03(row, query)` | 搜索**跨全部分类**，命中 `label`/`key`/`tomlKey`/`group`/`def.desc` 五个字段。注释记了踩坑：「只搜当前页签，于是搜一个明明存在的字段却得 0 条，而『它在别的分类里』这件事界面一个字都没说」 |

搜索一开，分类过滤让开；页签 title 换成「搜索中 —— 搜索跨全部分类，分类过滤先让开」；点任一页签先清空搜索。

### 6.2 表格布局

原生 `<table>` + `position: sticky` 双向冻结，**没有虚拟滚动**：

- `th.corner`「字段 / 对象」：`sticky top + left`，`z-index: 3`
- `th.colHead`：`sticky top`，`z-index: 2`，`min-width: 160px`
- `th.rowHead`：`sticky left`，`z-index: 1`，`width: 240px`
- `border-collapse: separate`（collapse 会让 sticky 的边框丢失）

性能走的是另一条路：**默认纯文本，点中了才升级成受控控件**。理由原文：「67 行 × 最多 16 列。全都做成受控输入是 1000 多个 state 与 1000 多次 re-render，而且同屏一片输入框」。

### 6.3 单元格四条互斥分支（顺序即优先级）

1. **不适用** —— `def === undefined || hit === undefined`：显示「不适用」，title「这台机型的机型过滤把这个字段排除了 —— 它没有这一项，不是值为空」
2. **G-code** —— 显示 `{N} 行 · 点开` 按钮，一律走右抽屉
3. **可编辑** —— 底色 `--w-primary-soft`，换成 `FieldControl form="cell"`
4. **只读文本** —— 显示 `valueTextB03(值)`，被上级条件关着时压暗 + title「改不动：由「{父字段}」控制，需{条件}」

**"不适用" 与 "被关着" 是两件不同的事**，注释分得很清：前者是这台机型根本没有这一项（`machineFilter`），后者是有这一项但被上级字段的条件关掉了 —— **看得见、改不动，并且写明由谁控制**。

值的显示统一走：

```ts
export function valueTextB03(raw, def): string {
  if (raw === '') return '空'                        // 空串显示「空」，不是空白
  if (control === 'switch') return raw === 'true' ? '开启' : '关闭'
  if (choices) return 命中的 choice.label ?? raw
  return raw
}
```

### 6.4 来源徽章：三档 + 草稿叠加

```ts
export const ORIGIN_TEXT = { factory: '出厂', machine: '机型', version: '版本' }
export const ORIGIN_WHY = {
  factory: '出厂默认 · 机型与版本都没写过这一项',
  machine: '机型基底 · 改它，这台机型下没自己写过这一项的版本全跟着变',
```

`draft=true` 时 title 追加 ` · 已改动未保存`，视觉上只加一圈蓝描边。

### 6.5 三种改法，一个写入口

## 7. 视角二：套餐与菜单（一屏三件事）

### 7.1 套餐卡片

### 7.2 版本的 BBS 归属

- 脱钩：title `脱钩：从机型默认复制一份，之后这个版本自己负责`

切回继承时先问一句（会丢掉本版本自己那份清单），按钮 title「挂回继承机型默认」。

### 7.3 菜单表

## 8. 视角三：生成 + 校验（工作流 SOP 的落点）

`BuildB03` 把 `IssuesB03` 并在**最上面** —— 它回答的就是"现在能不能生成"。

### 8.1 校验：三档，每条都能"去处理"

```ts
const LEVEL_TEXT = { blocking: '阻断', todo: '待办', info: '提示' }
const LEVEL_WHY = {
  blocking: '数据自相矛盾，生成一定出错 —— 这一档挡生成',
  todo: '要人去填的空。不挡生成',
  info: '合法，但值得知道。不挡生成',

```

**三档的分界是"能不能往下走"，阻断是全程唯一的硬闸门。** 每条一行：`[阻断] {消息} {参数 · A1 / STANDARD} [去处理 →]`

`去处理 →` 会 `setUi({ view: issue.view })` + `selectPrimary(machineId, uid)`。头注释：「一条说不清去哪儿的问题等于没报 —— 上一版那张问题列表就是只有文字，于是每条都得自己找。」

零问题不留白，显示逐字：

> `没有问题，可以生成。（阻断 0 · 待办 0 · 提示 0 —— 这一行不是空白，是真的都过了）`

「有 N 个文件未分配」刻意放在**提示**那一档：「仓库里放一个 0.2mm 的 profile 不分配给谁，是一种正常的交付身份（可选），不是一件待修的事」。

**确认**：标题 `生成`，flag `{N} 个版本`，note `假后端不落盘 —— 这一步只演示「先算完全部产物再一次性替换」这条语义`。每行显示 `首次生成 · {N} 项` / `无差异 · 重写一遍` / `变更 {N} 项`。有算不出产物的则顶部红字：

## 11. 四个维护页

### 11.1 字段定义（只读，74 条）

**为什么必须自己拉 `getParamMeta()` 而不用 `defsOf(机型)`**：后者已按 `machineFilter` 与废弃过滤，只有 67 条 —— 少的那 7 条恰恰是"这张表在管什么"的一部分（旧字段还在注册表里，只是不再显示）。

六列：`字段` / `TOML 键` / `分组` / `类型 / 控件` / `作用域` / `可见性条件`。三档筛选 pill 带实算计数：`全部 74` / `在用 67` / `已废弃 7`。搜索 placeholder「搜字段名 / 键名 / 分组」。

说明带逐字（数字实算；下面的具体数值是形态示例）：

> `74 条字段定义 · 在用 67 · 已废弃 7 · 12 个分组 · 这一页只看：增删字段、改类型、改范围都要改注册表并写盘，这一稿没做`

读失败时两行：

> `读不到字段定义：{原因}`
> `（不装成空表 —— 显示「0 个字段」会让人以为注册表是空的）`

详情抽屉 16 行键值（`key` / `tomlKey` / `jsonKey` / `configKey` / `TOML 节` / `布局分组` / `作用域` / `版本粒度` / `值类型` / `控件` / `单位` / `行尾注释` / `合并组` / `机型限定` / `可见性条件` / `约束`），加一段「出厂默认（各机型）」逐机型列值，取不到时：`这台机型看不到这个字段（machineFilter 排除）`。废弃字段末尾：

> `这条已废弃：还在注册表里，但不再显示、不进产物。删掉它要改注册表并处理历史数据。`

### 11.2 应急规则（回退登记表，20 条 / 五类 / 两档）

这是我们完全没有的一块。它是"厨房应急手册"：**输入不完整或自相矛盾时，构建流程会自动做什么补救**。

```ts
export interface FallbackRule {
  id: string
  category: 'override' | 'infer' | 'default' | 'migration' | 'recovery'
  trigger: string       // 什么情况下触发
  from: string
  to: string
  severity: 'info' | 'warn'
  desc: string
  reportField: string   // 触发后写进执行报告的哪个字段
  enabled: boolean
}
```

```ts
CATEGORY_TEXT = { override: '覆盖', infer: '推断', default: '默认', migration: '迁移', recovery: '恢复' }
CATEGORY_DESC = {
  override: '强行改掉原来的值：你设了 A，程序用了 B',
  infer: '不知道就根据其他信息猜（G-code 元数据、回抽量反推）',
  default: '你没填就给默认值',
  migration: '旧版字段名升级成新版字段名',
  recovery: '正常方法失败了，换个办法再试',
}
SEVERITY_DESC = {
  info: 'L2 默认填充类：你没设置时补默认。开启放行不留痕',
  warn: 'L1 改写类：覆盖你显式设置的值。开启则执行并留痕，关闭则报错中止',
}
```

界面四段：可折叠说明块（标题「这张表在管什么」，正文是上游 `guide` 原文，`pre-wrap` + 限高 148px 自己滚）/ 筛选条（分类单选 + severity 多选）/ 统计带 / 六列表格（`ID` / `类型` / `FROM → TO` / `级别` / `说明` / `启用`）。

唯一可写的是「启用」开关，只进组件内存。本地脏态模型干净得值得照抄：`enabledOf = edits[id] ?? r.enabled`；`toggle()` 里**改回原值就把这一条删掉**，所以"改了几处"不会虚高。脏行样式：淡蓝底 + 左侧 2px 主色竖条。

### 11.3 仓库盘点（18 行宽表，全静态）

**零 state** —— 没有搜索、没有筛选、没有排序、没有抽屉、没有写操作。理由是它只有 18 行，全部信息行内一次给完。这和字段定义（74 行，必须筛 + 搜 + 抽屉）是刻意的设计分野。

统计带逐字（模板原文，数字全部实算 —— 下面的具体数值是形态示例，不是我实跑出来的）：

> `18 个文件 = 6 个 MKP + 12 个 BBS · 套餐 3 个 · 已分配 9 · 可选 6 · 仅归档 3 · 身份在「套餐与菜单」视角里改 · 含 2 处未保存的改动`

三态呈现：**已分配与可选在视觉上不可区分**（同一个灰 chip），只有 `仅归档` 带琥珀色，且另起一行写 `客户端看不到`。JSX 注释给的理由：

> 「仅归档」要把后果写在行上，不能只藏在 title 里：盘点单是「仓库里有什么」那张表，而仓库里有 ≠ 客户端拿得到。光看「仅归档」三个字看不出它意味着客户端连看都看不到。

大小一列**无条件**显示 `未知`（上游 `PresetFileInfo` 根本没有 size 字段），悬停解释：

> `上游的资产清单里 size 与 sha256 都是空值，真值要到发布打 manifest 时才算得出来。宁可写「未知」，也不造一个看起来煞有介事的数字`

「未分配」在这一页只有行内文案 `没进任何套餐 · 客户端只能手动下`，聚合提醒在另外两处（菜单卡片底部、校验的 info 档）。**「未分配」与「仅归档」是两个正交的轴**，盘点单把它们摆在相邻两列就是为了让组合一眼可读。

### 11.4 回收站（两步彻底删除）

不是表格是列表（`<ul><li>`），扁平不按机型分组。一行：`{机型} / {版本名}` + 事实 + `还原` + `彻底删除`。

三个确认弹窗，**彻底删除是两步**：

```
① 还原
   标题  还原版本
   正文  把「A1 / 快拆版260628」放回配方本？
   后果  它会回到原来的机型下面，自有覆盖一项不少，重新出现在树上与矩阵列里，也重新参与生成。
   按钮  [取消] [还原]

② 彻底删除（第一次）
   标题  彻底删除
   正文  彻底删掉「A1 / 快拆版260628」？
   后果  它会从配方本里消失，连同它自己写的那几条覆盖。这一步之后还有一次确认。
   按钮  [取消] [继续]      ← 红

③ 彻底删除（第二次）
   标题  真的彻底删除
   正文  「A1 / 快拆版260628」将不可还原。
   按钮  [取消] [彻底删除]  ← 红
```

## 12. 基础组件的做法

### 12.1 三个浮层

| | ModalB03 | DrawerB03 | ConfirmDialogB03 |
|---|---|---|---|
| 宽度 | `max-width: 820px` | `width: 320px` | 继承 Modal |
| z-index | scrim 70 | scrim 60 / panel 61 | 70 |
| Esc | ✅ | ✅ | ✅ |
| 遮罩点击 | ✅ | ✅ | = 取消 |
| 焦点管理 | **无**（无 autoFocus、无 trap、无还焦、无 aria-modal） | 无 | 无 |
| 动画 | **无**（整个 b03 目录 grep 不到 transition / keyframes） | 无 | 无 |
| mini 档 | scrim padding 24 → 10 | width → 100% | — |

弹窗高于抽屉，所以抽屉里可以再开弹窗（字段定义、应急规则就这么用）。Modal / Drawer 的 body 都是 `flex: 1 1 auto; min-height: 0; overflow: hidden auto` —— **长内容在弹窗内部滚，头尾不动**。

### 12.2 两个插槽的语义分工（很值得抄）

- **`flag`**（标题右侧橙色标签）= **这次操作的规模 / 风险**：`有变更`、`7 个目标`、`12 项值变了`、`3 个版本`。三处调用都遵守"0 就不显示"，不会出现 `0 个目标`。
- **`note`**（footer 左侧说明）= **按下去会发生什么 / 不会发生什么**：`假后端不落盘，这一步只演示会写哪些文件`、`A1 → P1S。覆盖项原样保留，继承值换成新机型的基底`。

### 12.3 差异视图

左右对照（`grid-template-columns: 1fr 1fr`），每条三段：一行 `where`（**无衬线** —— 注释「它是说明不是代码」）+ 层徽标，然后左 `- {key} = {before}`（红 10%）右 `+ {key} = {after}`（绿 12%）。`max-height: 320px` 自己滚。空态 `没有差异`。

**每行都带层标签**（`机型基底` / `版本覆盖`），理由：「一次批量可以同时写机型基底与版本覆盖，看 diff 的人必须能分出『这一行改的是基底（会影响别的版本）』还是『只改这一个版本』。」

## 13. 假数据 / 假后端的做法

它不是"前端硬编码假数据"，而是**一个完整的契约 + 一个内存后端**：

```
src/api/contract.ts        全部类型定义（ParamMeta / RecipeBookMachine / PresetFileInfo /
                           MenuEntry / BundleDef / FallbackRegistry / RecipeIssue / ClientDataMeta …）
src/api/index.ts           api.getParamMeta() / getRecipeBook() / saveRecipeBook() /
                           getPresetFiles() / getMenu() / getBundles() / getFallbackRegistry() /
                           getRecipeIssues() …
src/server/**              内存实现。resolve/recipe.ts 里有真正的校验逻辑（issues 就是它算的）
```

四条做法值得照搬：

1. **契约先行。** 前端只认 `contract.ts`，换成真后端时改 `src/server`，页面一行不动。我们这边等价物是 Tauri 命令 + `api.ts` 的手抄镜像 —— 但我们**没有契约文件**，类型靠两边手抄，这是隐患。
2. **校验在"后端"算，不在组件里算。** `getRecipeIssues()` 读当前内存里的配方本/菜单/套餐，返回 `RecipeIssue[]`；组件只负责分档显示与跳转。我们的 preflight 在 Rust 侧，这点一致。
3. **假后端不落盘，而且到处说清楚。** 界面上反复出现 `写进假后端的内存（刷新还原）`、`假后端不落盘 —— 这一步只演示……这条语义`。**不假装自己能做到做不到的事。**
4. **"不装成空表"是一条贯穿全稿的纪律。** 每个读数据的地方，失败都显示原因 + 一句解释为什么不显示 0：

```
读不到配方本：{原因}
（这里不装成空表 —— 显示「共 0 个机型」会让人以为配方本是空的）

读不到菜单与套餐：{原因}
（不装成空表 —— 显示「0 个套餐」会让人以为套餐被删光了）

读不到字段定义：{原因}
（不装成空表 —— 显示「0 个字段」会让人以为注册表是空的）
```

## 14. 它的文案纪律（单独一节，因为这是它最强的地方）

**所有状态词与所有"为什么"都集中在两个文件里，一个词只有一个出处。**

`facts.ts` 头注释把理由说透了：

> 「已分配 / 可选 / 仅归档」这三个词会同时出现在套餐与菜单视角、仓库盘点、生成前的提示里。各写一遍的下场见 v034 的教训（同一个状态在一处叫「可选」另一处叫「未关联」）—— 界面开始自相矛盾，而两边看起来都对。

集中管理的清单：

| 文件 | 管什么 |
|---|---|
| `facts.ts` | `UNKNOWN` `NONE` `KIND_LABEL` `KIND_NAME` `VIS_TEXT` `VIS_WHY` `ARCHIVED_NOTE` `CATEGORY_TEXT/DESC` `SEVERITY_DESC` + 判据函数 |
| `origin.ts` | `ORIGIN_TEXT` `ORIGIN_WHY` |
| `recipeModelB03.ts` | `BUILD_STATE_TEXT` |
| `shell/types.ts` + `StatusStripB03` | `ARTIFACT_TEXT` |
| `IssuesB03.tsx` | `LEVEL_TEXT` `LEVEL_WHY` `VIEW_TEXT` |

还有两条更细的纪律：

- **空值一律有说法，不显示空白。** `NONE = '——'`，注释：「空白分不清『没有』与『没画出来』」。
- **每个禁用的按钮都有一句"为什么不能点"。** `PageActionB03.title` 的注释：「禁用的动作必须给一句「为什么不能点」，否则灰按钮就是个谜」。实例：`没有未保存的改动` / `没有可撤销的改动` / `一个都没勾` / `从来没生成过，没有可比的快照` / `配方和上次生成时一样，没什么可恢复`。

## 15. 差距清单：我们缺什么

按"缺失代价"排序，不按工作量。

### A 类：模型级缺失，会影响正确性

1. **没有出厂默认层。** 我们只有两层，于是 `A2L`（基底空）只能是"未配置"。它有三层，`A2L` 的每个字段都能回落到注册表 `defaultValue`。**这一条不补，"未配置"这个状态的含义就和它不一样。**
2. **没有版本稳定 uid。** 我们用 `machine/version` 路径当身份，换机型会让草稿、快照、选中全部指错 —— 我们的 `rename_snapshot` / `relink_version` 是在**事后搬运**来绕过这个问题，它是在**前端给一个不变的 uid** 从根上避免。
3. **没有 `showWhen` 条件字段。** 于是我们没有"看得见改不动"这个状态，也没有"由「X」控制，需 Y"这句话。批量编辑时我们也就不会跳过被关着的目标。
4. **没有撤销 / 重做。** 它是双栈 + `apply(label, patches)` 一次手势一条撤销，标签人类可读。我们连一层都没有 —— 批量改错一次只能手工改回去。

### B 类：交互缺失，会让人不想用

5. **矩阵的列不是勾选驱动的多机型清单。** 我们的矩阵是"选机型 → 看它的版本"，它是"在树上勾任意多个机型的基底列与版本列 → 一起看"。**"机型基底作为矩阵的一列"这个想法我们完全没有**，而它正是"改基底 vs 改版本"能在同一张表里对比的前提。
6. **只有一种改法。** 它有三种：点格 / 列编辑 / 行批量。我们只有底部一个批量表单。
7. **G-code 没有专门的编辑路径。** 它一律走右抽屉，并且**批量时明确拒绝**（「批量盖掉整段太危险」）。我们的 G-code 就是个 textarea，批量也能盖。
8. **校验只有两档且不能跳转。** 它三档（阻断/待办/提示）+ 每条 `去处理 →` 跳到对应视角并定位主选中。我们是阻断/非阻断，且只能看文字自己找。
9. **生成表没有"看差异"。** 它能弹出"当前配方 vs 上次生成时用的配方"逐字段三列表，note 明写"判据是这张表，不是文件修改时间"。我们只有一个 hash 相不相等。
10. **没有应急规则（回退登记表）这一整块。** 我们有一个空的 `fallback.json` 和一个进 hash 的指纹，**没有任何界面、没有任何规则**。
11. **没有仓库盘点页。** 我们的 BBS 列表≈它的一部分，但没有"未分配 / 仅归档两个正交轴摆相邻两列"这种设计。
12. **彻底删除只确认一次。** 它是两步。
13. **完全没有响应式。** 它有四档密度 + ResizeObserver + "mini 档不许藏掉任何可用操作"的纪律和实测记录。

### C 类：工程与表达缺失，会让它显得"一般"

14. **文案没有集中出处。** 我们的状态词、提示语散落在 7 个 tsx 里，同一件事在不同页可能说法不同 —— 它把这条当成过去踩过的坑专门建了 `facts.ts`。
15. **没有"为什么不能点"。** 我们的禁用按钮大多没有 title。
16. **没有"不装成空表"的统一处理。** 我们部分地方有，不成体系。
17. **没有 `flag` / `note` 这种插槽语义分工。** 我们的弹窗提示是随手写的段落。
18. **没有契约文件。** 我们的 TS 类型是 Rust 结构的手抄镜像，靠注释提醒"改一边时另一边有迹可循" —— 它有 `contract.ts` 作为单一真相源。
19. **没有拖动排序。** 套餐内文件顺序它能拖。
20. **视觉规范薄。** 它有一份 109 行、按语义分组、每组都写了理由的 tokens；我们是在 CSS 里就地写值 + 一堆 `var(..., 回退值)`。

### 三条它做到而我们做到了的（记账要两头记）

- 「已生成」不说「已同步」，四阶段分开 —— 双方都写在了注释里。
- 生成原子 + 失败不碰旧产物 —— 我们甚至更实（真的原子写 + rename）。
- `minClientVersion` 不瞎填 —— 它摆一个 disabled 输入框说明"要客户端先给清单"，我们**真的**按能力定义算出来了，这一项我们更强。

## 16. 一句话总结

它和我们要解决的是同一个问题、同一套边界、同一批决策。差别不在"做没做"，在**做到哪一层**：

> 我们做了一个正确的后端，加一套能用的表单。
> 它做了一个**产品**：三层取值、撤销栈、三种改法、跳得过去的校验、每个禁用都有理由、每个状态词只有一个出处、每处"我做不到"都写在界面上。

想追平的话，**A 类四条（出厂层 / 稳定 uid / showWhen / 撤销）是地基，必须先补**；B 类里第 5 条（勾选驱动的多列矩阵）是它整套交互的枢纽，补了它，6/7/8 才有地方落。
