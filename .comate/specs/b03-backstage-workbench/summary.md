## 一、最后长成什么样

工作台是**同仓库里的第二个窗口**，与客户端共用 Tauri 壳与错误/日志模型，但页面与命令都不进客户端构建。

七个页签，顺序就是工作顺序：

| 页签 | 干什么 |
|---|---|
| 配方 | 按机型/版本改参数，逐字段显示来源（继承 / 本版覆盖），可清除覆盖；另有「机型基底」编辑目标 |
| 参数矩阵 | 横着看多个版本，显式勾列做批量修改（预览后确认） |
| 结构 / 回收站 | 新建、克隆、改名、换机型（带变化预览）、删除、还原、彻底删除 |
| 预设 / 资源 | TOML 生成状态（逐版本）+ BBS 收录与三态 |
| 菜单 / 套餐 | 上下架、改显示名、配套餐 |
| 生成 / 发布 | 生成待更新项 → 出货检查 → 发布，三步三个按钮 |
| 字段定义 | 只读 |

## 三、值得单独说的几处判定

**状态是比出来的。** 判据是「当前有效配方的 sha256」对「上次成功生成时快照里记的那个」，**不看文件修改时间**。产物字节没变时连文件都不重写 —— mtime 一变，同步工具就可能让顾客莫名收到更新提示。

**"未配置"与"生成失败"分开。** 前者是有效配方为空（配方本上有名字、下面一行没写），后者是上次尝试没成而**上次成功的产物还在**。判据刻意落在"有效配方为空"而不是"版本覆盖为空"——后者会把「完全继承机型基底」的正常版本也误判成未配置。

**改基底 vs 改版本值在类型上就分开。** 批量编辑的目标是枚举（`VersionOverride` / `MachineBase`），没有"选了版本却写到基底"这条路。测试里两个方向各钉了一条：改版本不动基底、改基底不给任何版本造覆盖。

**能力定义是只读输入。** `capability.rs` 里没有写入函数（不是"有但不调"），还有一条断言扫自己的源码，哪天有人加了 `save_capability` 会立刻红。缺文件一律报"无法校验兼容性"并**归为阻断**——否则兼容性就是靠运气。

**`minClientVersion` 由生成时算出来**：支持期内哪些客户端吃得下这份配方，取其中最低的那个；一个都不支持就阻断生成并说清"先升级客户端"。发布时不重算，只搬运——重算就成了第二个真相源。

**发布把 `catalog.json` 放最后写。** 先写它，客户端就可能读到"目录说有、文件还没到"的中间态。有一条断言直接看写盘顺序列表的最后一项。

**开发配方不进发布目录。** 有一条断言遍历发布目录，确认 `registry.json` / `fallback.json` / `machines/` 一个都没出现。

## 四、实施中纠正过三处

1. **`atomic_write` 不重写一遍。** tasks.md 3.1 原文是"实现 atomic_write"，但仓库里已经有唯一的写盘出口 `fsx::atomic`，而且 `clippy.toml` 把 `std::fs::write` 列进了 `disallowed-methods` —— 再写一份不只是重复，是把那道机器判据绕开。改成复用。

2. **生成/状态/发布不读进程环境变量定位发布目录。** 一开始的测试用 `std::env::set_var("MKPSE_REPO_DIR", …)`，那是整个进程共享的，`cargo test` 默认并行 —— 一个测试改了它就把别的测试指到错地方，而这种失败看起来像随机偶发。改成把 `dist_root` 作为参数显式传入。

3. **一条测试的预期本身是错的。** "改了机型基底后产物应当变成待生成"实测为 Generated，而且**这是对的**：那个基底字段正好被本版覆盖遮住，有效配方一个字节都没变。已把结论与理由写进那条测试，并另加一条正面样例覆盖"恢复到与上次生成时不同的配方 → 仍是待生成"。

另有两处对 doc 的有意收窄，也都写在代码注释里：

- **未配置且没上架的版本只给提示，不阻断发布。** doc §12 举例里一律写成阻断；但仓库里留一个刚建好还没写的版本是正常工作状态，让它拦住整次发布会逼人为了发别的东西先把它删掉。
- **克隆/改名/换机型用了 `tauri:workbench:dev` / `:build` 两个脚本名**，而不是 tasks.md 1.6 写的单个 `tauri:workbench` —— `--config` 是子命令的参数不是全局参数，单脚本 + `npm run … -- dev` 的参数顺序过不去。

## 五、跑过什么

| 判据 | 结果 |
|---|---|
| `cargo test`（默认 features） | 18 passed / 0 failed |
| `cargo test --features workbench` | **126 passed / 0 failed** |
| `cargo clippy --all-targets`（两种 feature 组合各一次） | 零 warning |
| `npm run build` / `npm run build:workbench` | 两次都过（`tsc -b` 含在内） |
| `npm run lint`（eslint + stylelint） | 零 problem |
| 二进制隔离 | 负例/正例各一次，见第二节 |
| 端到端链路 | `workbench/e2e.rs` 两条：全链路走通 + "没生成就发布"被拦住 |

端到端那条覆盖：首次启动（不写配方）→ 建机型版本 → 改了不保存 → 重开草稿还在 → 保存（不自动生成）→ 生成待更新项 → 收录 BBS（默认仅归档）→ 上架 → 编套餐 → 出货检查 → 发布 → 再改一笔立刻回到待生成。

## 六、没做的事（如实登记，不算完成）

1. **GUI 没有被人点过。** 上面所有判据走的都是 Rust 侧函数与构建产物，不是真实窗口里的点击。`npm run tauri:workbench:dev` 能不能开出窗口、七个页签点起来顺不顺手，**本轮没有验证过**。这是最大的一块缺口。
2. **`tauri build`（release 打包）没跑。** 默认与工作台两种组合的 `cargo build` + 前端构建都过了，但完整打包（MSI/NSIS）没试 —— 它慢，而且可能缺 WiX 之类的打包工具链，失败了也说明不了代码问题。
3. **`workbench/capability/client-0.0.1.json` 是我按当前 registry 手写的**，不是客户端导出的。它的字段与区间目前抄自 `registry.json` —— 也就是说"客户端支持什么"这件事现在还没有独立来源。doc §3.2 已经把这条标成实现边界：理想形态是客户端构建时导出。**在那之前，兼容性校验能挡住的只是"配方超出了我以为客户端支持的范围"。**
4. **BBS 收录靠粘路径**，没有系统文件对话框 —— 本仓库没装 tauri 的 dialog 插件，为工作台单独引一个会连带改客户端的权限清单。
5. **`mkpse-presets/presets/bbs/` 当前实测是空的**（只有 `Process/` 与 `.keep`），所以 BBS 那一栏交付的是"导入按钮 + 空清单 + 三态标记"，没有伪造样本。
6. **写盘的原子性是文件级，不是批次级。** 一批生成到第 3 个时断电，前两个是新的、后面是旧的；但每个文件自己完整，不会出现半个 TOML。真正被这套顺序挡住的是另一类失败：校验与渲染全在写盘之前做完，所以"配方有问题"永远碰不到旧产物。
7. **客户端侧一行没写。** 内置能力定义、读 `catalog.json`、按 `minClientVersion` 过滤并提示升级、官方文件只读 / 用户副本、旧版归档 —— 全部属消费端，本稿只产出它需要的数据与身份字段。
