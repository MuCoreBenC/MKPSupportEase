# B03 配方台：默认视角换成「分组列表 + 右抽屉」，矩阵降级为对比工具

这一份处理三件事，来源都是刚才那轮真机试用：

1. **一个真 bug**：改过去改不回来。已经定位并修掉（根因在下面 §1，不是后端算错）。
2. **卡**：一次手势现在要走两次全量派生 + 一次磁盘原子写，dev 下还全部 ×2。
3. **形态不对**：矩阵当默认视角，本来就不好看也不方便改。参照 `mkpse-next-v3/mkppanel`
   已经迭代很多轮的那套「分组列表 + 右抽屉 + 批量模态框」，把它当默认，矩阵退成对比工具。

三个已定的决议：

| # | 决议 |
|---|---|
| A | **草稿以 Rust 内存为真相**，懒落盘（空闲 2 秒 / 窗口失焦 / 生成前各写一次快照） |
| B | **分两页**：默认页只改配方值；字段定义单独一个维护页，页上明确标出「这是在改上游」 |
| C | **矩阵降级成次要页签**，默认进分组列表，想横向比几列时才切过去 |

---

## 1. 那个「改不回去」的 bug：界面没刷新，不是后端算错

日志（`wb_apply_draft` 每次都 ok，`草稿已更新 patches=1`），但**其中几次后面没有跟着 `wb_matrix`**：

```
02:43:33 apply 擦料方式  → 没有 matrix
02:43:38 apply 擦料方式  → 没有 matrix
02:43:51 apply 擦料方式  → 没有 matrix
02:43:53 apply 擦料方式  → 没有 matrix
```

根因在 `App.tsx`：矩阵的重取信号写的是 `dirtyKey={book.dirtyCount}`。

而「把某个版本覆盖从 `disk` 改成 `tower`」这件事**脏计数一个不变** ——
草稿里那一条还在（这一层本来没有自有值，写 `tower` 也是一条自有值），只是值换了。
计数不变 ⇒ `dirtyKey` 不变 ⇒ 矩阵不重取 ⇒ 格子上还显示 `disk`。
再点开那个下拉，回填用的是**旧的** `cell.raw`，于是永远显示 `disk`，怎么点都「改不回去」。

后端每一次都写对了。

**已修**：改成一个只增不减的 `tick`，**每写一次 +1**，与改了几处无关。
`dirtyCount` 这种「业务计数」永远不该当刷新信号 —— 它可以在状态真的变了的时候保持不变。

这条要进纪律：**刷新信号必须是「发生过一次写」，不能是任何业务量**。

## 2. 卡在哪：一次手势的真实开销

| # | 开销 | 现在 | 改成 |
|---|---|---|---|
| 1 | 草稿原子写（临时文件 + rename，一次 fsync） | **每次编辑一遍** | 内存改完就返回；快照**懒写**（§3） |
| 2 | 全量派生 | **两次**（`wb_apply_draft` 返回 `BookView` 算一次，前端再 `wb_matrix` 算一次） | 一次：`wb_apply_draft` 顺带把当前这一页的数据带回来 |
| 3 | IPC 往返 | 2 次 | 1 次 |
| 4 | dev 下 `React.StrictMode` 让所有 effect 跑两遍 | 全部 ×2（日志里 `wb_boot` / `wb_words` / `wb_registry` 都是成对出现） | 生产构建没有这个问题；但开发时的手感是真的，**首屏那几个请求改成只发一次**（用一个 ref 挡住第二次） |
| 5 | 67 行 × N 列全量重渲染 | 每次 apply 重建整张表 | 分组列表天然只渲染当前分组的十几行 |

第 2 条是最值得改的：现在写一个值，后端把整本书算两遍。
**`wb_apply_draft` 应该一次把调用方要的那一页带回来**，而不是让前端再问一次。

## 3. 草稿：内存为真相，磁盘只是崩溃快照

现在的行为（你问的那个问题的答案）：**是真文件，不是内存**。
`workbench/.draft/book.json`，每一次 `wb_apply_draft` 都走 `atomic_write_json`
（写临时文件 → rename），干净时删掉这个文件。也就是你说的「不停去读写文件」。

改成：

```
Rust 进程内存（SESSION 里的 Draft）   ← 唯一真相，编辑只碰它
        │
        │ 懒写，三个时机：
        │   1. 空闲 2 秒（每次编辑重置计时）
        │   2. 窗口失焦 / 关闭前
        │   3. 生成 / 发布 / 保存之前（这几个动作要有一份对得上的快照）
        ↓
workbench/.draft/book.json          ← 只是崩溃恢复用的快照
```

三条纪律：

- **读只在开场读一次。** 之后内存说什么就是什么，不再回读文件。
  现在的 `state(ctx)` 每次命令都 `read_draft` 一遍 —— 那是把磁盘当状态源，
  也是「三份状态不一致」那个老病的另一种形态。
- **快照写失败不阻断编辑**，只记一条提示。快照的价值是崩溃恢复，
  为了它让一次编辑失败是本末倒置。
- **`.draft/` 仍然保留**，因为「改了一堆没保存，窗口崩了」这件事真的会发生。
  但它从「状态所在地」变成「上一次快照」。

对 `Ctx` 的改动：

```rust
pub struct Ctx {
    pub up: Upstream,
    pub store: Store,
    /// 落盘的那一份（开场读一次，保存时重读）
    committed: Committed,
    /// **草稿的真相在这里**，不在盘上
    draft: Draft,
    /// 懒写用：最后一次编辑的序号与已落盘的序号
    dirty_seq: u64,
    flushed_seq: u64,
}
```

`flushed_seq == dirty_seq` 就是「快照是最新的」，不需要再写。

## 4. 默认视角：分组列表 + 右抽屉（照 mkppanel 的骨架）

```
│ [A1 / 标准版 ▾]   74 个参数   未保存 3 处   ↶撤销 ↷重做 保存 │
├──────────┬──────────────────────────────────────────────────┤
│ 分组树    │ 分组卡片列表                                      │
│ 偏移 5    │ ┌ 擦料方式                              1 项 ─┐  │
│  空间偏移3│ │  擦料方式          string        擦料塔  ✎  │  │
│  运动挤出2│ └────────────────────────────────────────────┘  │
│ 擦料 27   │ ┌ 擦料塔位置与打印                      4 项 ─┐  │
│  擦料方式1│ │  擦料塔X坐标       float         20 mm   ✎  │  │

│ …        │ └────────────────────────────────────────────┘  │
└──────────┴──────────────────────────────────────────────────┘
```

与 mkppanel 的差别（**刻意不做的那些**，你说的「多余」的部分）：

| mkppanel 有 | 我们要不要 | 理由 |
|---|---|---|
| 拖拽排序（`⋮⋮` 手柄） | ❌ | 顺序是上游 `layout.order` 说的，我们不改它 |
| 自由增删 section / 参数（`+` 按钮） | ❌ | 字段清单是上游的 |
| 布局模式、主题工作台那一整套 OTA 化布局 | ❌ | 你已经说了没必要，现在是编译进去的 |
| 父参数/子参数**自由改挂靠** | ❌ | 父子关系是上游数据，我们只**照它显示**（缩进 + 「属于：X」） |
| 右抽屉看全部元数据 | ✅ | 这是它最好的部分 |
| 批量编辑模态框 | ✅ | 但只做「按机型/版本铺值」这一件事 |
| 顶部 SOURCE / ARTIFACT / LAST BUILD 状态条 | ✅ 已有 | 我们那条已经在了 |

### 4.2 一行长什么样

一行只给四样：**中文名 · 类型徽章 · 当前值（带来源色）· 一个展开箭头**。

点一行 → **行内展开**（不是跳走、不是弹窗）：

```
擦料塔X坐标   float                                    20 mm 版本  ⤺
  当前值  [ 20 ] mm                 ← 真控件，就地改
  擦料塔在热床上的X坐标位置 (mm)      ← desc
  ▸ 高级元数据
      键名 wiping.wiper_x · TOML 键 wiper_x · TOML 节 wiping
      来源 版本覆盖（A1 / 标准版） · 出厂默认 20
      受「擦料方式」控制，需 等于 擦料塔
  [在所有机型上看这一项 →]           ← 跳到矩阵，这一行预先展开
```

右抽屉留给「要一次看全」的场合：完整元数据、G-code 全文、按机型的值一览。
抽屉里**不放编辑控件的第二份实现** —— 行内展开与抽屉用同一个 `FieldControl`。

### 4.3 「被上级条件关着」在这里更好办

矩阵里只能靠一小行灰字，列表里可以直接**把子项收到父项下面**：
父项关着的时候，子项整组折起来并写一句「擦料方式选了圆盘擦拭，这 7 项现在不生效」。
点那句话可以展开看（值还在、会进产物），但默认不占地方。

这正好是你说的「要不然他就分到它的子类」。

### 4.4 批量：一个模态框，不是行内条

矩阵里的行内批量条是「多列」语境下的产物。列表里只有一个版本，所以批量的语义变成
**「把这一项铺到哪几个机型/版本」**：

```
批量设置：擦料塔X坐标 = 20
  ☑ A1 · 标准版      现在 20      不变
  ☑ A1 · 快拆版6月   现在 18      → 20
  ☐ A2L · 标准版     暂无资源，跳过
  [取消]  [确认，落一次撤销]
```

影响范围仍然由后端 `wb_preview_bulk` 算，前端不判。

## 5. 字段定义维护页（决议 B）：能改，但**不回写上游**

这一页显示全部 74 条的完整定义，形态照抽屉那份。要能改的话有一个硬约束必须先说清楚：

`mkpse-presets/content/param_registry.json` 是**上游的构建产物**（它的源是
`source/registry/param_registry.ts`，而那个目录我们不读也不该改）。直接回写产物，
上游下一次构建就会把我们的修改冲掉，而且**不会有任何报错** —— 这是最坏的一种丢数据。

所以这一页的写入落到我们自己仓库的一层覆盖上：

```
workbench/registry-overlay.json      我们对字段定义的改动（只存差异）
```

界面与生成 TOML 时都叠加它，页面顶部常驻一句：

> 这一页改的是**字段定义**，不是配方值。改动存在我们仓库的覆盖层里，
> 不回写 mkpse-presets —— 那是上游的构建产物，回写会被下一次构建冲掉。

能改的与不能改的分开：

| 能改 | 不能改 | 为什么 |
|---|---|---|
| 中文标签、描述、单位 | `key` | 它是主键，改了所有引用都断 |
| min / max / step | `tomlKey` / `jsonKey` / `configKey` | 产物的键名，改了客户端读不到 |
| 出厂默认值 | `machineFilter` | 它决定「哪台机型有这一项」，改了会让已有配方值变孤儿 |
| `deprecated` 标记 | `showWhen` / `parentKey` | 它们是上游的逻辑结构，不是外观 |

> **这一条需要你点头**：如果你其实希望直接改 `content/param_registry.json`
> （接受被上游构建冲掉的风险），告诉我，我把覆盖层那一层去掉。

## 7. 边界与异常

| 情形 | 处理 |
|---|---|
| 懒写还没落盘就崩了 | 丢掉最后 ≤2 秒的编辑。接受：代价是几个键，换掉的是每次编辑一次 fsync |
| 快照写失败（磁盘满 / 权限） | 编辑照常进行，状态条上出现「快照写不进去」+ 原因。**不静默** |
| 窗口关闭时还有未 flush 的改动 | 关闭前同步 flush 一次；flush 失败则弹一次确认「未保存的改动可能丢失」 |
| 列表页选中的版本被草稿里的「移动/归档」改了 | 顶部选择器跟着走（uid 稳定，不受改名移动影响） |
| 字段定义覆盖层里有一条指向已经不存在的 key | 开场丢弃并记一条提示，不让整份覆盖失效 |
| 覆盖层改了 min，而已有配方值超出新 min | 记一条**待办**（不是阻断）：值还能生成，但下次编辑时会被控件挡住 |
| 从列表跳矩阵，那一项在别的机型上不适用 | 矩阵照常显示「不适用」那一格，不隐藏这一行 |

## 8. 预期结果

1. 改一个值 → 一次 IPC、一次派生、**零磁盘写**；连续改 10 个值只在停手 2 秒后写一次快照
2. 把「擦料方式」改成圆盘再改回擦料塔，**两次都立刻生效**（这次的 bug 有回归测试兜着）
3. 默认进来看到的是分组列表，一屏十几行、每行看得清值和来源，点一行就地改
4. 父项关掉时子项整组收起，并写明是哪一项关掉的
5. 矩阵还在，但只在「想同时看几台机器的同一项」时才切过去
6. 字段定义那一页能改外观类字段，改动落在我们仓库，**上游一个字节没动**
7. 状态条上「未保存 N 处」与快照状态是两条独立信息，各自说真话
