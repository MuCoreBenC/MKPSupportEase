# 新工作台产品流程与数据契约章程

> **这份文档定位：** 新工作台要**生产什么、消费什么、如何发布**的契约。
> **它不是旧系统的修复计划。** 旧版实现与旧版命名只作为数据来源和经验参考，不作为新系统的设计约束。
>
> **本轮授权边界：** 只产出文档与决策边界。不重构代码、不迁移数据、不重命名任何文件。

---

## 0. 这份文档要解决什么

新工作台的管辖范围已定：**配方域 + 资产域 + 套餐域**。
FAQ、公告、主题、布局、about、model_copy 这些通用客户端内容**不纳入**。

但范围定了不等于结构定了。这次审计发现的核心问题不是"缺少分层"，而是：

> **分层已经成形，可是同一件事实在三到四个地方各有一份写法，而入口和出口都还是空的。**

所以这份文档做六件事：

1. 定义**你怎么完成一项工作**——四阶段产品骨架 + 一个端到端用例（§4）；
2. 把四层的术语钉死，以后不再用"源文件 / JSON / TOML"指代用途；
3. 列出**现状硬事实**（带证据行号），特别是三套并存的预设命名；
4. 给出**文件职责表**——每类文件回答六个问题；
5. 圈出**四项待决策**，其中 D-1 按你的要求摆代价不拍板；
6. 定下**旧版数据迁移与新版初始化原则**（§12）。

### 0.1 一条排序原则

> **先定生产流程，再定文件结构。文件结构服务于流程，不是反过来。**

这一条现在写在文档最前面，是因为上一版章程把顺序搞反了——它先讨论命名和目录，才顺带提到用户操作。本版把 §4 的操作流程提到文件职责表之前。

**没有例外。** 上一版曾把 D-2（命名）写成"必须先修才能继续"，那个论证是错的：它拿现有 `build.rs` 的一段注释当前提，而消费端本身也在重新设计范围内。**正确的顺序是：先定新系统的身份与命名规则，再决定旧数据怎么进来。** 不是先把旧系统修到能继续用。

D-2 因此改写为「统一新系统的版本身份与文件命名规则」（§6），与流程设计**并行确认**，在数据契约冻结前完成。

## 1. 术语：四层，以后只用这套词

| 层 | 名称 | 定义 | 谁写 | 删掉会怎样 |
| --- | --- | --- | --- | --- |
| ① | **源定义文件**（Source Definition） | 描述业务定义的数据：机型是什么、有哪些版本、参数怎么取值、套餐包含什么 | 人（经工作台界面） | **真相丢失**，不可恢复 |
| ② | **原始载荷**（Source Payload） | 被①引用的真实内容本体：参数正文、图片、图标、模型 | 人（放入 / 经工作台管理） | **真相丢失**，不可恢复 |
| ③ | **构建产物**（Build Artifact） | 程序读①②，校验后生成 | 构建器 | 可重新生成，不丢信息 |
| ④ | **交付文件**（Delivery File） | 经筛选、校验后给消费端的输出 | 发布动作 | 可重新发布 |

三条推论，后面反复用到：

- **TOML 不等于源，JSON 不等于产物。** 角色由职责定，不由格式定。本仓已有反例：`presets/machines/A1.toml` 是①，`crates/preset/assets/presets/A1-standard.toml` 是③，两者都是 TOML。
- **SSOT 不是"整个项目只有一个文件"**，而是"每一种业务事实只有一个权威来源"。机型名归机型定义，参数值归配方正文，引用关系归构建结果。
- **②不等于④。** 资产库是管辖范围，交付目录是筛选结果。一张没被任何有效内容引用的图片，不进交付。

### 1.1 业界对照（回答"别的软件怎么做"）

这套分层不是自创结构，是三种成熟模式的同一个骨架：

| 模式 | 代表 | ① 源 | ③ 产物 | ④ 交付 | 有没有工作台 |
| --- | --- | --- | --- | --- | --- |
| 纯 Git + CI | **Bambu Studio / OrcaSlicer 的 profiles** | 手写 JSON + `inherits` 继承树 | CI 展开继承 | 随安装包分发 | **没有**。靠 JSON Schema + CI + PR review 挡错 |
| Git-based CMS | Decap / TinaCMS / Sanity | 界面写回仓库源文件 | SSG 构建 | CDN | **有**，形态与你要做的一致 |
| 资产流水线 | Unity / Unreal | DCC 源文件 + `.meta` 旁挂元数据 | Importer 转中间格式 | 打包成 `.pak` | 有（编辑器本身） |

两点结论：

- 切片机圈子（也就是你的直接对照）**确实没有工作台**，但那不是"程序员死记硬背"——是靠 schema 校验 + CI + code review 把记忆外化成机器可查的规则。你不是程序员，走不了这条路，所以工作台对你是**必需品而不是奢侈品**。
- 旧版 `mkpse-presets` 的三层 = Git-based CMS 的标准形态。**分层原则该保留**。旧版的问题不在层数，在层内粒度：17 个 build step、每个资产一份元数据 TOML、以及把客户端文案内容也塞进同一条流水线。

## 2. 现状审计（事实 + 证据）

### 2.1 好消息：四层已经成形，而且比旧版更硬

| 层 | 现状位置 | 证据 |
| --- | --- | --- |
| ① 源定义 | `presets/machines/*.toml`（6 机型）、`presets/registry/param_registry.toml`（56 KB，参数唯一真源）、`presets/brands.toml`、`presets/layout_schema.toml`、`presets/forbidden_zones/*.toml`（3 份） | `src-tauri/src/workbench/paths.rs:140-146` `presets_root()` 用标志文件定位 |
| ② 原始载荷 | `crates/preset/assets/preset_recipes.toml`（607 行配方正文）；图片在 `public/models/`、`public/printers/` | `crates/preset/assets/preset_recipes.toml:1` 自称"这一份是真源" |
| ③ 构建产物 | `crates/preset/assets/presets/*.toml`（9 份） | `crates/preset/src/generate.rs:47-49` `assets_dir()` |
| ③' 对照基线 | `crates/postprocess/tests/fixtures/presets/*.toml`（9 份） | `crates/preset/src/generate.rs:168-170` `fixtures_dir()` |
| ④ 交付 | `dist-presets/` | `paths.rs:25-27`（刻意不叫 `dist`，避免与 vite 产物混淆） |

判据也已经就位：`gen-presets --check` 逐字节比产物（K-G7）、`--baseline` 比基线（K-G0'）、`builtin_presets_match_dir.rs` 守 `include_str!` 表。**这套机制的清晰度比旧版高，不该推翻。**

### 2.2 问题一：流水线的入口和出口都是空的

- `workbench/` 下 `machines/ bbs/ .draft/ .trash/ .snapshots/` 五个子目录首启建齐（`paths.rs:36`、`:51-55`），**当前全空**。
- `dist-presets/` **当前空**（`paths.rs:58-64`，只有发布动作才写）。

也就是说：工作台的编辑落点和发布落点都还没通电。这解释了你"做了很久却没到以前的效果"的感觉——不是结构没搭，是**两端还没接上**。

### 2.3 问题二（本次最关键）：预设文件名有**三套**并存

| 命名体系 | 样本 | 谁在用 | 证据 |
| --- | --- | --- | --- |
| **A. 产物命名** `{机型}-{变体}.toml` | `A1-fastv3.3.toml` | 入库产物目录、`include_str!` 内置表 | `generate.rs:55-57` `file_name()`；`crates/preset/src/lib.rs:85-122` |
| **B. 云端历史命名** `{代号}{改装后缀}[_{日期}]` | `A1F_260628.toml` | 对照基线目录、**机型定义的 `presetFile` 字段**、派生 IR 夹具 | `presets/machines/A1.toml:50,58,66`；`crates/postprocess/tests/fixtures/ir/build9/*.json` |
| **C. 消费端期望** `{机型}-{版本id小写}.toml` | `A1-fastv3.3.toml` | 工作台发布路径 | `src-tauri/src/workbench/app/build.rs:206-215`、`:219-221` `preset_file_name()` |

A 与 C **看起来一样但是两份独立实现**：`generate.rs` 那个直接拼 `{machine}-{variant}`，`build.rs` 那个多做一次 `version_id.to_lowercase()`（`FASTV3.3` → `fastv3.3`）。两处未共用函数，漂移只是时间问题。

B 是最要命的一套：**机型定义文件里写的是 B，而消费端找的是 C。** `build.rs:206-215` 的注释已经点明后果——"名字对不上的后果不是报错，是消费端找不到"。

命名规律（代码里有解释，不是猜的）：
- `M` = mini（`presets/machines/A1_MINI.toml:6` 别名表含 `A1M`）
- `F` = 快拆改装件（`presets/machines/A1.toml:57` 版本名 `快拆版6月以前` ↔ `presetFile = 'A1F.toml'`）
- `_260628` = 2026-06-28 开源的那一版快拆件（`A1.toml:65-69`）

### 2.4 问题三：九份 TOML 两处并存，内容**逐字节完全相同**

九对 SHA-256 全部相等，字节数逐对相等，**连 `release_time` 都不差**（配方顶层 `preset_recipes.toml:22` 写死了时间戳，正是为了让"重新生成逐字节相同"成立）。

| 产物 | 基线 | `machine:variant` |
| --- | --- | --- |
| `A1-standard.toml` | `A1.toml` | A1 : standard |
| `A1-fast.toml` | `A1F.toml` | A1 : fast |
| `A1-fastv3.3.toml` | `A1F_260628.toml` | A1 : fastv3.3 |
| `A1_MINI-standard.toml` | `A1M.toml` | A1_MINI : standard |
| `A1_MINI-fast.toml` | `A1MF.toml` | A1_MINI : fast |
| `A1_MINI-fastv3.3.toml` | `A1MF_260628.toml` | A1_MINI : fastv3.3 |
| `P1S-lite.toml` | `P1.toml` | P1S : lite |
| `P2S-standard.toml` | `P2.toml` | P2S : standard |
| `X1C-lite.toml` | `X1.toml` | X1C : lite |

**两份并存不是冗余，是刻意的安全网。** `preset_recipes.toml:14-17` 写明：基线守的不是"数值对"，而是"没有未经审阅的变化"——配方里改错一个数，K-G7 不会红（产物与配方一致），只有基线 diff 和真机打印看得出来。

但要注意一条**会阻挡统一命名的断言**：

```rust
// crates/preset/src/generate.rs:402-417
assert_ne!(
    a.file_name(), b.file_name(),
    "这条判据的前提就是两边命名不同；名字一样了说明有人统一过命名，这个断言要重写"
);
```

写这条的人已经预告了今天这一步。统一命名的第一件事就是重写它。

### 2.5 问题四：配对靠头字段，属于弱关联

`pair_by_head()`（`generate.rs:172-208`）读每个文件头部 `# machine:` / `# variant:` 注释来配对，不认文件名。它能工作，但：

- 关联建立在**注释**上——注释被删、被改、被格式化工具动一下，配对就断，且报的是"它不像一份预设"这种指向受害者的错；
- 全仓只有 4 处调用，全在 `generate.rs` 内部，`src-tauri` 那边完全没用它——**工作台侧根本没有配对机制**；
- B 组九个名字被硬编码成常量数组**至少 4 处**（`crates/postprocess/tests/pipeline_wiping_source.rs:30-40`、`crates/preset/tests/build9.rs:35`、`crates/preset/tests/registry_branch_diff.rs:35`、`crates/preset/src/build.rs:1119`），改名要同步这些点；
- B 组目录路径被**手写重复 7 次**，未复用 `fixtures_dir()`（`tests/recipe.rs:22`、`ranges.rs:185,228`、`lineage.rs:17`、`write_roundtrip.rs:17,62,118,160`、`key.rs:11`）。

### 2.6 问题五：套餐域是悬空的

- 机型定义里有 `defaultBundle = 'A1_default'`（`presets/machines/A1.toml:5`）和每个版本的 `recommendedBundle`（`:51,59,67`）；
- **本仓没有任何文件定义这些 bundle。** `src-tauri/src/workbench/presets/mod.rs:155-157` 明确写着：`assets/` / `bundles/` 还没搬，`defaultBundle` / `presetFile` 因此是悬空引用，**这是刻意的**；
- `Bundle` struct 只用于解析**上游** `manifest.json`（`src-tauri/src/workbench/upstream/manifest.rs:120`）。

要把套餐域纳入管辖，就要给它一个①源定义文件——这是本轮要设计的新东西，不是搬迁。

### 2.7 问题六：资产域也没有真源

- 图片散在 `public/models/`、`public/printers/bambu/`，代码硬编码路径引用；
- 机型定义里的 `image = 'a1.webp'` / `icon = 'a1'`（`A1.toml:7-8`）是**裸文件名**，没有目录约定，也没有"这个文件存不存在"的校验；
- 唯一带真 sha256 的资产清单在**上游** `manifest.json`（72 条），只读。

### 2.8 另有两处零碎事实

- `presets/forbidden_zones/` 只有 P1S / P2S / X1C 三份，A1 / A1_MINI / A2L 没有；
- `src-tauri/src/workbench/app/build.rs:748` 引用 `../mkp-ssr/crates/preset/assets/presets` —— 指向一个本工作区**不存在**的兄弟仓库。

## 3. 文件职责表

六问：**是什么 / 谁创建 / 谁可改 / 依赖什么 / 何时生成 / 删除后怎么办**。

### 3.1 机型定义文件

| 问 | 答 |
| --- | --- |
| 是什么 | ① 源定义。一台机型的身份与物理事实：id、显示名、品牌、尺寸、校准坐标、涂胶区、运动范围、flags、版本列表 |
| 谁创建 | 人，经工作台「机型管理」 |
| 谁可改 | 工作台（保格式写回，现已用 `DocumentMut`）。构建器只读 |
| 依赖什么 | 品牌定义（`brand`）、禁区定义、资产定义（`image` / `icon`）、套餐定义（`defaultBundle`）、参数源（版本的 `presetFile`） |
| 何时生成 | 保存时立即写回 |
| 删除后 | **真相丢失**，不可恢复 |
| 现状位置 | `presets/machines/*.toml`（6 份） |

### 3.2 版本定义

| 问 | 答 |
| --- | --- |
| 是什么 | ① 源定义。一台机型下一个可选版本：id、显示名、tag、描述、指向哪份参数源、推荐哪个套餐 |
| 谁创建 | 人。**新增版本只创建定义，不要求参数文件已存在**——这条是你之前卡住的那一点 |
| 谁可改 | 工作台 |
| 依赖什么 | 所属机型；参数源（可后补）；套餐 |
| 何时生成 | 保存时 |
| 删除后 | 真相丢失。但要先检查：删掉后是否有参数源变成孤儿（已有 `wb_version_orphans`） |
| 现状位置 | 内嵌在机型文件的 `[[versions]]` 数组 |

**当前形态的问题**：`presetFile` 用的是 B 套命名，与消费端期望的 C 套不一致（§2.3）。

### 3.3 参数源（配方正文）

| 问 | 答 |
| --- | --- |
| 是什么 | ② 原始载荷。真正承载 `[toolhead]` / `[wiping]` 参数值与 G-code 片段的内容 |
| 谁创建 | 人。工作台支持「复制已有版本 → 改值 → 保存」 |
| 谁可改 | 工作台（参数台）。取值范围受参数注册表约束 |
| 依赖什么 | 参数注册表（合法键与区间）；机型（一台机型一份正文，不共享模板） |
| 何时生成 | 保存时写回配方真源 |
| 删除后 | **真相丢失** |
| 现状位置 | `crates/preset/assets/preset_recipes.toml`（607 行，集中式：`[[machines]]` 正文 + `机型:变体` 覆盖表） |

**这一类的组织形式就是 D-1 的争议点**，见 §5。

### 3.4 参数注册表

| 问 | 答 |
| --- | --- |
| 是什么 | ① 源定义。哪些参数存在、类型、区间、UI 控件、分组、机型级边界 |
| 谁创建 | 人（低频） |
| 谁可改 | 工作台（注册表编辑器，已有 `registry_edit.rs`） |
| 依赖什么 | 无（它是最底层的约定）。布局 schema 引用它 |
| 何时生成 | 保存时 |
| 删除后 | **真相丢失**，且所有校验失效 |
| 现状位置 | `presets/registry/param_registry.toml`（56 KB，唯一真源，被 `include_str!` 嵌入） |

### 3.5 资产（图片 / 图标 / 模型）

| 问 | 答 |
| --- | --- |
| 是什么 | ② 原始载荷 |
| 谁创建 | 人放入文件；工作台负责导入、预览、关联、改名、删除 |
| 谁可改 | 工作台（文件级操作）。构建器只读 |
| 依赖什么 | 无。反向被机型 / 版本 / 套餐引用 |
| 何时生成 | 导入时 |
| 删除后 | **真相丢失**，且所有引用它的地方变成悬空——必须有"谁在用它"的反查 |
| 现状位置 | `public/models/`、`public/printers/bambu/`（无索引、硬编码引用） |

**本轮要新增的是资产的①层**：一份资产定义，登记 id、类型、归属机型、相对路径。旧版每个资产一份 TOML（18 份）粒度太细，新版应当**一份集中的资产定义 + 目录约定**，而不是一文件一元数据。

| 问 | 答 |

### 3.7 入库产物（预设 TOML）

| 问 | 答 |
| --- | --- |
| 是什么 | ③ 构建产物。配方渲染成的最终预设文件 |
| 谁创建 | 构建器（`gen-presets --write` / 工作台 `wb_generate`） |
| 谁可改 | **只有构建器**。人不改 |
| 依赖什么 | 配方正文 + 机型 + 变体 |

### 3.8 对照基线

| 问 | 答 |
| --- | --- |
| 是什么 | ③' 判据资产。**不是**产物的副本，是"上次人工审阅通过的样子" |
| 谁创建 | 人显式同步（`--sync-baseline`），确认 diff 是自己要的之后 |
| 谁可改 | 只有显式同步动作 |
| 依赖什么 | 入库产物 |
| 何时生成 | 审阅后同步 |
| 删除后 | **不可自动恢复**——恢复等于无条件接受当前值，安全网就废了 |
| 现状位置 | `crates/postprocess/tests/fixtures/presets/*.toml`（9 份） |

| --- | --- |

### 3.10 manifest

## 4. 你怎么完成一项工作（产品骨架）

**这一节是本文档的主干。** 下面的文件结构都是为了支撑它。

### 4.1 四个阶段

工作台的产品骨架就是四个阶段，不是"三层文件"。**三层是后台的数据职责，不要求你理解三层文件。**

| 阶段 | 你在做什么 | 后台在动什么 | 现有实现 |
| --- | --- | --- | --- |
| **① 管理内容** | 增删改机型、版本、参数、图片、套餐 | 写①源定义 + ②原始载荷 | `wb_add_machine` / `wb_add_version` / `wb_set_version_field` / `wb_apply_draft` |
| **② 检查内容** | 看一份问题清单，不自己翻文件夹 | 读①②，跑引用 / 参数 / 唯一性 / 孤儿四类检查 | `wb_preflight`（待扩展） |
| **③ 生成内容** | 看生成了哪些、哪些还不能生成、生成前后差异 | 产出③构建产物 | `wb_generate`（原子整批）、`wb_preview_toml`、`wb_diff_draft` |
| **④ 发布内容** | 确认后一键交付 | 筛选 → 写④交付 + manifest | `wb_publish`（待补目录 JSON 与筛选） |

阶段之间是**闸门**，不是建议：检查不过不生成，生成不过不发布。

### 4.2 页面 ↔ 后台数据的映射

你在界面上看到的是业务对象，不是文件。

| 工作台页面 | 后台管理的内容 | 你需要知道文件在哪吗 |
| --- | --- | --- |
| 机型与版本 | 机型定义 + 版本定义（①） | **不需要** |
| 参数编辑器 | 配方正文（②），受参数注册表约束 | **不需要** |
| 资产库 | 图片 / 图标 / 模型（②）+ 资产定义（①） | **不需要** |
| 套餐管理 | 套餐定义（①） | **不需要** |
| 检查与生成 | 构建产物（③）+ 对照基线（③'） | 只需看得见 diff |
| 发布中心 | 交付文件（④）+ manifest | 只需看得见清单 |

页面数量与数据层数**没有对应关系**。资产库可以是一套库 + 在机型页用模态框选图；版本管理可以在机型详情页内完成。

### 4.3 端到端用例：新增一个 A1 快拆版本

这是你之前反复卡住的那件事。逐步写清楚每一步动了什么。

| 1 | 进入 A1 的版本管理 | 读机型定义 | — |

## 5. D-1（待你决定）：机型定义与配方正文的边界

**你选了 C：摆代价，不拍板。** 以下是两个方案的对比，读完请告诉我选哪个。

### 方案甲：保持两个域分开（现状）

```text
presets/machines/A1.toml                      ← 机型是什么（身份、尺寸、版本列表）
crates/preset/assets/preset_recipes.toml      ← 参数正文（6 台机型集中一个文件）
```

| 维度 | 评价 |
| --- | --- |
| 文件组织 | 机型 6 份 + 配方 1 份 = 7 个文件。配方文件 607 行，加机型会线性增长 |
| SSOT 边界 | **清楚**：机型事实归机型文件，参数值归配方。目前无重叠字段 |
| 工作台操作 | 「改机型尺寸」只动 1 个文件；「改参数」只动 1 个文件。但**「新增一台机型」要动两处**，两处都成功才算完成——需要跨文件事务 |
| 校验与构建复杂度 | 低。`gen-presets` 只读配方，跟机型文件解耦，现有判据全部适用 |
| 迁移成本 | **零**。这是现状 |
| 风险 | 配方文件会长成又一个巨型文件（现在 607 行 / 6 机型，20 台机型时约 2000 行）。它内部以 `[[machines]]` 分段，不是无结构，但 diff review 变难 |

### 方案乙：按机型合并成一机一目录

```text
presets/machines/A1/
├── machine.toml      ← 身份、尺寸、版本列表
├── recipe.toml       ← 这台机型的参数正文 + 变体覆盖
└── zones.toml        ← 禁区（当前只有 3 台有）
```

| 维度 | 评价 |
| --- | --- |
| 文件组织 | 6 目录 × 2~3 文件 = 13~18 文件。单文件都短，增机型是加目录不是改巨型文件 |
| SSOT 边界 | 同样清楚，且**物理邻近**——"这台机的一切都在这个目录"。反过来说，"所有机型的参数"不再有一个统一入口 |
| 工作台操作 | 「新增机型」= 建一个目录，一次事务。「复制机型」= 复制目录，语义直观。**这是对你日常操作最友好的一点** |
| 校验与构建复杂度 | 中。`gen-presets` 要从"读一个文件"改成"遍历目录、合并配方"。`recipe_path()`（`generate.rs:42-44`）与 `include_str!`（路径必须字面量）都要改——`include_str!` 那处最麻烦，一机一目录时无法再写一个字面量路径，可能要改成 build script 生成或运行时读盘 |
| 迁移成本 | **中高**。要拆 607 行配方、改 `recipe_path` / `Recipe` 解析 / `include_str!` 策略，并同步 `crates/preset/tests/recipe.rs` 等判据 |
| 风险 | 拆分过程中可能改变渲染结果的字节。防线是现有 K-G0' 基线——拆完九份产物必须逐字节不变，这是硬验收条件 |

### 5.1 方案甲必须补的跨文件事务设计

上一版只写了"需要跨文件事务"就收笔了，这是个缺口。**如果选方案甲，这套机制要一并定下来，不能留到实现时才发现。**

出问题的动作有三个：新增机型、删除机型、复制机型。每个都要同时改机型文件与配方文件。

**设计：工作台层的两阶段写。**

1. **算**：在内存里把两处改动都算完（新机型文件的完整内容 + 配方文件的完整内容）。任一处算不出来就整体放弃，磁盘不动。
2. **写**：两处都走 `atomic_write`（临时文件 → rename）。
3. **失败点**：第一处 rename 成功、第二处失败——这是唯一会留下半成品的窗口。

**第 3 点的处理方式（两个选项，选一个）：**

| 方案 | 做法 | 代价 |
| --- | --- | --- |
| **补偿回滚** | 写前把两个文件的原内容存进 `.snapshots/`；第二处失败就用快照把第一处写回去 | 回滚本身也可能失败，需要"回滚失败"的兜底提示 |
| **可检测的不一致 + 修复入口** | 不回滚。校验层能识别"机型存在但配方缺它"和反过来，并给一键补齐 | 会短暂留下不一致状态，但状态是**可见且可修的**，没有隐藏的半成品 |

**我倾向第二个。** 理由：`.snapshots/` 目录已经在 `WORKBENCH_DIRS` 里（`paths.rs:36`），但回滚路径本身是一条很少走到、因此很少被测到的代码；而"校验能看见不一致"这条能力**本来就要做**（§11 的引用完整性检查），成本是零额外。把不一致变成一条 error 而不是一个隐藏状态，更符合本文档"错误要可据以行动"的原则。

**方案乙不需要这套机制**——一机一目录时，新增机型是建一个目录，删除是删一个目录，本身就是单一事务。这是方案乙的一项实质优势，上一版的对比表没算进去。

## 6. D-2（方向已定）：统一新系统的版本身份与文件命名规则

**问题：** 旧系统存在多套预设命名（§2.3 的 A / B / C），机型定义、构建产物与消费端的查找规则并不一致。`build.rs:206-215` 已记录这种不一致可能导致消费端找不到文件。

**但本节不是"修复旧命名"。** 消费端也在重新设计范围内，所以 A / B / C 中**没有任何一套自动成为新标准**。

### 6.1 决策方向

1. 新系统**不继承**旧系统的多套命名规则。
2. 工作台、构建器、消费端、发布器**统一使用同一套身份与命名规范**。
3. 旧版命名**仅作迁移输入**，不作为新系统的长期兼容约束。
4. 统一规则必须覆盖五处：版本定义、参数源关联、构建产物、消费端查找、发布文件名。
5. 旧数据迁移时**明确旧名 → 新身份的映射**；不能只靠重命名文件完成迁移。

### 6.2 两件事必须分开

| 概念 | 是什么 | 谁拥有 | 能不能变 |
| --- | --- | --- | --- |
| **内部身份** | 机型 ID + 版本 ID（如 `A1` + `FASTV3.3`） | 源定义 | 稳定，改它等于换一个业务对象 |
| **外部文件名** | 构建产物与交付文件叫什么 | **唯一的命名函数** | 可以调整，因为它是算出来的 |

**不要让文件名同时承担业务身份、版本关系和消费端寻址三种职责。**
`A1 + fastv3.3` 是身份；最终文件叫什么由唯一规则生成，不是机型定义、构建器、发布器各拼一遍。

现状违反了这一条：`generate.rs:55-57` 与 `build.rs:219-221` 是两份独立实现（后者多做一次 `to_lowercase()`），而机型定义的 `presetFile` 又硬写了第三套字面量。**新系统只允许一处实现。**

### 6.3 待你确认的具体内容

| 项 | 待定 | 我的建议 |
| --- | --- | --- |
| 字段组成 | `{机型id}-{版本id}` 还是加上更多分量 | 只用这两个分量。多余分量会把关系塞进文件名 |
| 大小写 | 版本 id 现在是 `FASTV3.3`（大写），文件名现在是 `fastv3.3`（小写） | 身份保持大写，文件名统一小写，转换只在命名函数里发生一次 |
| 分隔符 | `-` 还是 `_` | `-`。机型 id 本身含 `_`（`A1_MINI`），换成 `_` 会歧义 |
| 扩展名 | `.toml` | 不变 |
| 映射关系 | 内部 ID ↔ 文件名是否需要可逆 | 需要单向可算即可（ID → 文件名）。反向查找走目录 JSON，不靠文件名解析 |

### 6.4 `presetFile` 字段的去留（仍需你定，闸 G-2）

命名规则统一后，`presetFile` 变成**可从身份推导**的冗余字段。

- **保留**：留一个"指向非常规文件名"的余地；
- **删除**：消除一处会与真相不一致的写值（现在它就不一致）。

我倾向**删除**。影响面：`presets/catalog.rs` 的 `VersionField` 枚举、前端 `src/workbench/api.ts` 的类型、机型文件的字段集合。

### 6.5 执行顺序与硬防线

**顺序**：D-2 与生产流程设计**并行确认**，在新系统的数据契约与消费端契约**冻结前**完成。
**不要求**先修补旧消费端，**不要求**先批量重命名旧文件。

**硬防线**：无论命名怎么定，九份产物的**内容**必须逐字节不变（sha256 与 §2.4 表一致）。改名只改名字，参数值一个都不许动。

| 场景 | 期望行为 |
| --- | --- |
| 新增版本时参数源还不存在 | **允许**。版本定义可以先存在，参数源后补。校验时报 warning 而非 error，构建时才报 error |
| `image` / `icon` 指向不存在的文件 | 校验报 error，指出机型 id + 字段名 + 找过的路径 |
| `defaultBundle` 指向不存在的套餐 | 当前是刻意的悬空引用（§2.6）。套餐定义落地后转为 error |
| **同机型下出现仅大小写不同的版本 id**（如 `Fast` 与 `FAST`） | **error**。文件名统一小写后两者会冲突成同一个文件。唯一性检查必须是**大小写不敏感**的，不能只比字面量 |
| **机型 id / 资产 id / 套餐 id 仅大小写不同** | 同上，一律 error。理由同上：它们都会参与路径构造 |
| 删除一个被引用的资产 | 阻止，并列出引用它的机型 / 版本 / 套餐 |
| 删除一个版本 | 允许，但提示由此产生的孤儿参数源（已有 `wb_version_orphans`） |
| 构建时某一份渲染失败 | **整批不落盘**（现有 `wb_generate` 已是原子整批语义） |
| 产物与基线出现 diff | 不自动同步。展示 diff，等人确认后才 `--sync-baseline`。**基线更新不是生成或发布的自动步骤，也不是每次发布的必经步骤** |
| **交付目录里有上次发布的残留文件** | **blocker，阻止发布**，直到清理或确认。理由见下 |
| 找不到上游参考仓 | 返回 `None` 是有意义的状态，显示"试过哪几个位置"，不用空数据装成能跑（`paths.rs:85-90`） |
| 所有写盘 | 一律走 `fsx::atomic::atomic_write`，由 `clippy.toml` 的 `disallowed-methods` 强制 |

### 9.1 为什么残留文件是 blocker 而不是 warning

`strays`（`generate.rs:79-90`）现在的语义是"点名但不删除"，那是对**入库产物**目录的正确处理——那是开发者自己看的目录。

但**交付目录不一样**：残留文件会被消费端真的下载到。而且它不是人手改的，是构建器自己留下的历史产物——所以"人手改了下次发布会被覆盖"这条说法覆盖不到它。

规则定为：

- 发布前扫描交付目录，任何**不在本次可达集合内**的文件都列出来；
- 有残留就**中止发布**，不写 manifest；
- 提供一个显式的「清理残留」动作（走回收而不是直接删，进 `.trash/`）；
- 清理后重新发布。

这样 manifest 永远只描述一批自洽的交付，不会出现"清单里没有但目录里有"的文件。

### 12.4 BBS 盘点结论（G-3 的决策依据）

**体量**：`presets/bbs/Process/` 下 9 个 JSON，`0.2mm/` 4 份 + `0.4mm/` 5 份，单份 1.2–1.9 KB，总计约 14 KB。只有 `Process/` 一层，没有 `Filament/` / `Machine/`。

**结构**：扁平的一层 key-value，值全是字符串或字符串数组（连数字也是 `"0.6"`）。带 Bambu / Orca 原生身份字段：

```json
{
    "from": "User",
    "inherits": "0.20mm Strength @BBL A1",
    "name": "MKPProcess A1",
    "print_settings_id": "MKPProcess A1",
    "version": "2.0.0.83",
    "enable_support_ironing": "1",
    "support_ironing_spacing": "0.3",
    "support_interface_top_layers": "1",
    "support_top_z_distance": "0"
}
```
（节选自 `presets/bbs/Process/0.4mm/MKPProcess A1 0.4 0.20.json`）

**与配方域的耦合程度**：

- **键名零重叠。** 逐键对比过：BBS 侧是切片机官方 snake_case（`enable_support_*` / `support_interface_*` / `tree_support_*`），MKP 侧是 `glue_*` / `tower_*` / `prime_*` / `wiper_*`。**没有任何一个键同时出现在两边** —— 不存在"两处写值"的 SSOT 冲突。
- **但存在语义耦合，必须成套配发。** MKP 的 `use_ironing_path = true`（用熨烫路径当涂胶路径）只有在 BBS 侧 `enable_support_ironing = "1"` + 那一组 `support_ironing_*` 值成立时才有意义；`min_support_interface_enabled` 对应 BBS 的 `support_interface_top_layers = "1"` / `support_interface_spacing = "0"`。**发了 MKP 预设不发配套 BBS 预设，用户打出来的结果是错的。**

**决定性事实：套餐的内容就是 BBS 引用。** `source/bundles/A1_default.toml` 全文：

```toml
id = 'A1_default'
display = '官方推荐'
machineId = 'A1'
assetRefs = ['a1_bbs_mkpprocess_a1_04_020']
updatedAt = '2026-07-12'
```

`assetRefs` 指向一条 `resourceType = 'bbs_profile'` 的资产。**所以 G-3 不是独立决策：不纳入 BBS，套餐就成了空壳，套餐域没有内容可管。**

**我的建议：纳入 BBS，舍弃 Orca。**

- 纳入 BBS 的理由：体量小（14 KB / 9 份）、键名不与配方域冲突、且它是套餐域唯一的实质内容。
- 舍弃 Orca 的理由（两条硬事实）：
  1. **它是孤儿**。`source/assets/` 里**没有任何条目**引用 `presets/orca/` 下的文件——旧版 Builder 也没管过它们；
  2. **目录与内容错位**。`presets/orca/Support/0.4mm/MKPSupport S1C.json` 放在 `Support/` 目录里，内容却是 process 预设（`print_settings_id: "MKPProcess S1C"`），且 `post_process` 文案是 `"请粘贴预设"`，与 BBS 侧的 `"请将MKP命令粘贴到这里"` 不一致。这是一份未完成的实验产物。

若将来要支持 Orca，按新系统的资产定义重新登记，不搬这两份。

### 12.5 资产元数据：旧结构与新结构的差异

旧版每份资产一个 TOML，6 个字段。`source/assets/a1_mkp_standard.toml` 全文：

```toml
id = 'a1_mkp_standard'
resourceType = 'mkp_preset'
category = ''
machineId = 'A1'
fileName = 'A1.toml'
relativePath = 'presets/mkp/A1.toml'
```

18 份里 **9 份是 `bbs_profile`，9 份是 `mkp_preset`**。

**新版要砍掉 `mkp_preset` 那 9 份。** 理由：它们做的事是"给 9 份 MKP 预设登记路径"，而新系统的命名规则（§6）已经能从 `机型id + 版本id` 算出路径——留着它就是又一处会与真相不一致的写值。`category = ''` 这种空字符串字段也说明这张表是为 BBS 设计的，MKP 预设是硬塞进来的。

### 12.6 切片器是一个开放维度，不是写死的类型（G-3 定稿）

旧仓把切片器名字**焊进了类型里**：`resourceType = 'bbs_profile'`。这是将来最容易出事的一处——
加 Orca、加快造科技 U1 时要改枚举、改所有 match 分支、改前端类型。

**新版拆成两个字段：**

```toml
type   = 'slicer_profile'   # 闭集：slicer_profile | image | icon | model
slicer = 'bbs'              # 开放取值：bbs | orca | kz_u1 | …
```

| 字段 | 性质 | 加一个新切片器要改吗 |
| --- | --- | --- |
| `type` | **闭集**，四个值 | **不用改** |
| `slicer` | **开放**，字符串 | **不用改代码**，加一条数据即可 |

目录同构：`presets/slicers/<slicer>/<category>/…`，`bbs` 是其中一个子目录而不是特例。

**Orca 现在删，但形状预留。** 舍弃那两份文件（§12.4 的两条理由：无元数据引用 + 目录与内容错位），
**不删这个维度**——将来要支持 Orca 或 U1 时，是往 `slicer` 加一个取值、往目录加一层，
不是回来改类型枚举。

这条把品牌绑定从**代码**移到了**数据**。代价只有一点：`type` 与 `slicer` 的组合要靠校验兜
（`image` 不该带 `slicer`），这条进 Task 11。
