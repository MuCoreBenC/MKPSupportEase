# `render()` 机型来源变更 —— 独立审查（b05 Task 3.3 附项）

> **审查对象**：`afa7bf6` 里的一处**生产**代码改动 —— `render()` 的机型查询从
> `book.up.catalog.machine()` 换成 `book.machines()`（`presets/machines/*.toml`）。
>
> **审查纪律**：M0 判据绿**不能**用来验收这处改动 —— 它只说明比对成立，
> 不说明机型来源变更是对的；两件事分开汇报（见聊天里的结论）。
>
> 审查问题（提出者）：① `book.machines()` 是不是当前正式机型来源；
> ② 上游机型目录退出后生产是否也该走这条路径；③ 是否需要独立判据。

---

## 1. 问①：`book.machines()` 是不是当前正式机型来源

**是。** 三条证据：

1. `Book.catalog` 的**定义处**就写着：`**清单**：有哪些机型、每台有哪些版本。来源是
   presets/machines/*.toml`，并记了改为上游的反面理由 —— 「b04 Task 8 之前这里读的是
   `up.catalog`……那是上游的构建产物，只读，于是『加一个版本』保存之后它在树上看不见」
   （`src-tauri/src/workbench/domain/derive.rs:93-98`）。
2. `Book::new` 里**版本清单、机型层取值、版本层取值**全部从 `committed.catalog`
   与 `presets.registry` 长出来（`derive.rs:124-160`）：可写的真源早就在我们这边。
3. 章节定位：b05 doc §3.1 / §3.2 把机型定义与版本定义的「现状位置」记成
   `presets/machines/*.toml`；上游那层自称**"还没搬过来的那几份数据"**、**"只读，而且正在缩小"**
   （`src-tauri/src/workbench/upstream/mod.rs:1-5`）。

## 2. 问②：上游机型目录退出后，生产是不是也该走这条路径

**是，而且渲染链里只剩这一处没走** —— 就是这次改的那一行。改之前，上游 catalog
在渲染链里的唯一用处是"按机型 id 查它在不在"，查出来只用了 `machine.id`。

真正在**读上游内容**的地方是**产物视图**（`VersionIdentity.mkp_preset`，
`derive.rs:149-153`）：它回答的是"上游有没有为这一版生成过产物"，
与"这台机型是谁"是两件事。其余仍在读上游的地方都不是机型身份：

| 位置 | 读什么 | 归谁 |
| --- | --- | --- |
| `domain/issues.rs:176` | 客户端最低版本要求 | b04 Task 12 收尾 |
| `app/mod.rs:345-352` | 发布页：channel / 版本 / 交付物计数 / 应急规则数 | b04 Task 12 收尾 |
| `app/build.rs:640-649` | 发布 manifest：channel / version / bundles | b04 Task 12 收尾 |
| `domain/derive.rs:251-266` | 套餐里的 BBS 列表 | 与 G-3 / Task 9 一起 |

这四项**不在本轮范围内**，本审查也不替它们背书。

## 3. 问③：这次行为变化要不要独立判据

**要。** 已补 `render_takes_the_machine_from_our_own_catalog`（`app/build.rs` 测试模块）：

- 反空转①：断言夹具上游**确实不认** `A1_MINI`（`testkit::FIXTURE_MACHINES` 只有
  A1 / A2L / P1S）—— 前提没了就红，不空转；
- 反空转②：断言真 `presets/` **有** `A1_MINI`；
- 主判据：这台机型渲染得出来、`# machine:` 用的是我们清单里的 id、产物名跟着它走。

**判据的判据（本次实测）**：把 `render()` 临时改回 `book.up.catalog.machine()` →
新判据与 M0 **同时红**（`机型 A1_MINI 不存在`）；改回来 266/266 全绿。
也就是说这条判据不是"跟着生产代码写的注释"，它真的锁住了那一行。

## 4. 变更的真实边界

| | 改前 | 改后 |
| --- | --- | --- |
| "机型在不在"的判据 | 上游那份 catalog | 我们自己那份清单 |
| 上游不认识的机型 | 渲染失败（`机型 X 不存在`） | 渲染成功 |
| 产物正文 | 只用到 `machine.id` | 同（值不变：id ↔ 同名的 id） |
| 版本清单 / 取值层 | 我们自己的数据 | 同（未动） |

**那条失去的信号搬到哪了**：发布路径仍然逐版本看上游产物视图
（`app/build.rs:614-625`）—— `mkp_preset == None` 记「暂无资源」，产物文件不在就报
「还没生成，先在生成视角里生成，再发布」。所以"上游还没认可这一版"这件事在**发布**时说，
而且说得更准：它说的是"这一版没有产物"，而不是"这台机型不存在"。

## 5. 残余风险（照实记，未解决）

1. **「机型在我们清单里、上游不认」现在没有人在拦。**
   上游那层的断言（`catalog.rs` 的 `check_consistency` 一族）只保证上游**自己两份文件**
   之间自洽；`testkit::check_same_catalog` 只对**夹具**生效；真上游与真 `presets/` 之间
   **没有任何判据**在比机型集合。改动前，那种不一致至少会在渲染时以"机型不存在"暴露一次，
   现在不会了。
   → 建议并入 **Task 11（校验层）**：把它做成一条可见的 warning（上游存在时才有意义），
   而不是靠渲染失败来暴露。
2. **`Book` 仍持有 `up`**：本判据为构造 `Book` 还得造一份夹具上游。
   b04 Task 12 收尾后这个字段会消失，那时连夹具都不用造。
3. **本审查只回答了那三个问题**：没有顺带验收 §2 表里那四项上游读取，
   也没有替上游层的整体退役下结论。
