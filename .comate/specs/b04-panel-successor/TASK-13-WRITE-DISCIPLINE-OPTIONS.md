# 写盘纪律：三种方案的实际约束、漏检与验证

**状态：已定案（2026-09-23，见 §4）。** 原为 `TASK-13-MIGRATION-INVENTORY.md` §2.5 ① /
§6 第 4 条那条待决策项。取证基线：`MKPSupportEase @ eb283b2`、
`mkp-ssr @ a2a47ca`（`crates/core` 只读）。

**结论一句话**：主约束用**源码扫描断言**（C），辅助用 **workspace 根唯一一份 `clippy.toml`**（A1），
「接进 `fsx::atomic`」（B）**推迟**为独立架构任务。
定案前取证出的两处既有缺口（CI 不覆盖工作台、clippy 禁列不全）见 §5，各自独立一笔修。

判据（你给的，不是我拟的）：

1. 能不能守住**长期**约束「所有写盘只经一处」；
2. 不把**迁移验证**与**行为改动**混在一起；
3. 不接受把"管不到它"当默认结论 —— 那等于永久漏检口。

---

## 0. 先说一个改变结论的发现：现在的守卫比看上去弱

这条纪律今天靠两个机制，而**两个都有覆盖缺口**。取证如下。

### 0.1 `clippy.toml` 只禁了 3 个方法，且唯一 allow 洞只有一个

`src-tauri/clippy.toml:8-12` 禁 `std::fs::write`、`std::fs::File::create`、
`tokio::fs::write`；全仓 `#[allow(clippy::disallowed_methods)]` 只有一处
（`src-tauri/src/fsx/atomic.rs:23`）。这两点是好消息。

但禁列**不含** `std::fs::OpenOptions`（`create(true).write(true)` 那条路）、
也不含 `std::fs::File::options()`（1.58 起的等价物）、`create_dir_all`、`remove_file`。
也就是说**绕过这条纪律的第二条写法一直存在**，只是没人踩。

### 0.2 更要紧的：CI 里的 clippy **不覆盖工作台**

- `lib.rs:24-25` 是 `#[cfg(feature = "workbench")] pub mod workbench;`，
  旁边的注释自己写着「默认构建里下面这一行不成立，所以 `src/workbench/` 整个子树连编译都不会被碰」
- `.github/workflows/ci.yml:84-85` 是 `cargo clippy --all-targets -- -D warnings`，
  **没有任何 `--features`**（全文件 grep `workbench` 零命中），`:87-88` 的 `cargo test` 同样
- 工作台里的写盘相关调用点共 **44 处**

所以今天这条纪律在 CI 里的实际覆盖面是：**编译得到的那些代码**，
而唯一会写 `presets/`（用户数据）的那棵子树一次都没被它检过。
本地跑 `cargo clippy --features workbench` 才覆盖 —— Task 13.5 的验收正是这么写的，
但那不等于 CI 会守住。

### 0.3 `clippy.toml` 的官方定位是「不稳定」

Clippy 官方文档在该配置页顶部明写：**`clippy.toml` 是不稳定的（unstable），未来可能被弃用**。
把"长期约束"完全押在它上面，有一个官方已经声明过的到期风险。
（另外查找规则：起始目录是 `CLIPPY_CONF_DIR` > `CARGO_MANIFEST_DIR` > 当前目录，
**找不到就逐级向上遍历父目录**，就近优先 —— 这一条对方案 A 的取舍是决定性的。）

### 0.4 与之对照：本仓库已有的**源码扫描断言**更强，而且是被验证过会响的

`workbench/upstream/mod.rs:107` 的 `upstream_layer_has_no_write_path`：

| 它做的事 | 证据 |
|---|---|
| 扫目录、只取非测试代码（`production_part()` 切掉 `#[cfg(test)]` 之后那一段，并滤掉注释行） | `:111-134` |
| 禁 **6 个**符号：`atomic_write` / `fs::write` / `fs::remove` / `create_dir_all` / `File::create` / `OpenOptions` —— 比 clippy 的禁列**多三个** | `:117-123` |
| 反空转哨兵：扫到的文件数 < 3 就报「判据在空转」 | `:133` |
| **自检**：`the_zero_write_judge_would_catch_a_write` 喂一份假源码，断言这条判据真的会命中；还验了"注释里的同名符号不算" | 紧随其后那条 |

`upstream/mod.rs:37-39` 的模块文档自己说明了两个机制的分工：
「`clippy.toml` 只拦 `std::fs::write`，**拦不住走仓库那个合法出口写到上游路径去**」。

**结论**：本仓库里"真的守住"的那一条是扫描断言，clippy 是廉价的外围网。
所以新 crate 的长期守卫应当以扫描断言为主 —— 这决定了下面的方案取舍。

## 1. 待管制的两处，真实语义是什么

| | `pipeline/mod.rs:589` `write_atomic` | `main.rs:248` |
|---|---|---|
| 干什么 | 处理后的 G-code 落到调用方给的路径 | CLI 把结果写到用户给的路径 |
| 写法 | `<out>.part` → `std::fs::rename`；rename 失败则 `std::fs::copy` + 删 `.part` | `std::fs::write`，**先 `path.exists()` 拒绝覆盖** |
| 崩溃语义 | 目标文件不会被截断（比裸 write 好）；但 `.part` 名是**确定的**，两个并发进程会撞 | 新文件、非覆盖场景下风险小；`exists()` 与 `write` 之间有 TOCTOU |
| 持久性 | **无 `sync_all` / 无父目录 fsync** | 同左 |
| 与 `fsx::atomic` 的差 | 少一次 fsync、临时名不随机、多一条**非原子的 copy 回退** | 同左，且它写的是"用户指定的任意路径" |

顺带说清：`fsx::atomic::atomic_write` 用的是 `tempfile::NamedTempFile::new_in(parent)`
+ `write_all` + `sync_all` + `persist` + 父目录 fsync（`src-tauri/src/fsx/atomic.rs:24-52`）。
两者目标一致，细节不同 —— **换过去是行为改动，不是搬家**。

## 2. 三个方案

### 方案 A：`clippy.toml` 层面收口

两种落地形态，**不能混着理解**：

- **A1 统一到 workspace 根**：把 `src-tauri/clippy.toml` 挪成根上唯一一份。
  依据是 §0.3 那条查找规则（向上遍历 ⇒ 所有成员都能找到）。**但必须删掉
  `src-tauri/clippy.toml`** —— 就近优先，留着它 src-tauri 就还是只吃它自己那份，
  而根上那份对新 crate 生效、对 src-tauri 不生效，两份还会各自漂移。
- **A2 每个 crate 各一份相同内容**：需要额外一条判据盯"两份逐字节相同"，否则漂移是静默的。

| | |
|---|---|
| 约束力 | 只约束**方法名**，不约束"写到哪个路径"。挡不住"走合法出口写到不该写的根"—— 这正是 `upstream` 那条扫描断言存在的理由 |
| 漏检 | ① 禁列只有 3 个方法（§0.1）；② 官方标注不稳定（§0.3）；③ **CI 不覆盖工作台**（§0.2）⇒ 在新 crate 上它能生效（新 crate 不带 feature 门），但同一个仓库里最该管的那棵树仍然没人管；④ 文档未展开"别名 / 函数指针 / 宏生成的调用"是否失效，属**待实测**，不当结论用 |
| 验证方式 | 往新 crate 里塞一行 `std::fs::write`，`cargo clippy -- -D warnings` 必须红；这条能自证（负向测试） |
| 代价 | 小。但 A1 会顺带改动 `src-tauri` 的配置位置，属于"纪律配置"改动，不该塞进迁移批次 |
| 与判据 2 的关系 | 不混行为改动 ✅ |

### 方案 B：把那两处接进 `fsx::atomic`

**它的真实前置比看上去大得多。** `fsx` 不是独立 crate，它是 `mkp-support-ease`
这个 Tauri 应用 lib 里的一个模块（`src-tauri/src/fsx/`），并且 `atomic_write` 返回
`crate::error::AppError`。所以 `crates/postprocess` 要用它，必须先把
**`fsx` 与 `error` 抽成独立 crate**（否则就是子 crate 反向依赖应用 crate，因果倒置）。

| | |
|---|---|
| 约束力 | 最强：不只管 API，还管"怎么落盘"（fsync、随机临时名、无 copy 回退） |
| 漏检 | 抽出去之后 `fsx` 就成了**多个使用者共用**的出口，"唯一写盘出口"的守卫面反而要重画 |
| 验证方式 | 要判"换成 fsx 之后字节不变、且崩溃语义变强"—— 后者在测试里很难真验（要断电），只能靠代码审查 + 强制的实现细节断言 |
| 代价 | 大：抽 2 个模块 + 改 `src-tauri` 的引用路径 + postprocess 新增 2 个本地依赖（会推翻迁移盘点里"只依赖 9 个第三方"那条干净边界）+ **改的是一条真机验证过的写盘路径** |
| 与判据 2 的关系 | **直接冲突**：这是行为改动，混进 M2 之后"零 diff 搬运"这条证据就没了 |

### 方案 C：源码扫描断言 + **钉死豁免清单** + 自检

照 `upstream_layer_has_no_write_path` 的成熟写法，给 `crates/postprocess` 加一条：

- 扫 `crates/postprocess/src`，切掉注释与 `#[cfg(test)]` 之后那一段
- 禁列比 clippy 宽：`fs::write` / `File::create` / `File::options` / `OpenOptions` /
  `create_dir_all` / `fs::remove` / `fs::copy` / `fs::rename`
- **豁免不是"放行这两处"，而是"钉死这两处"**：把命中结果收集成 `(文件, 符号)` 集合，
  断言**等于**允许清单（不是 `⊆`），清单每项带**理由 + 退役条件**：

  ```
  ("pipeline/mod.rs", "fs::write",  "同目录 .part + rename；退役条件：M3 或写盘批次并入 fsx::atomic")
  ("main.rs",         "fs::write",  "CLI 输出到用户给定路径，且已拒绝覆盖；退役条件：M3 一并评估")
  ```

  这样**新增第三处会立刻红**，而豁免项自己也在册 —— 漏检口是"有名有姓、有退役条件"的，
  不是"管不到所以不管"
- 反空转哨兵（扫描面文件数下限）+ **自检**（喂假源码断言判据会响）—— 两条都照抄现成写法

| | |
|---|---|
| 约束力 | 只约束这**一个 crate** 的写盘面，不解决"整个仓库多个出口"的问题（那是 Task 19.1 的事，这条判据到时候是它的输入） |
| 漏检 | 文本匹配天然弱于类型（`use std::fs as f; f::write(..)` 这类改写能绕过 —— 但 `upstream` 那条也存在同样的洞，且它禁的 6 个符号里已经覆盖了常见别名写法的收口点） |
| 验证方式 | 三条自证：① 新增一处写盘 → 红；② 删掉豁免项 → 红；③ 自检那条证明判据本身会响 |
| 代价 | 小。**且可以放进 M2/B3 之后的独立一笔**，不碰被迁移的代码 |
| 与判据 2 的关系 | 不混行为改动 ✅ |

## 3. 三者对照

| | A（clippy） | B（接 fsx） | C（扫描断言） |
|---|---|---|---|
| 管的是 | 方法名 | 落盘实现 | 这个 crate 的写盘面 |
| 能否长期守住 | ⚠️ 官方标注不稳定；CI 覆盖面另有缺口（§0.2） | ✅ 最强 | ✅ 与现有机制同族、已证明会响 |
| 新增第三处会红吗 | 会（仅限禁列内的方法） | 不适用 | **会（集合相等，不是包含）** |
| 漏检口是否在册 | 否（躲开禁列即可） | — | **是（带理由与退役条件）** |
| 是否混行为改动 | 否 | **是** | 否 |
| 代价 | 小 | 大（要抽 2 个 crate） | 小 |

## 4. 定案（2026-09-23）

| | 方案 | 状态 | 定案 |
|---|---|---|---|
| **C** | 源码扫描断言：命中集合与允许清单**完全相等**，每项带理由 + 退役条件 | **已定：主约束** | 迁入后为 `crates/postprocess` 加这一条。写法照 `upstream_layer_has_no_write_path`（切注释与 `#[cfg(test)]`、反空转哨兵、自检） |
| **A1** | workspace 根唯一一份 `clippy.toml` | **已定：辅助约束** | 把 `src-tauri/clippy.toml` 挪到 workspace 根做唯一一份，**必须删掉 `src-tauri/` 那份** —— 就近优先，留着它根上那份就管不到 `src-tauri`，两份还会各自漂移 |
| **B** | 把那两处接进 `fsx::atomic` | **推迟** | 不抽 crate、不改那条真机验证过的写盘路径。以后作为**独立架构任务**评估，不挂在迁移上 |

三条理由对着判据逐条写下来：

- **守长期**：C 是唯一能表达「豁免有名有姓、新增即红」的机制，且与仓库里已经跑了、
  带自检的那条同族。A1 保留作廉价外围网 —— 它覆盖不到「写到哪个路径」，
  但能挡住顺手写 `std::fs::write` 的手滑。
- **不混行为改动**：B 的前置是抽 `fsx` + `error` 成 crate，并改一条真机验证过的写盘路径。
  那是独立一段，不该在 M2 里做。
- **不留永久漏检口**：C 的允许清单强制带**退役条件**，Task 19.1 的全局扫描直接引用这份清单。
  B 没有被否决 —— 它以"退役条件"的形式挂在 C 的清单上，等写盘批次单独做。

**明确不采用的做法**：只做 A 就算完。它本身没问题，但它今天在 CI 里**连工作台都没覆盖到**
（§0.2），却容易被当成"已经有人管了"。

## 5. 两处既有缺口：已定，各自独立一笔

这两条是**既有缺口**，不修的话 C 与 A1 的效力都会被削。**都已定，分别做、分别验、分别提交**，
不混进 Task 13 迁移批次，也不把两项合成一笔：

| # | 独立任务 | 范围 | 验收重点 |
|---|---|---|---|
| 1 | **CI feature 覆盖** | `clippy` 与 `test` 启用 `workbench` | CI 实际编译并运行工作台；264 条判据进入 CI。**不要把「clippy 通过」当成「写盘纪律已验证」** —— 那是两件事 |
| 2 | **Clippy 禁列补全** | 补 `std::fs::OpenOptions`、`std::fs::File::options` | 验证禁列**确实生效**（拿一段会违规的代码试），不只是配置文件看起来完整 |

执行纪律：先检查 CI 命令、feature 组合与现有测试的真实情况，再改、再验、再提交。
**若启用 `workbench` 后暴露既有失败，先记录并定位，不许通过跳过测试或放宽判据制造绿灯。**

**执行顺序**：方案文档入库 → CI 覆盖修复 → Clippy 禁列补全 → 再开始 Task 13 迁移。
这样 Task 13 开工时，写盘纪律与 CI 验收口径都有明确、可复现的基线。
