## 2. 首要问题：把三种文件角色分开

必须在写业务代码前逐项确认：

- **源数据（Source）**：由人维护、需要保留注释/格式/稳定路径的 TOML。哪些 TOML 是权威输入？是否包含机型、参数定义、资源、套餐、规则？
- **中间表示（IR）**：解析后供校验、合并、计算使用的数据结构。它是进程内临时对象，还是必须落盘的 JSON 工件？若落盘，谁消费、何时生成、如何失效？
- **交付产物（Output）**：MKP 客户端/处理器实际读取什么文件、什么 schema、什么目录？逐一列出消费者与版本兼容要求。

不能仅因“JSON 好处理”就增加持久化 JSON；也不能因现有任务写了 TOML 输出，就假设下游不需要 JSON。结论必须由真实消费者、接口或测试夹具证明。

## 3. 独立核查阶段（只读，不改业务实现）

### A. 建立证据清单

- 固定基线 commit、工作区状态、现有任务文档版本。
- 枚举所有数据根目录及其读取/写入点；追踪 `paths.rs`、upstream 模块、build/generation、IPC 到具体文件。
- 搜索所有 JSON/TOML 文件名、schema、序列化/反序列化入口与调用者。
- 对上游 4 份 JSON 分别记录字段、消费者、是否可由源 TOML 重建；不得仅凭文件名推断用途。
- 核实客户端/后处理器真正读取的格式与路径；缺少消费者证据的，标记为“待确认”，不臆造。

**验收：**形成路径—所有者—读者—写者—用途—证据表；关键链路可从入口追到文件。

### B. 核实数据完整性与写入边界

- 对 12 份 TOML 重新计算 SHA-256，与声明的原始来源逐文件比较。
- 检查参数保存调用链：UI draft → IPC → app → domain → repository/source writer → 文件。
- 明确写入是局部键更新还是整文件重序列化；验证注释、未修改字段、float/int 表示与其他 variant 不受影响。
- 区分“正式源数据”“临时草稿”“生成产物”“发布索引”，禁止多个层同时成为权威源。

**验收：**有只改一个目标值的测试、清除值的测试、对照组、未触碰文件哈希证明。

### C. 做出数据流决策记录（ADR）

针对每条数据类别分别决定：

`Source TOML → parse/validate → in-memory IR → merge/derive → output artifact`

明确 JSON 若存在，是临时 IR 的编码、可缓存构建产物，还是客户端交付格式；三者不可混称“中间 JSON”。

**验收：**每种输入和输出都有 owner、schema、生成时机、消费方、失败行为与验收命令；未确认项不得进入实现任务。

## 4. 新架构目标（待 ADR 验证后定稿）

建议保持单向、可追踪的数据流：

`Source TOML → Parser/Validator → Domain IR → Generator → Deliverables`

- `Source TOML`：唯一可编辑的正式数据源。
- `Parser/Validator`：负责解析与跨文件约束，不读 UI 状态、不访问网络。
- `Domain IR`：只承载业务语义；默认内存态。只有明确的消费者/缓存收益证明需要时才序列化。
- `Generator`：确定性地生成客户端真正消费的产物；输入相同则输出语义相同，并提供 diff/manifest。
- `Workbench UI`：通过统一 IPC 调用应用层；不自行读写文件、不复制业务规则、不造假数据或静默 fallback。
- `Repository/Writer`：集中处理原子写入、局部 TOML 修改、格式保留和错误回报。

不预先规定必须保留现有四层模块，也不预先规定必须删除所有现有 domain 逻辑。以职责和依赖证据为准，能复用纯逻辑则单独验证后复用。

## 5. 实施顺序与阶段门

### P0 — 只读审计
完成第 3 节 A/B，输出证据表；不改业务代码。

### P1 — 数据流 ADR 与新任务拆分
确认 TOML/IR/JSON/交付物契约；明确模块边界、数据所有权、错误处理和禁止事项。

### P2 — 最小端到端垂直切片
选择一个参数字段和一个目标 variant：读取真实 TOML → 展示真实值 → 修改 → 保存真实 TOML → 重载验证 → 生成/消费端验证。只做这一条链，不先铺满所有页面。

### P3 — 源数据与生成器
按已确认 schema 接入剩余 TOML 数据；生成器支持预览 diff、明确写入、结果校验。不得覆盖源数据或静默修复未知字段。

### P4 — 清理旧路径
仅在调用图、搜索、测试证明不再需要后，删除 workbench JSON 配方存储、旧 upstream 读取层及过期动作；运行 source-scan 防止回流。

### P5 — 页面逐步接入
按“真实后端已完成”开放入口；未完成页面隐藏，不用 mock/fallback 冒充成功。每页单独验收。

### P6 — 最终验收
运行默认/workbench feature 测试、clippy、前端 lint/build、数据哈希、生成产物可重现性、无旧路径扫描、端到端持久化测试。

## 6. 明确不做

- 不在核查前一次性重写整个 B04。
- 不把现有 UI mock 当作后端能力。
- 不为了架构整齐而额外引入数据库、缓存、JSON 中间文件或抽象层。
- 不把发布产物写回源 TOML。
- 不静默吞错、不以默认值伪装读取成功、不在未知 schema 下自动迁移。
- 不在本计划提交中改动业务代码或真实 preset 数据。
