# 工作台编辑器模型（2026-11-03 定稿）

> 这份文档定义**编辑器应该怎么工作**，不是"现有代码怎么调"。代码是实现，文档是契约；
> 两者不一致时以本文为准，改代码。上一代口径见 `WORKBENCH-STATE-REARCH-2026-11-02.md`，
> 被本文取代的部分在那一份里已标注。

## 0. 一句话

> **改一个值 = 改一次内存 + 记一条命令；撤销 = 反向应用那条命令；只有点「保存」才写文件。**

作者的原话（2026-11-03）：

> 我把一个参数从 1 改成 2，界面马上显示 2。按撤销，马上恢复 1。按重做，又变回 2。
> 只有我明确保存时，才把修改提交出去。

现在做不到的原因不是撤销算法不好，是**编辑的落点错了**：每敲一下都真的在跑一次文件事务。
见 §6 的实测。

## 1. 三层数据的归属（唯一真值）

```text
① Base        打开会话时磁盘上那一份          —— 只读，进会话时读一次
② Doc         内存里的 Presets 文档           —— 唯一真值（Base ⊕ 已应用的命令）
③ Shadow      影子树文件                      —— 只在「保存」那一步写一次
④ Committed   真仓库 presets/                 —— 只有 wb_save 能改
```

| 问题 | 答案 |
| --- | --- |
| **当前参数值的唯一事实来源是什么？** | `ctx.presets`（② `Doc`，一份内存文档）。不是影子树文件，也不是前端的草稿表。 |
| 前端显示的数据直接来自它吗？ | **间接来自它，但不是它的副本**。每笔编辑后端返回派生（`BookView` / `Desk` / `Matrix`），前端只渲染。前端那份 `draft`（`sheet/draftOverlay.ts`）**只是"这一笔还没回来之前先显示什么"**，回来后一律以后端为准。 |
| 后端每次输入还写文件吗？ | **不写**。写文件只剩两处：`wb_save`（影子树 → 真仓库）与 `wb_reload`。 |
| 撤销碰磁盘吗？ | **完全不碰**。撤销 = 在 ② 上反向应用一条命令。 |
| 影子树还留着吗？ | 留着，语义不变（会话根），只是**从"每次输入的实时存储"降级为"保存时的暂存"**。见 §5。 |

### 1.1 Base 与「改之前的值」

- `Base` = `<appData>/workbench/workspace/base/`（`txn::base_root`）。会话开始、以及**每次保存成功后**各重读一次。
- 它回答两个问题：徽章说「本版修改」时用的 `rest`（上次保存是多少）、以及 `↩ 保存值 X` 那个 X。
- **不许每笔重读**：一次读整棵目录是几十个文件，正是要消掉的成本。

### 1.2 Doc 里"已有草稿"这件事

现在 `ctx.draft`（`Draft{values, follows, visibility, bundles}`）挂着的就是"命令还没落成文件的那些改动"。
新模型里它仍然是**命令的落地形态**——只不过落点是内存文档而不是文件：

```text
Patch  ──apply_patches──▶  Draft（改了什么）  ──plan_value_edits──▶  ValueEdit[]
                                                                │
                                                     Presets::apply_values
                                                                ▼
                                                        ctx.presets（② Doc）
```

`Draft` 不退休。它是「待交付的差异」，不是「待写的文件」。跑完这一步 `ctx.presets` 就是
`Base ⊕ 全部命令`，派生（`book_of`）照旧只读它。

## 2. 命令（撤销记录什么）

新增 `workbench/domain/history.rs`。**一条命令 = 一次用户操作**，与文件无关：

```rust
pub struct Entry {
    pub label: String,        // 「A1 · 标准版 · Z 轴偏移」
    pub patch: Patch,         // 执行它 = apply_patches(正向)
    pub inverse: Vec<Patch>,  // 撤销它 = apply_patches(倒序)  ← 由 patch::apply 现算，不手写
    pub cell: Option<EditKey>,// 合并判据：哪一格
    pub at: Instant,          // 合并判据：多久以前
}
pub struct History { undo: Vec<Entry>, redo: Vec<Entry> }
```

**为什么逆命令不自己写**：`patch::apply` 已经在算 `inverse`（`apply_one` 里那段 `inverse.push`），
而且它是唯一知道"版本层原来跟随 ⇒ 反向要发 `None` 而不是写回旧数"的地方。
两个实现就是两条判据，迟早分叉。

### 2.1 撤销粒度：按时间合并（成熟编辑器那一档）

```text
同一条 EditKey（同一格）
  且 距上一条 ≤ COALESCE_MS（建议 300–500ms，实施时用真实手感校一次）
  且 上一条不是「结构编辑」也不是「跟随状态切换」
  ⇒ 就地更新上一条的 inverse（保留最早的"改前"、最新的"改后"），不新增条目
```

断点（**必断**）：

| 事件 | 为什么断 |
| --- | --- |
| 换格（`EditKey` 变了） | 两个参数不是同一次连续编辑 |
| 停顿超过窗口 | 作者原话：「停顿一会儿，再改，就应该形成另一条撤销记录」 |
| 保存 / 放弃 | 之后的编辑属于新的一代 |
| 撤销 / 重做 | 新输入不能被吸进已被撤掉的那一条 |
| 点「跟随基底」/「保存值」/「出厂」这类按钮 | 它是**一次性动作**，不是连续输入；与步进器混在一条会被一次撤掉太多 |
| 落点不同（机型基底 ↔ 版本） | 一次改基底要连带写跟随版本，那是"一条命令改多格"，不该被下一笔并进去 |

`COALESCE_MS` 替换掉现在的 `txn::MERGE_MS = 5000`。**5 秒太长了**——作者按住步进器
连点十几下，本该是"一次连续编辑"，但中间停 3 秒再接上也被并了进去，一次 Cmd+Z 退掉一长串。

### 2.2 一次手势改多格怎么办

`Patch` 目前只有 `SetValue` / `SetVisibility` / `SetBundle`。**一条 `Patch` 就是一个条目**，
即使它实际改了好几格（改基底会连带写跟随版本 —— 那是 `plan_value_edits` 算出来的，
不是多条 Patch）。所以"改基底 + 3 个跟随版本"天然是一条命令，撤销时一起退。
这正是作者要的：**要么全退，要么不退**。

### 2.3 值的唯一真值 & 值+状态同一笔

「跟随」不是另一个开关，它就是 `SetValue{value: None}` 在版本层的语义：

```text
版本层 value:None → 值同步成基底的有效值 + follows = true   （同一笔）
机型层 value:None → 删掉那一行（回出厂默认）
```

Draft 里 `values` 与 `follows` **同键同写**（`patch::apply_one` 已经这么做）。
保存时 `plan_value_edits` 把两者合成 `ValueEdit{action, follows}`，**一次 `apply_values`**。
所以「值变了、状态没变」在数据结构上不可能出现 —— 它是同一个 `ValueEdit`。

## 3. 保存（唯一写文件的时刻）

```text
点「保存」/ Cmd+S
  ├─ 历史为空 且 草稿干净 ⇒ 幂等返回（不弹框、不报错）        ← 现状已经是这样，保留
  ├─ 磁盘在会话期间被外部改过 ⇒ 拒绝（stale），一个字节不写        ← 现状 `save_in` 已有
  ├─ 前端先弹「未保存改动」窗口（现有 UI，不改）
  │    用户在框里确认
  ├─ ① 一次性把 Doc 的差异写进影子树（`write_back()`，每个文件一次 atomic_write）
  ├─ ② `txn::commit(real ← shadow)`（现有提交阶段机，不动）
  ├─ ③ 基准跟上（mirror real → base）+ 重读 Base
  └─ ④ 清历史、清草稿、刷状态栏、重算派生
```

### 3.1 保存失败时

| 失败点 | 之后的行为 |
| --- | --- |
| 弹窗前（外部改过 / 校验不过） | 内存草稿与用户输入**一个字节都不动**，界面停在草稿态 + 报错 |
| 写影子树时（①②之间） | 沿用 `apply_values` 的**整批校验**：先全部校验再全部应用。落盘失败 ⇒ 事务阶段停在 `Prepared`，下次启动 `recover_save_stage` 收拾；**内存草稿保留**，用户可以重试 |
| commit 时（②之中） | 同上；真仓库是逐份原子写，`SaveStage` 记录走到哪一步，重开时补完或报错。**草稿不清空** |

**唯一的硬要求**：任何一步失败，`Doc`（②）与用户的编辑**都还在**。不许出现"存了一半、界面变干净了"。

### 3.2 保存成功后

- 清历史 + 清草稿 → 「未保存」= 0
- Base 换成新内容 → `↩ 保存值 X` 的 X 变成刚保存的那个数
- **`built.json` 一个字节不动**（生成台账不归保存管，沿用现状）

## 4. 放弃 / 撤销 / 重做

| 动作 | 做什么 | 不做什么 |
| --- | --- | --- |
| 撤销 | 从历史尾取一条，应用它的 `inverse` | 不碰磁盘、不重读影子树 |
| 重做 | 把被撤掉的条目重新正向应用 | 同上 |
| 放弃 | 清历史 + 清草稿 + `Doc` 从 `Base` 重新展开（`Presets::reload()` 一次） | **不动影子树**（它可能根本还没被写过） |

放弃的定义仍然是作者 2026-11-02 那条裁定：**回到「打开工作台那一刻」**，不是"回到磁盘现在"。
所以它从 `Base` 重展开，而不是从 `real_root` 重读。

无改动时三个动作都幂等返回（不许变成错误 —— 以前那条"fatal 横幅永远消不掉"就是这么来的）。

## 5. 影子树的定位（收窄，不删除）

| 用途 | 现在 | 改后 |
| --- | --- | --- |
| **值编辑**时的实时存储 | ✅ 每次输入都写 | ❌ **不写**（只落内存） |
| **结构编辑**时的实时存储 | ✅ 每次写一个对象文件 | ✅ 仍写（一对象一文件，成本一次一个小文件） |
| 事务快照 / 撤销栈的依据 | ✅ 每笔前后各快照一次整树 | ❌ 不再拍整树（结构命令只读它碰的那几个文件） |
| 保存的暂存区（写 → commit） | ✅ | ✅ 保留 |
| 差异比较（`wb_shadow_diff`） | 读影子 vs 真源 | 保留，但它比的是「保存时的暂存」，不是「每一次输入」 |
| 未保存 N 份文件 | 快照两份目录算差集 | 改成从 `Draft` / 历史推（§7） |

**为什么结构编辑仍写盘**（与 §1 的"只改内存"并不矛盾）：

1. 结构编辑是**一对象一文件**（`machines/A1.toml` / `bundles.toml` …），一次写一个
   小文件；而参数全挤在一个 56KB 的注册表里，那才必须"只改内存"。
2. 结构命令的**逆命令就是那一份文件的字节**（`before` / `after`）—— 写盘与撤销是
   同一件事的两面，改成"只改内存"就得为 25 类命令各写一个逆命令。
3. 作者先前已明确选过这条：「编辑写的是工作区文件（不是内存）」（2026-10-29）。
   影子树是**工作区**，不是真仓库；`presets/` 只有 `wb_save` 会动。

保留影子树的理由很实际：`txn::commit` 的整目录替换 + 阶段机（`SaveStage`）+ 崩溃恢复
（`recover_save_stage` / `recover_dir_replace`）是成熟且被验证过的，没必要为了"更纯粹"重写一遍。

## 6. 迟钝从哪来（实测，不是猜测）

日志（`supportease.log.2026-11-03`，一次改 Z 偏移 = 一次 `wb_apply_draft`）：

```text
值已写进影子树（事务） req=r00000411 label=A1 · 机型基底 · Z 轴偏移 patches=1 written=4
编辑已进事务 req=r00000411 label=改参数值 files=1 ops=4 fields=0
```

一条用户手势在后端实际做了：

| 步骤 | 次数 | 代价 |
| --- | --- | --- |
| `txn::snapshot(shadow_root)`（`run_ctx` 进入时） | 1 | 读整棵影子树 |
| `txn::snapshot(shadow_root)`（`run_ctx` 退出时） | 1 | 读整棵影子树 |
| `Presets::apply_values` + **写文件** | 1 | 序列化整份 `param_registry.toml` + `atomic_write` |
| `txn::record_with_fields` | 1 | 比两份快照、存整文件字节（before/after 各一份） |
| `refresh_unsaved_files` | 1 | **再快照两次**（real + shadow）+ `changed_files` |
| `derive`（`book_of` → desk/matrix） | 1 | 读内存（这部分必须留） |

改后：

| 步骤 | 次数 | 代价 |
| --- | --- | --- |
| `apply_patches` + `plan_value_edits` + `apply_values` | 1 | 纯内存 |
| `history.push` | 1 | O(1)，不存文件字节 |
| `derive` | 1 | 纯内存（不变） |
| 写文件 | **0** | — |

也就是**每次输入的 syscall 从 O(整棵树) 降到 0**；`derive` 那部分一点没少 —— 它是
"点下去立刻看到新值"的必要成本，不能省，也不是卡顿的来源。

> 这部分是**设计承诺**，不是已完成的结论。阶段 1 落地后要用
> `strace`/日志时间戳实测一次「同一手势的耗时」，并把实测数字补进本节。

### 6.1 前端这一侧

- `writeQueue` 的**单飞去重**保留：同格连点只发最新一条，省 IPC。
- 但它不再"等文件落定"——`drain()` 只等 IPC 往返。
- `draftOverlay` 里的本地草稿保留：它保证"IPC 还没回来时屏幕已经是新值"。
  这个职责不变，**它不是真值**。

## 7. 「未保存 N」与 diff 的数字来源

| 数 | 现在 | 改后 |
| --- | --- | --- |
| 未保存 **N 处**（页头） | `txn.dirty_count()`（按事务条目去重字段） + `draft.dirty_count()` | `Draft::dirty_count()`（一「处」= 一格字段；`values` 与 `follows` 同键算一处） |
| 未保存 **N 份文件** | 快照两份目录算差集 | 从 `Draft` 反推"这些改动落在哪些文件"（值全在 `param_registry.toml`，可见性/套餐在 `delivery.json`）——**不读磁盘** |
| 「改了什么」清单 | `wb_diff_draft`（对象级） | 不变，它读的是 `Draft` + registry |
| 文本 diff（`wb_shadow_diff`） | 影子 vs 真源 | 改成「`Draft` 应用后的渲染」 vs 「`Base` 的渲染」——不写文件也能算，因为两边都是内存里的 `to_toml()` |

**同一条判据不许两个源**：N 处 = `Draft::dirty_count()`；N 份文件从同一个 `Draft` 推。
两者相加的历史（value 草稿 + 事务）在阶段 3 之后归为一条。

## 8. 异常退出

作者 2026-11-03 裁定：**不做自动恢复**。

- 不写任何"恢复草稿"文件；`Draft` 的磁盘快照（`Store::DRAFT_REL`）在阶段 1 一并下线。
- 启动时 `settle_shadow` 保持现状：认出"上次有草稿"就**以磁盘为准**重新铺，并打一句
  `上次会话有未保存的改动 —— 已丢弃`（现在是 `按新口径丢弃，以磁盘那一份为准`，措辞改一行）。
- 影子树里可能残留"上次保存失败"的字节：启动时**基准以真仓库为准**（现状如此）。

> 将来若要做：单独一条「自动恢复草稿」通道（带时间戳、与撤销栈无关、重开时问一句），
> 不许和撤销历史混在一起。今天**不做**。

> `a_machine_field_edit_does_not_wipe_value_edits`、

>

> （改值 → 影子树 mtime 不变 → 撤销/重做立刻生效 → 保存才落盘）。

| **2** | 保存在提交前一次性 `write_back()`；`discard` 清历史 + 从 `Base` 重展开；`wb_txn_state` 的 `can_undo/can_redo` 读历史 | 保存前后 `built.json` 不变；失败时影子树未动、草稿还在 | 同上 |

| **4** | 删 `MERGE_MS` 与 `Txn` 的编辑栈（`snapshot` 只留测试工具）；改 `AGENTS.md` / `MEMORY.md` | 完整验证集 | 整阶段可整体 revert |

**过渡期规则**（阶段 1–2 期间两套栈并存）：**值编辑走历史，结构编辑暂走事务栈**。
日志里把两者标清楚（`命令` / `事务`），避免"撤一次只撤回一半"。
阶段 3 每搬一类，就在 `EDIT_COMMANDS` 里删掉那一行 —— 登记表就是进度表。
