## 一、作者拍板的两条口径（本轮的宪法）

这两条是作者口头定的，之前的实现与它们冲突，本轮按这两条改：

### 1. 状态只有两档：跟随 / 不跟随

| 徽章 | 判据 | 含义 |
|---|---|---|
| **跟随基底**（灰） | 这一层**没有自己的一行** | 值来自上一层，上游改了它跟着改 |
| **不跟随**（蓝） | 这一层**有自己的一行** | 上游怎么改都不关它事 |
| （无徽章） | 基底列 | 基底是根，不挂徽章 |

**判据只有一条：有没有那一行。值等不等于基底，完全不参与判断。**

旧的四档（出厂默认 / 机型默认 / 本版修改 / 已固定）全部退役 —— 它们答的是
"值从哪一层来"，而作者看屏幕时问的是"我改过它没有"。

### 2. 改过就留，同值不再被自动删掉

「改回原值」**算改过**：3.9 → 3.85 → 3.9 会留下 `3.9` 这一行，仍显示「不跟随」。

这是**推翻**了之前那条「70 → 75 → 70 之后文件要恢复原始字节、不许留痕」。
作者明确选了"写过就留"（`ask_followup_question` Q1 选 A）。

回到「跟随」的**唯一**入口是右键「跟随默认基底」（发 `setValue { value: null }` 删键）。
写一个"等于基底的值"只会让它继续不跟随。

> 未保存的表达另算：徽章**不随保存状态跳**，改没保存由那一格的橙色 ↩ 还原按钮
> + 右上角「未保存 N」表达（作者 Q2 选 A）。

### 2.2 "改回原值"判据换了实现（`domain/patch.rs`）

```rust
// 旧：含继承
Some(v) => at_rest_effective(registry, level, owner, key).as_ref() == Some(v)
// 新：只看本层那一行
let settled = at_rest(registry, *level, owner, key).as_ref() == value.as_ref();
```

差别正是新口径的落点：

- 本层**原本没有**这一行，写了个与继承值相同的值 → 旧判"改回原样"吞掉，
  新判"**写过**"（从无到有）→ 记进草稿，落盘后显示「不跟随」；
- 本层**原本有**这一行，改回那一行的值 → 两边都判"改回原样" → 草稿拿掉，脏数不涨。

`at_rest_effective` 因此没人用了，已删（clippy 会报死代码）。

### 2.5 变化日志：落盘事实（`app/logging.rs` 新文件 + storage 改造）

**这是日志系统的第一步，也是最重要的一步**：日志不再复述前端的意图，
而是列出**每一个写进文件的键**。

```rust
// app/logging.rs
pub struct KeyChange { key, owner, before, after, why }
pub enum Why { UserEdit, Promoted, CopySnapshot, EmptyVariantsDropped, Unknown }
```

- `Why::Promoted` 就是作者最困惑的那种"改一次基底，几个版本跟着动" ——
  改机型基底时连带写掉的版本键，用户这一笔根本没碰过，必须单独标记。
- `render_changes()` 拼成一行；超过 32 条只报条数（防批量改 74 条刷爆日志）。
- `show_value()`：`None` → 「（跟随上一层）」、`null` → 「（空）」、
  字符串不带引号、超过 120 字符截断并标总长（G-code 会把日志刷成垃圾）。

`storage` 侧：`plan_value_edits_why()` 返回带 `Why` 的 `PlannedEdit`；
`apply_draft_now_traced()` 在 **`apply_values` 之前**采 `before`（之后问到的就是自己刚写的值），
返回 `Vec<KeyChange>`。`wb_apply_draft` 的日志行现在是：

```
值已写进影子树（事务） label=A1 · 机型基底 · Z 轴偏移 patches=1 written=4
  changes=A1 · Z: 3.9 → 3.95；A1:STANDARD · Z: 3.9 → 3.95（归并连带）；…
```

## 三、还没做的 4 项（plan 里剩下的）

按依赖顺序：

### ① `nonvalue-cmd` — 非值类写盘命令的变更摘要

`wb_set_param_meta`（改参数定义）、`wb_set_section_meta`、`wb_add_version`、
`wb_copy_recipe`、`wb_set_machine_dimensions`、`wb_set_bundle_refs`、
`wb_set_calibration_identity` 等十几条，**只在日志里出现一个汇总结论**
（`编辑已进事务 label=改参数值 files=1 ops=N`），没有"改了什么"。

做法：`app/mod.rs:760-790` 的 `CMD_LABEL` 表旁加一份"变更摘要"函数，
各命令把自己改的字段列出来（字段名 + 旧值 + 新值），由 `traced()` 出口统一打印。

### ② `req-id` — 请求关联 id

`traced()` 入口生成 `req`（单调 u64 → hex），存 thread-local（与 `CURRENT_COMMAND` 同级）；
所有日志行带 `req=...`；`wb_apply_draft` 把 `req` 回传前端（`ApplyResult` 加字段）。
这样一次手势 → 队列 → IPC → 后端 → 派生 → 前端刷新可以 `grep` 同一个 id 串起来。

### ③ `frontend-trace` — 前端显示变化日志

新增 `src/workbench/sheet/trace.ts` + `wb_trace` IPC 命令，把前端事件写进**同一份**
后端日志（两份日志必然对不上）。打点位置：

- `draftOverlay.patchRow`：草稿改变了显示值 → `draft`
- `writeQueue`：合批出队 / 失败回落 → `batch` / `rollback`
- `setDesk` / `setMatrix` 前后比当前列显示值 → `derived`（**用户没点但界面变了**，就是这条）

节流 200ms，连续点步进器不能刷几十行。

### ④ `verify` — 三个场景验收

- 改一次机型基底：日志必须逐行列出裸键 + 每个被连带写的版本键，后者标「归并连带」
- 连续点步进器 10 次：日志 ≤ 2 行（合批）
- 只读操作（切机型、开面板）：不产生写入日志，但派生导致的显示变化有 `derived` 行

### 7.1 非值命令的「改了什么」—— 每一条结构写都有 `fields=`

以前改参数定义 / 机型尺寸 / 机型与版本信息，日志里只有一句

  手写迟早漏一格，而漏的那格恰好就是"改了没记录"的那种。

  工作台那份值类日志（`KeyChange`）复用它。

### 7.2 请求号 `req=` —— 一次点击的七八行能串起来了

```text
req=r0000002a label=参数台·值 patches=1 written=true changes=A1|toolhead.offset.z: 3.9 → 3.95  值已写进影子树（事务）
req=r0000002a files=1 ops=3 unsaved=1  编辑已进事务
req=r0000002a code=E_...  某条命令失败了
```

- 号在 `ipc::traced` 里发（进程内单调，`r` + 8 位十六进制），
  存 `workbench/app/mod.rs` 的 `CURRENT_REQ`，日志取 `logging::current_req()`。
- **成功也回执到前端**：`wb_txn_state` 的返回值多一格 `receipt: {req, command, ok} | null`，
  取走即清；状态栏「未保存改动」右边把那串号显示出来（等宽字体、可选中），
  复制去日志里 grep 就是完整一条线。
- 失败时号进 `AppError.detail` 末尾（`req=r0000002a`）—— **不新增结构字段**：
  `AppError` 是几乎所有返回值的 `Err` 侧，多一格就跨过 clippy 的 `result_large_err`
  门槛（128 字节），把整个仓点红。这一条试过 `Option<String>` 与 `Option<Box<str>>`，
  前者全仓报错、后者只剩两处，仍然不值得。

| 值草稿条数 + 事务条数 | 连点涨到 14 | 连点不是 14 处 |
| 格子数 `层\|归属\|键` | 改了很多还是 1 | 一次 `setValue` 连带写 4 行，只记 1 格 |
| **行数**（现在） | —— | 与 diff 框里的红绿行同源 |

### 实现

- `Payload` 新增 `lines: BTreeSet<(文件, 行的身份)>`；`dirty_count` 数它，
  结构性编辑（没有行可言）仍按条计。
- 行的身份 = **表名 + 等号左边那个键**（`[A1]` 下 `toolhead.offset.z = 3.9`
  ⇒ `"A1/toolhead.offset.z"`）。**不用行号** —— 前面插一行后面的全漂，跨两笔就叠不上。
  表头行用 `(表名, "#0")`，注释 / 空行用 `(表名, "#行号")`。
- `absorb` 里**整份重算** `lines`（不在旧集合上累加）：迭代中的
  `3.9 → 3.95 → 3.9` 必须把那几行抹掉。
- `view_of` / `txn_state` 都读 `Txn::dirty_count() + draft.dirty_count()`，一个源。

### 钉住这一幕的测试

`one_gesture_that_writes_several_rows_counts_several_rows`：一次手势改三处版本键，
`ops().len() == 1` 但 `dirty_count() == 3`。

同步改了三处旧断言（它们钉的是旧口径）：`an_edit_only_touches_the_shadow_tree`
（1→2 行）、`the_six_step_scenario_stays_in_memory_until_saved`（6→10 行，
另加一句 `undo_depth() == 6` 表明"步"与"行"分开）、
`the_unsaved_count_is_the_same_number_as_the_diff_file_count`
改名 `the_unsaved_count_counts_rows_not_files`。

**diff 框那句"1 份文件有改动 · +153 −9 行"仍然按份/按行各说各的** —— 它俩本来就不是一个数，
页头那个 N 现在跟后半句同源。

## 十、2026-11-03 定稿：以事务为唯一数据源的**字段级**变化

作者两次报的问题其实是同一件事的两面：

| 报的现象 | 根因 |
|---|---|
| 「改了很多还是只有 1」 | 页头数的是**手势**（一格一记），附带写入的版本键不算 |
| 「改了什么一直显示空的」 | 那个框只读 `ctx.draft`，而改完值就 `Draft::default()` 清空了 |
| 「怎么从 2 瞬间变成一百多」 | 上一轮改成"数文件行"，而 75 个 `[[params]]` 撞键 ⇒ 一行改动炸成上百行 |

### 定稿口径（作者 2026-11-03 逐条确认）

1. **唯一数据源 = 事务**。不从影子树 vs 磁盘反推（那里混着不是本次事务的差异）。
2. 去重键 `(层, 归属, 参数键)`。**不同归属不许合并** —— `A1`、`A1:STANDARD`、
   `A1:FAST` 是三处。
3. 页头「未保存 N」= 「改了什么」的条数，**同一个函数**（`Txn::dirty_count`）。
4. 结构编辑（改说明 / 改默认值 / 改尺寸 / 改机型版本信息）**也进账**，
   记真实 `before / after`，不是从日志摘要拼。
5. 同一格连改两次只留一条：`before` 保最初、`after` 换最新（`0 → 0.05 → 0.1`
   显示 `0 → 0.1`），页头不随操作次数膨胀。

### 实现

| 位置 | 做了什么 |
|---|---|
| `domain/txn.rs` | 新增 `FieldEntry{level, owner, key, label, before, after, why}`；`Payload.fields: BTreeMap<(层,归属,键), FieldEntry>`；`record_with_fields()`；`field_changes()`；`dirty_count()` = 它的条数 |
| `Payload::merge_fields` | `before` 保最初、`after` 换最新；净零（改回原值）当场剔掉 |
| `Txn::field_changes` | 跨 payload 也要合并（两次 record 之间隔了别的编辑时，`payloads` 不会并成一条） |
| `Txn::is_dirty` | **改回看字节**：`dirty_count` 是显示用的（没记字段就不虚构处数），"能不能保存"必须只认字节 |
| `Ctx.pending_fields` | 命令写盘后填这一笔的字段账，`run_ctx` 记事务时取走 |
| `value_field_entries()` | `KeyChange` → `FieldEntry`：`why` 保留 `promoted`（归并连带）、`label` 查注册表 |
| `structural_fields()` / `one_field()` | `FieldChange` / 机型版本字段 → `FieldEntry`（`why = "structural"`） |
| `wb_diff_draft` | 改为读 `txn.field_changes()`；`DiffLine` 加 `why` |
| `HistoryModal` + `ShadowDiffModal.module.css` | 「改了什么」改三列表格：归属（等宽）/ 字段变化 / 来源（标签） |
| `api.ts` | `WHY_LABEL` 唯一出口：`user→用户修改`、`promoted→归并连带`、`copy→复制快照`、`empty→空表清理`、`unknown→来源不明`、`structural→改定义` |
| `mockBackend.ts` | 桩不再返回 `[]`，每写一笔记一条 `structural` |

### 删掉的东西（别再请回来）

- `Payload.lines` / `changed_lines()` / `line_index()` —— 上一轮"数文件行"的整套。
  两套口径并存必然漂，这正是前四次口径变更的共同病根。
- `Payload.cells` 与 `cell_signature()`。
- `diff_draft(ctx, committed, draft)` 的三段遍历（`draft.values` / `visibility` / `bundles`）。

### 测试

## 十一、下一轮：源 TOML 有序化（本轮**不实施**）

作者原话：「源 toml 需要像生成的 mkp 预设的 toml 一样有序的机械检查的」。

**目标**：同一份数据，每次渲染出的字节顺序一致；改一个字段只产生与该字段有关的
diff（现在因为字段序不固定，改一处会把整节重排，`+153 −9` 那种噪声大半来自这里）。

**四步，必须按顺序**：

1. **定规则**：固定字段序（`key, label, labelEn, labelTw, labelJa, desc…` 这个顺序
   由 `presetdata::registry::ParamDef` 的字段声明决定，不再手写）、固定节序
   （机型按 id 字典序、版本按 id）、固定空行与注释位置。
2. **让生成器能稳定输出**：`param_registry.toml` 的写回走一个**渲染器**
   （像 `presets generate` 那样先构造再序列化），不再就地 `toml_edit` 打补丁。
3. **单独提交一次规范化**：整文件重排会产生一个大 diff，**必须单独一次提交**，
   否则没法 review，也没法把"格式变了"与"逻辑变了"分开。
4. **之后保存统一走同一渲染器**：`wb_save` 与 `presets generate` 共用它，
   否则下一次编辑又会把顺序打乱。

**闸**：做完后 `presets check` / `presets diff` 必须仍然全绿；
`presets verify` 的 SHA 会变（字节变了），属预期，随第 3 步一起提交。

**为什么放在下一轮**：本轮改的是"怎么记账"，规范化改的是"字节怎么排"。
混在一起时，`git diff` 里分不清哪一行是记账逻辑、哪一行是重排。

## 十二、2026-11-03：抽屉里四格全亮，页头却说 1 处

作者截图：右栏「各版本取值」四行（A1 基底 / 标准版 / FAST / FASTV3.3）全都显示
`↩ 3.9` 与 `3.95`，可页头和「改了什么」只有 1 条。

### 先判清楚哪一半是 bug

日志是一行定案：

```text
值已写进影子树（事务） label=A1 · 机型基底 · Z 轴偏移 patches=1 written=1
  changes=A1 · toolhead.offset.z: 3.9 → 3.95
编辑已进事务 files=1 ops=1 fields=1
```

- `written=1`、`fields=1` —— **计数是对的**。查表：`toolhead.offset.z` 的
  `machineVariants` 里 A1 只有基底 `A1 = 3.9`，**三个版本键根本不存在**
  （只有 `A1_MINI:FAST` / `A1_MINI:STANDARD` / `A1_MINI:FASTV3.3`）。
  没有版本键就没有归并连带，文件里只该多写一行。
- **错的是抽屉**：三个版本列没有自己那一行，却亮着「改过」。

### 根因：`dirty_of` 比的是**有效值**

```rust
match (now, self.base_effective_at(col, key)) { (Some(now), Some(before)) => now != &before }
```

版本列继承基底 —— 基底 3.9→3.95，三个版本列的**有效值**跟着从 3.9 变成 3.95，
于是全被判脏。2026-11-02 把判据从「这一层有没有钉记录（`own`）」改成「比有效值」，
是为了修相反的病（归并把值从版本层提到机型层，版本列 `own` 永远 false ⇒ 徽章永不出现）。
改到另一半抖出去了。

### 改法：判据回到**这一层自己那一行**

新增 `base_own_at()`（盘上那一份里，这一层自己写着的值，**不往上找继承**），
`dirty_of` 改为：

```rust
let own_before = self.base_own_at(col, key);          // 盘上
let own_now    = col.layers.own_value(col.level, key); // 现在
// 原来没有 / 现在有了 / 有了又没了 / 都在但值不同 ⇒ 脏；都在且相同 ⇒ 不脏
```

- 跟随基底的格子（`over` 里没有它）⇒ `(None, None)` ⇒ **永远不脏**。这就是「跟随」的意思。
- 归并那种情形仍然判得对：那一笔在 `draft` 里留了 `pending`，`dirty_of` 第一条就返回 `true`。
- `dirty` 与 `own` 从此**同源**（都读 `layers.has_own` / `own_value`）—— 正是 MEMORY 里
  记过的那条纪律（第一版 `pinned_same` 读 registry 原始表、`own` 读 `layers`，
  两个控件互相拆台，同一类错）。

### 测试

`changing_the_base_does_not_make_following_versions_dirty`：改 A1 基底的 `wiping.mode`，
断言基底格 `dirty && own`、版本格 `!dirty && !own`，但版本格 `text` 仍是跟随后的值。
**已验证它能抓住旧实现**（临时还原成比有效值，它当场红）。

### 验证

`cargo fmt` · 双档 clippy 零告警 · `cargo test --features workbench --lib`
**1185 通过 / 7 失败**（改动前同一批）· `tsc` · `lint` · `npm test` 40 通过。

## 十三、2026-11-03 破坏性重做：标签跟**模型**走，不跟**存储**走

作者截图报两个 bug，本质是同一个病：

1. `A1:FAST` 那一行的「字段变化」显示 `3.85 → （跟随上一层）`。
2. 同一屏里 `随基底生效` 与 `归并连带` 混着出现，A1 一种、A1_MINI 另一种。

### 根因一：日志写法被搬进界面

`logfmt::show(None)` 返回「（跟随上一层）」—— 这句话的受众是**日志**：
「值从 3.85 变成"跟着上一层走"」。可 `value_field_entries` 里写的是

```rust
before: Some(crate::logfmt::show(&c.before)),   // None ⇒「（跟随上一层）」
```

把它当成**值**塞进了 `FieldEntry`，界面原样显示。

**改法（两层）**：

- 上游：`None` **不格式化**（`c.before.as_ref().map(...)`），保持 `None` 语义。
- 下游：`effective_text()` 是界面取值的**唯一出口**，把 `None`（以及任何仍带日志
  写法的字符串）解析成**继承出来的具体数字**。第二层是保险 —— 将来谁再写一处
  `show(&None)`，也在这里被挡住，而不是漏到屏幕上。

### 根因二：`promoted` 与 `inherited` 是同一个行为的两张脸

- `promoted`：改基底时，为了**保住这个值**额外写了版本键（A1_MINI 文件里有版本键）
- `inherited`：改基底时版本**没有版本键可写**，纯靠继承跟着变（A1）

两者在模型上**完全一样**（版本的有效值都跟着基底变了），只因为文件长得不同而
贴了两个标签。这正是作者要消除的「同样操作、不同机型、不同结果」。

**改法**：界面只保留三种来源，按**模型行为**分：

| `why` | 意思 | 界面 |
|---|---|---|
| `user` | 用户手改的那一格 | 用户修改 |
| `follows` | 跟着基底变（写没写版本键都一样） | 随基底生效 |
| `structural` | 改定义（说明 / 默认值 / 尺寸…） | 改定义 |

`promoted` **不再出现在界面上** —— 它是"我们写了几个键"的存储解释，用户不关心。
日志里照旧保留（`KeyChange.why` 原样输出），排查时能看出这一次到底写了几个键。

### 判据：这个版本有没有自己的值

```rust
fn has_own_value(table, uid) -> bool {
    table.contains_key(&variant_key(Level::Version, uid))
}
```

- 有 ⇒ 不受基底影响，**不展开**
- 没有 ⇒ 有效值跟着基底变 ⇒ 一条 `follows`

判据只看**模型**，与"文件里有没有那一行"无关。所以 A1 与 A1_MINI 走
**完全同一条分支**，行为天然一致。

### 写值路径同步改（storage.rs）

旧代码用 `promoted_to_base()` 决定写几个键 —— 那个判据读的是**文件里有没有版本键**，
于是同一套模型在 A1 与 A1_MINI 上写出 1 个 vs 4 个键。现在按模型算：
版本有独立值（且不等于旧基底）⇒ 保住它；否则若它等于旧基底 ⇒ 跟着改。
没有裸键时（P1S 那种只有一个版本、值全写在 `P1S:LITE` 上）拿"版本键里的共同值"
当旧基底 —— 否则值改了、版本键不动，保存之后又被版本键盖回去。

「文件写几行」与「用户看到几处变化」从此是**两条独立的账**：前者可对账
（`written=n` 在日志里），后者按继承关系展开（`fields=n`）。

### 测试

- `the_field_table_never_prints_the_log_phrase` —— 塞一个真实的日志写法进去，
  断言界面上不会出现「跟随上一层」
- `every_version_that_follows_the_base_gets_the_same_label` —— 跨所有机型收集
  连带项的 `why`，断言只有一个值
- `the_same_edit_behaves_the_same_on_every_machine` —— 继承数相同的机型等条数
- `a_version_with_its_own_value_is_not_swept_into_the_base_expansion`

### 验证

`cargo fmt` · 双档 clippy 零告警 · `cargo test --features workbench --lib`
**1192 通过 / 7 失败**（改动前同一批）· `tsc` · `lint` · `build` · `npm test` 40。

### 还没做

`presets/registry/param_registry.toml` 的**机械化重排 + 清冗余**（§十一）。
现在 A1_MINI 那三条与基底同值的版本键仍在文件里 —— 界面上已经不影响行为了
（标签统一、展开按模型），但它仍是存储冗余，清掉之后文件才与模型真正一一对应。
