### 1.1 这些问题共同的形状

把 18 条按"根因"归一下，只有四类：

| 根因 | 涉及 | 一句话 |
| --- | --- | --- |
| **A. 声明与实现脱节** | X-01、X-02、X-03、X-04、X-06、X-08、X-09、X-11、X-16 | 界面上摆着的东西，后端没有 / 没接线 / 只打日志 / 契约里没有。这是"点了没反应/点了报错"的全部来源，也正好是仓库自己写的纪律（"后端没有的命令不渲染入口"）被违反的地方 |
| **B. 同一事实多口径** | X-05、X-07、X-10、X-12、X-13 | 一个状态有 2~3 个回答者，或者"成功"与"落盘"不是一回事 |
| **C. 内部概念外泄** | X-15、X-18 | 用户被迫理解实现细节（或反过来，实现细节被包装成用户概念） |
| **D. 流程盲区** | X-14、X-17 | 判据/纪律没覆盖到的地方 |

### 2.1 复杂性里"最贵的五条"（按改动收益排序）

1. **CX-05 + CX-01（状态由前端拼 + 五套状态词）**：这两条合起来是"界面显得花里胡哨"的主要来源，也是重写时改动量最大、收益最大的地方。它把"后端应该给单一状态"这件事藏了五年。
2. **CX-03 + CX-09（内部概念外泄 + 三条追溯链）**：用户被迫理解血统/归档/目录指纹。把"用户可见状态"与"内部追溯"彻底分层，能同时删掉一批 UI 概念。
3. **CX-04 + CX-07（动作词交叠 + 重复入口）**：这是"没有正常软件的样子"的直接观感来源 —— 同一件事有三个入口、五个词。
4. **CX-10 + X-01/X-08（两份清单 + 已漂移）**：这是"功能时有时无"的根源，且它是**流程问题**，不修会在新代码里重演。
5. **CX-11 + CX-13 + CX-14 + CX-16（角色混淆 + 小账本 + 占位页 + 兼容层）**：这一组是"减法"，单独看都不大，但合起来决定了新版本第一屏的干净程度。

### 2.2 明确**不建议**删的

- **CX-02（两张表）**：它不是重复，而是两个不同问题（官方有什么 / 我有什么）。合并会把"断网时我手上这份能不能用"藏起来 —— 这正是 2026-10-08 那次改判踩过的坑（改回去后又改回来）。
- **逐参数官方更新那套链**（`RD-12`）：用户的真实需求是"官方改了几项、我手改过的项不能被顶掉"。要简化的是**默认路径**，不是删掉能力。
- **本地磁盘为权威这条原则**：整个仓库最正确的设计决定之一，务必在新系统里保留（`R-06`）。
