# WORK-STRATEGY.md · 干活顺序

> 这份只管**先做什么、后做什么**。具体命令、数据从哪来、失败怎么恢复
> 看 `docs/PRESET-WORKFLOW.md`；铁律看 `AGENTS.md`。三份不重复。

## 一句话

**先看清一条已经跑通的链路，再沿它一次改完，最后集中验证。**
不要「改一处 → 报错 → 调查 → 再改一处」。

## 1. 动手前：找一个相似实现，把链路看清楚

要找的是**同类功能最近的那一个完整实现**，不是「最像的文件名」。

看四件事：

1. 它的源在哪（谁是真源，谁是生成物）。
2. 它经过哪几个文件，各自只负责什么。
3. 哪些文件是**生成的**、由哪条命令生成。
4. 有没有测试或闸盯着它。

一项功能从源到成品通常是这样一条链：

```
源（注册表 / 配方 / 布局）
  → 配置模型 / 校验 / 写回
  → 运行时 IR
  → 消费逻辑（真正产出字节的地方）
  → 生成产物
  → 验证
```

**看清这一遍，本次任务就不再需要回头确认「这个文件是谁生成的」。**

## 2. 动手前：先圈定影响范围

在改第一个文件之前，先把「这次要动哪些文件」列出来。

判断方法：拿一个**已有的同类参数/配置**，顺着第 1 步的链路走一遍，
看它出现在哪些文件里 —— 那些文件就是本次的修改清单。

清单里要标出三类：

- **直接改**：源文件、消费逻辑。
- **不能改**：生成产物（改了会被下次生成覆盖）。
- **要跟着改**：测试基线、布局、多语言、写回白名单。

范围没圈完就动手，等于用报错来找下一个文件。

## 3. 一次性改完源文件

按清单连续改完，中间不插验证、不插探索。

- 同一条链路里的文件一起改（模型 + 映射 + IR + 消费点）。
- 类型相关的错误（`String` / `&str`、可空、枚举）在**通读一遍时**一次性对齐，不要靠编译器一个个报。
- 只改这一层的源，**不碰生成产物**。

## 4. 源改完了，统一生成

已知的生成关系不要重复调查，直接跑既定的生成命令。

顺序固定：**先把源改齐 → 再生成 → 再看差异**。
不要「改一个源 → 生成一次」地反复滚。

生成产物与源不同源，说明源没改全 —— 回去补源，**不要手改产物**。

## 5. 最后集中验证

跑完既定的验证，然后**一次读完所有失败**，再分类、再定向修。

失败先归类，不同类的修法完全不同：

| 类别 | 判断 | 修法 |
| --- | --- | --- |
| 产品代码错 | 输出确实不对 | 修实现 |
| 判据错 | 实现合理，但测试的**判断方法**挡不住重复行 / 生成物格式变化 | 修判据，并按下方要求报备 |
| 基线过期 | 只有数量、快照这类**预期值**变了，行为没变 | 同步基线，并在提交里写清差集 |
| 环境 / 命令问题 | 用错目录、旧产物、没重编 | 修命令，不动代码 |

**不许为了让测试变绿而放宽判据。** 判据是要求的一部分。

验证阶段只查**失败那一处**。不要因为一个失败就把整个项目重读一遍。

## 6. 什么时候该调查

调查是**辅助动作**，不是主流程。只在这几种情况停下来查：

- 链路里有一步不知道谁负责（多个候选真源）；
- 找不到相似实现可以参照；
- 生成器行为不明，或没有对应生成命令；
- 报错指向的区域与第 2 步圈定的范围**完全无关**；
- 两个已有文档/代码对同一件事说法冲突。

调查只回答**一个具体问题**，查到能回答就停、就继续干活。
调查结论如果推翻了前面的理解，把它补进相关文档，别只留在脑子里。

**不构成调查理由**：某个字段的格式长什么样、某个文件是不是生成的、
某条命令怎么拼 —— 这些看一眼既有实现就有答案。

## 7. 收工怎么说

报告分三块，不要混：

1. **本次做到的** —— 对应任务要求做了什么，实际生效在哪。
2. **顺带发现的** —— 不在本次范围内的问题，**只记录、不动手**。
3. **没做的 / 要你定的** —— 需要人决策的列出来等；纯流程内的事别反复问。

另外：

- 改了测试判据，必须写清：**旧判据、新判据、保住了什么、放弃了什么、为什么必须改**。
- 预留的、还没接上的东西，如实说成「预留」，不要说成「已实现」。
- 不要用「调查过什么」充当成果。
