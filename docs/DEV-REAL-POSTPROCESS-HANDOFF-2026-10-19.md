## 1. 我要什么（需求本体）

**一句话：从工作台的「开发台」启动一趟【真实】的 G-code 后处理，让真正的客户端窗口显示真正的预检 / 进度 / 塔位变化 / 结果弹窗。**

做完之后，工作台「开发台」应当只有**三件事**，职责互不重叠：

| # | 能力 | 动什么 | 真不真 |
| --- | --- | --- | --- |
| ① | **打开真实界面** | 动界面，不动后端 —— 把某一格真实界面打开 | 真组件、真数据 |
| ② | **运行真实后处理** | 动后端 —— 真的跑一趟管线，界面跟着真进度变 | **真任务、真进度、真结果** |
| ③ | **故障注入** | 动后端 —— 让某个 API 方法真的 reject 一条 `AppError` | 真错误、真错误码，真界面显示 |

三者合起来覆盖"我想看某一屏"的所有情形。② 是这份文档要做的那一个。

### 1.1 为什么（作者的裁定链）

- 2026-10-19 作者原话：「希望所有的模态框都能触发，而且要真实的 mock 触发」
- 又：「现在的工作台里面的还挺假的，按钮都不一样，按钮还是关闭预览，根本不真实」
- 又（区分两类东西）：「不是实现不了真的，而是要分清楚：哪些东西已经实现成真功能，哪些只是开发台里的演示场景」
- 又：「不要再扩充预览，而是给工作台开发台增加一个**真实后处理测试入口**」
- 又：「最省事的做法是先检查能否从现有入口启动真实任务，再决定是否需要新增 Hook 消息，**而不是先重写一套流程**」

### 1.2 明确**不做**什么

- **不做**"把进度条数字放慢、任务其实早跑完了"那种假减速 —— 那会出现"显示进度与实际任务状态不一致"，比不减速更糟。
- **不做**"把预览档那几颗按钮换成真按钮的名字" —— 换了名字、点了还是报错，那是更隐蔽的假。
- **不删**真实界面格（①）与故障注入（③）。

## 2. 验收判据（怎样算做成了）

这几条是**唯一**的完成标准，与实现路径无关：

1. **真任务**：确实跑了一趟真的后处理管线（不是 `devsim` 演出）。判据：产物真的落盘、执行记录真的写进 `gcode_history/`。
2. **真界面**：客户端窗口里那一屏**不带**任何"预览"标记 —— 页脚是真机的那几颗按钮，标题不带「预览 ·」前缀。
3. **真按钮**：「停止 / 后台运行 / 强制继续 / 终止」这些真业务按钮**点了真的有用**（能真的取消那一趟，而不是报"没有正在跑的处理"）。
4. **够慢**：进度条、预检、塔位变化、那一问，都有足够时间看得清、截得下来。
5. **可重复**：能反复跑，能换文件，能控制跑多久。
6. **不进正式包**：正式客户端二进制里没有这条入口（与开发台其它能力同一道闸）。

> 判据 3 是**决定性的**。达不到 3 就还是"演示"，只是演示得更像而已 —— 那还不如不做。

## 3. 纪律（动手时必须守住）

- **优先复用，不重写**：先查现有入口能不能直接起任务；只有确实起不来才加协议变体（作者明确要求）。
- **不在产品逻辑里留钩子**：拦截/注入只许住在 `src/api/` 那一层或 dev 事件那一层，不许散进页面组件。
- **跨进程必须算"客户端那棵树"**：工作台的 identifier 与客户端不同，`app_data_dir()` 给的是工作台自己那棵，端点文件各写各的，发错树 = 消息石沉大海（这个坑已经踩过一次）。
- **故障注入的诚实边界**：它拦在 API 调用层，**不代表真实业务真的执行失败了** —— 被拦的那次调用可能根本没进后端。文档与注释要把这句话写清楚，别让人以为注入了就等于"文件/网络真的坏了"。
- **减速只能改时序、不能改状态**：只许在**开发构建**下给指定阶段加暂停点 / 延迟，且不得影响正式版本；进度显示必须与实际任务状态一致。

## 4. 现状（2026-10-19 快照 · 动手前请重核）

### 4.1 已经落地的：故障注入（③）—— 真机制，不是 UI 预览

装在 **API 方法**上（作者选的粒度），一个开关覆盖所有走这个方法的界面，产品代码一行没改。

```text
工作台「开发台」──invoke──► wb_dev_fault_arm(id) ──hook loopback──► 客户端进程
                                                                       │ 按 id 自己造那条错
                                                                       ▼
                                                       emit `dev-fault` → 前端记表（方法 → 错）
                                                                       │
                                                       src/api/bridge.ts 的 call() 查表 → reject
```

当时的落点（**路径可能已变**）：

- `src-tauri/src/devfault.rs` —— 档位表 + 造错。**无条件编译**（与 `devsim` 同路），因为造错发生在客户端进程，而客户端是普通构建（不带 `workbench` feature）。
- `src-tauri/src/workbench/app/devfault.rs` —— 三条命令薄壳：`wb_dev_faults` / `wb_dev_fault_arm` / `wb_dev_fault_clear`。
- `hook_ipc::FromHook::DevFault { fault: Option<String> }` —— **只过 id，不过 `AppError`**（`None` = 卸下）。
- `hook_ui::run_fault` → emit `dev-fault`。
- `src/app/dev/fault.ts` —— 前端那张表 + `armedFaultFor(method)`。
- `src-tauri/src/runtime/delivery.rs` 的 `sha_mismatch_sentence` / `size_mismatch_sentence` / `sha_mismatch_code` 提成了 `pub(crate)` —— **演示的错调产品代码那一族**，有测试钉"演示那条与真机那条一字不差"。

★ 值得抄的一点：**真值只有一份**。演示用的错不重写文案，而是调产品代码自己那句话。抄第二份的话改一处漂一处，演示出来的反而是错的那句。

### 4.2 现状：后处理预览档 —— **是演示，不是真任务**（本轮要处置的那一个）

链路：`wb_dev_trigger(scene)` → `FromHook::DevScene` → `hook_ui::run_preview` → `devsim::drive` 演出 → 置 `preview: true`。

当时的**硬约束**（已查证，这条结论大概率仍然成立）：

- `HookView::cancel()` → `write()`，在 `!hook_connected()` 时报「这一趟已经结束了，没有正在跑的处理」。
- 演出时钩子根本没连 ⇒ **那几颗真业务按钮点了必然报错**。
- 所以 2026-10-14 那条"预览里不摆真业务按钮"的裁定是站得住的 —— 不是"忘了接"，是接不上。
- 现状界面表现：页脚换成「预览模式 · 不接真实后处理」+「关闭预览」按钮，`subtitle` 加「预览 ·」前缀。作者说的不真实，指的就是它。

## 5. 建议路径（按作者给的三步）

### 第 1 步：解决"跑得太快"

- **优先复用**已有基准文件（作者说的那份 A1，约 23.8 MB）。
- 还不够慢就换更大的；但**大小只是初步参考**，最终以真实处理耗时为准（越大不一定按比例变慢）。
- 目标：预检、进度、塔位变化、那一问，都够时间看。

### 第 2 步：从工作台启动真实后处理

作者给的期望流程：

1. 工作台开发台选一份测试 G-code
2. 点「运行真实后处理」
3. 工作台通过**现有的** Hook 通道通知客户端启动任务
4. 客户端执行真正的后处理管线
5. 客户端正常显示预检 / 进度 / 塔位变化 / 结果

### 第 3 步：还是太快的话，加"开发专用减速开关"

两种测试方式，分开，别混：

| 方式 | 用途 | 真不真 |
| --- | --- | --- |
| 大文件真实处理 | 验整体流程、性能、实际进度 | **是** |
| 开发专用减速开关 | 放慢进度更新 / 在指定阶段暂停，方便观察 | 业务结果可以真，但**时序经过人为干预** |

★ 减速的**正确做法**：只在开发模式下，对指定阶段设暂停点或延迟，**不影响正式版本**。
★ 减速的**错误做法**：把进度条数字放慢、任务其实已经跑完 —— 那会造成显示进度与实际状态不一致。

## 6. 我未验证的一个假设（写完就停在这里了，供你参考）

> **假设**：最干净的做法**不是加新协议**，而是**工作台直接 spawn 一个真的钩子子进程去跑那份真的 G-code**。
> 那个子进程连 `hook_ipc` 端点把真进度发给客户端窗口 —— 客户端收到的就是**真钩子消息**、
> `preview` 恒为 `false`，于是界面完全是产品行为，连"预览"这个标记都不存在。
>
> 支撑（当时看到的，未验证）：
> - `devsim` 模块头说自己"是假钩子 `hook-sim` 的界面版" ⇒ 说明有"起一个钩子进程"的先例可抄；
> - `paths::internal_root_headless()` 能从工作台算出**客户端那棵**树的端点（devsim / devfault 都靠它跨进程）；
> - `workbench/app/dev_source.rs`（本地测试源那颗按钮）有"替用户起外部进程"的先例。
>
> **反例/风险**：如果真钩子必须由**客户端进程**起（比如要用它的 app handle / 窗口上下文），
> 那就要走"工作台发指令 → 客户端 spawn"这一条，需要新增一个 `FromHook` 变体。
