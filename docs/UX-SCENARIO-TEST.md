# UX 场景测试协议（用户故事测试）

> 你不是测试工程师。你是一名第一次使用 SupportEase 的普通用户。
> 你的目标不是验证代码是否正确，而是验证一个真实的人能不能自然地完成任务。

## 这份文档管什么

现有探针（`scripts/probes/*.mjs`）答的是「机器认为对不对」：写死选择器、断言字段与文案。
这份协议答的是另一半：「人用起来顺不顺」。两者互补，不能互相替代。

核心一句：

> **不要从功能出发测试，要从"我现在想干什么"出发测试。**

不给 AI 用户说「测试另存为功能」，只给它一个处境：
「我觉得官方预设很好，想保留原版，同时复制一份以后自己改」。
它怎么走到目标、在哪里卡住，就是测试结果。

## 铁律（违反即测试作废）

1. **只使用用户在界面上能看到的信息。** 页面文字、按钮、菜单、提示条、弹窗、截图。
2. **不读代码、文档、数据结构来帮助自己判断下一步。**（执行代理的工作目录必须在仓库之外。）
3. **不提前假设产品设计者的意图。**
4. **不把"功能存在"视为"功能好用"。**
5. 需要猜 → 记录「需要猜」。
6. 需要记住前面某个页面的信息才能继续 → 记录。
7. 需要返回上一页 / 上一步才能继续 → 记录。
8. 按钮、字段、名称让人困惑 → 记录（引用界面原话）。
9. 一个操作虽然能完成、但路径明显绕（"正常人不会这么走"）→ 记录。
10. **如果一个正常用户必须知道开发者设计、数据结构、字段名或业务规则才能继续，则视为 UX 缺陷。**
11. 禁止测试代理"帮助用户"：不允许用产品内部知识替自己找捷径。找不到就停下来，记录
    「可发现性失败」（约 30 秒没有头绪即算），而不是突然点出它"碰巧知道"的按钮。
12. 不要为了发现问题而制造问题；好的体验也要如实记录。

## 五个评分维度（每个故事各打 1-5 分）

| 维度 | 问题 |
| --- | --- |
| 可发现性 | 用户知道下一步去哪吗？ |
| 可理解性 | 用户知道这个东西是什么吗？ |
| 可预测性 | 点下去之前知道会发生什么吗？ |
| 可恢复性 | 做错以后能回来吗？ |
| 连续性 | 用户还记得自己刚才在做什么吗？（跨页面 / 跨步骤的信息要不要靠记忆搬） |

其中**可预测性**最重：`官方文件 → 修改 → 编辑器 → 保存 → 原来是复制` 虽然功能上能做到，
但用户点下去之前不知道会发生什么，就是不及格。

## 每个故事结束后的报告模板

不要只报 PASS / FAIL。按真实用户的使用故事写：

- 我想做什么
- 我以为会发生什么
- 实际发生了什么
- 我在哪里困惑 / 需要猜 / 不得不绕路（引用界面原话）
- 五维评分 + 一句话理由
- 最后我是否相信自己完成了任务

尤其关注：能不能找到下一步；名称是否符合直觉；信息是否出现在用户需要它的时候；
同一个事实是否在不同地方说成了不同的话；是否要求用户记忆前一个页面的信息；
是否把开发者概念暴露给用户；是否存在「功能能用，但正常人不会这么用」。

## 每轮跑完后的收口

先分四档，再回答终局问题：

- **A** 真正阻碍使用的问题
- **B** 轻微别扭的问题
- **C** 纯视觉问题
- **D** 不是问题、无需修改的问题

终局问题（必答）：

> **如果你是一个真实用户，你会不会觉得这个软件在和你作对？**
> 如果只能改三处，你改哪三处？

"用得不舒服"大多数时候不是一个明确 bug，而是这类东西：我要复制 → 为什么不能？我要看它是谁的 →
为什么这里有、那里没有？我要删 → 为什么不拦我也要问我两遍？我要知道它哪一版 →
为什么给我一个"云端更新时间"？这类问题传统断言测不出来，用户故事特别容易测出来。

## 用户的一天（10 个故事，按顺序经历）

同一个 AI 用户、同一个连续会话走完。故事只给目标，不给功能名、不给按钮名。

1. 我第一次打开软件，想给我的 A1 mini 找一个官方预设，让电脑里有一份。
2. 我想知道：眼前这些文件里，哪份是官方的、已经在我电脑上的？它是给打印机哪个版本的？
   什么时候到我电脑上的？
3. 我觉得官方那份很好，想保留原版不动，同时有一份自己的副本，以后自己慢慢改。
   我不想动原版，也不想一上来就进编辑器。
4. 我想搞清楚自己那份副本的身世：它基于哪个官方版本？官方后来更新了的话，我的这份算什么？
5. 我打开自己的副本，改一点东西，保存。然后我想确认：改到的是我那份，不是官方原版。
6. 假装离开了一会儿又回来。官方可能已经更新过几版。我想确认：我电脑里那份是哪一版、
   过时了没有、和最新差在哪。
7. 我觉得一份没用的文件想删掉。按直觉操作：敢不敢点？确认框讲不讲人话？删完状态是什么？
   知不知道还能不能找回来？
8. 我自己保存过好几个版本，想删掉旧的，只留最新的。
9. 我看到一份旧版本的记录，想知道它和现在在用的版本是什么关系（谁从谁来、差在哪）。
10. 我记得三天前自己保存过一份文件，今天想把它找出来用。能找到吗？靠什么找到的？

## 运行环境与边界

- 测试走浏览器预览（`npm run build` → `vite preview`），数据是 mock。
- mock 的边界要事先告诉测试代理：**下载 / 删官方交付行 / 云端更新检查**在浏览器里会如实报
  "没有下载区"一类的失败。失败不是缺陷；**失败时界面说什么、用户能不能明白下一步**才是材料。
- mock 的会话态不跨刷新（刷新即还原演示集合）。测试代理整个一轮不许刷新页面；
  意外刷新要记入"技术备注"（环境限制，不算软件缺陷），不能算进 UX 发现。

## 怎么跑一轮

1. `npm run build`，起 `vite preview --port 4173`，开一个带 CDP 的无头浏览器。
2. 起一个**全新的**执行代理（没有本仓库上下文），工作目录在仓库之外，把下面两段给它：
   - 铁律 + 报告模板 + 终局问题（即上文）；
   - 10 个故事（只给目标措辞）。
3. 代理把每故事一节随做随写进报告文件；跑完由知情者（有仓库上下文的人或代理）把发现
   对照现有设计稿归档成一份带日期的发现报告。
4. 发现归发现：**下一轮改什么，由发现决定，不由"我们觉得应该这样"决定。**
