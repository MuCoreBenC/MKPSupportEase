# SupportEase 预设：官方更新与用户自定义规则

- 文档性质：根据当前 HTML Demo 的实际代码整理
- 适用范围：SupportEase 预设的产品行为讨论与后续程序实现
- 当前演示对象：单个 MKP 预设「A1 Fast」
- 重要说明：本文描述的是 HTML 当前实际实现的逻辑，不把早期讨论中的设想当成已实现行为。

## 1. 目标与核心规则

官方持续发布最新版；用户可以继续使用自己的参数。官方更新不能直接覆盖用户正在使用的值，同时用户也应当能方便地挑选官方新版的参数。

核心规则：

1. 官方侧只需要维护当前最新版，不要求云端保存全部旧版。
2. 用户自己的参数优先级最高，官方发布新版不能覆盖用户明确修改过的值。
3. 官方发布新版时，先记录发生变化的参数，用户当前生效值不立即改变。
4. 用户可以逐项或批量决定是否采用官方的新值。
5. 用户明确不采用某项更新后，该参数保持当时的旧值，不会在后续官方发布时自动跳变。
6. 用户可以随时将单项参数恢复为当前官方值；恢复后该参数采用当前最新版的值。
7. 不需要为了官方更新而创建「我的 A1 Fast 2026新版」「我的 A1 Fast 2」等副本。用户管理的仍然是同一个「我的 A1 Fast」。

这份 Demo 采用的是 **“官方更新由用户选择，用户修改优先保留”** 模型。它不是“所有未修改参数自动跟随官方”的纯自动模型。

## 2. 页面中的对象

### 2.1 官方预设

「官方 A1 Fast」代表官方当前最新版。

Demo 里显示官方版本日期，例如 `2026-10-08`、`2026-10-20`、`2026-10-25`。开发者点击“发布官方新版”模拟官方发布；每次发布只把当前官方版本和值推进到新状态。

Demo 内部为了演示，预置了若干次发布的参数变更。它们是模拟数据，不代表真实官方发布内容，也不表示生产环境需要在本地保存官方历史版本。

### 2.2 我的预设

「我的 A1 Fast」是用户实际使用和编辑的预设。它不是每次官方发布都重新生成一个副本。

它的最终参数由以下几类状态共同决定：

- 用户手动修改的值；
- 用户明确选择保留的旧值；
- 尚未处理的官方更新所对应的旧值；
- 当前官方最新版的值。

### 2.3 当前使用状态

页面展示「当前使用 ✓」，用于表达此 Demo 中的预设正在使用。

当前 HTML 没有完整实现多预设之间的切换流程；因此，“当前使用”在此 Demo 中主要是演示状态，不应误认为已完成真实切片器或运行时的应用操作。

## 3. 参数状态与优先级

HTML 内部维护三份按参数键索引的数据：

| 状态 | 含义 | 最终值如何处理 |
|---|---|---|
| `overrides` | 用户手动修改过的值 | 优先使用用户值 |
| `hold` | 用户看过官方更新并明确选择保留旧值 | 使用冻结的旧值 |
| `updates` | 官方改过、用户还没处理的参数；记录其更新前的官方值 `old` | 暂时继续使用 `old` |
| `official.values` | 当前官方最新版的参数值 | 以上三种状态均不存在时使用 |

最终值优先级为：

1. `overrides[key]`
2. `hold[key]`
3. `updates[key].old`
4. `official.values[key]`

可以理解为：

**用户主动改过的值 > 用户决定保留的旧值 > 尚未决定是否采用的旧值 > 当前官方值。**

这使得官方可以更新自己的最新版，而用户的当前参数不必立即变化。

## 4. 用户编辑参数

用户在参数编辑页修改数值时：

1. 将输入转换为数字，并按该参数定义的小数位数取整。
2. 如果输入值与当前生效值相同，不做状态变更。
3. 如果输入值等于当前官方最新版的值，则删除该参数的用户覆盖、冻结值和待处理更新记录，让该参数回到官方当前值。
4. 如果输入值不等于当前官方最新版的值，则把它写入 `overrides`，清除该参数的 `hold`。
5. 如果该参数原本有待处理的官方更新，手动修改不会自动删除这条更新记录；这样 Demo 仍可提示官方也改过这个参数。

用户修改的参数在官方发布新版时不会被覆盖。

### 示例

官方喷嘴温度是 `230 °C`。用户改成 `225 °C` 后，`overrides.nozzleTemp = 225`。

之后官方将喷嘴温度改成 `235 °C`，用户最终仍然使用 `225 °C`。官方当前值变为 `235 °C`，但用户覆盖值保持不变。

## 5. 官方发布新版时发生什么

用户点击开发者模拟区的“发布官方新版”时，Demo 执行以下行为：

1. 先记录本次发布前，各参数的官方值。
2. 将官方版本推进到下一版，并把本次发布的参数变更应用到 `official.values`。
3. 对官方值确实发生变化的参数，创建待处理更新记录：`updates[key] = { old: 发布前的官方值 }`。
4. 如果某个参数已经存在未处理的更新记录，则保留最早记录的 `old`，不重复覆盖它。
5. 显示提示，说明官方已经发布新版、存在多少项参数变化。
6. 保存状态并重新渲染页面。

**发布新版本身不会把官方新值直接写入用户当前生效值。** 用户需要在后续的更新选择中决定是否采用。

如果连续发布多版而用户还没有处理更新，待处理项保留最早的旧值，官方侧则推进到最新值。因此更新选择中可以表达“之前的值 → 当前最新版的值”，而不是要求云端提供每一个历史版本。

## 6. 更新提示与待处理列表

当官方发布新版后：

- 页面提示官方新版本日期。
- 如果有参数变化，显示“官方更新待选择 N 项”。
- 用户可以点击“选择要跟随的更新”或“看看这 N 项”，进入更新选择窗口。
- 用户也可以从编辑页筛选“官方已更新”，只查看有待处理更新的参数。
- 用户可以关闭提示横幅；关闭横幅只隐藏提示，不会自动应用或丢弃更新。

待处理更新数量统计的是 `updates` 中、当前参数定义范围内的项目。Demo 支持切换是否展示更多模拟参数。

## 7. 更新选择窗口

窗口列出官方值发生变化、且尚未处理的参数。每一行展示：

- 参数名称；
- 官方更新前的旧值；
- 官方当前最新版的新值；
- 如果用户已经修改或冻结该参数，也显示用户当前实际值；
- 勾选后确认将采用的结果值。

### 默认勾选规则

打开窗口时：

- 没有用户覆盖、也没有冻结旧值的参数：默认勾选，表示默认倾向采用官方新值。
- 已有用户修改或已冻结旧值的参数：默认不勾选，避免默认覆盖用户的决定。

用户可以逐项勾选，也可以使用“全选”切换所有待处理项。窗口会显示已选数量和确认后的值。

### 确认应用勾选项

对每个待处理参数：

**勾选（采用官方新值）：**
- 删除该参数的 `overrides`；
- 删除该参数的 `hold`；
- 删除该参数的 `updates`；
- 该参数立即使用当前官方最新版的值。

**不勾选（保留当前值）：**
- 如果该参数没有用户覆盖、也没有既有冻结值，则把 `updates[key].old` 写入 `hold[key]`，冻结在这次更新前的官方旧值；
- 如果该参数已有用户覆盖或冻结值，则保留现有用户值；
- 删除该参数的 `updates`，表示这次更新决定已经处理完毕。

确认后，页面显示本次采用了多少项官方更新、多少项保持原值。

取消或关闭窗口不会应用选择，待处理更新仍然保留。

## 8. 单项“用新值”与“恢复官方值”

对有待处理更新的参数，可以直接选择“用新值”。它会清除该参数的覆盖、冻结和待处理状态，让参数使用当前官方最新版的值。

“恢复官方值”同样清除该参数的 `overrides`、`hold` 和 `updates`。其结果是使用**当前官方最新版**的值，而不只是回到某个历史旧值。

这两个操作的核心语义都是：放弃该参数当前的用户覆盖/旧值保留，让它采用官方当前值。

恢复单项不创建新预设，也不创建历史副本。

## 9. “模拟修改全部参数”与“恢复全部官方设置”

开发者模拟区提供两个用于测试的按钮。

### 模拟：我修改了全部参数

- 对当前展示的所有参数，以当前生效值为基础生成一个模拟用户值（约增加 3%，并按参数精度取整；若结果恰好等于官方值，则再微调一次）。
- 将生成的值写入 `overrides`。
- 清空 `hold` 与 `updates`。
- 保存并刷新页面。

用途：验证官方发布新版后，用户全部自定义时是否能保留自己的参数。

### 恢复全部官方设置

- 清空 `overrides`、`hold` 和 `updates`。
- 当前最终值因此全部回到当前官方最新版。
- 保存并刷新页面。

用途：快速重置参数状态，验证完全采用官方值的场景。

注意：此按钮会丢弃全部用户自定义值，真实产品中若提供类似功能，应使用清楚的操作名称和必要的确认；Demo 当前按钮用于测试。

## 10. 参数列表与筛选

编辑页支持以下视图：

- 全部参数；
- 我的修改；
- 官方已更新；
- 按参数类别筛选。

“我的修改”只筛选 `overrides` 中有记录的参数。“官方已更新”只筛选仍存在 `updates` 记录的参数。用户已经决定采用新值或保留旧值的参数会从待处理更新列表中消失。

参数定义包含显示名称、单位、类别、输入步长、小数位数和默认模拟值。当前 HTML 使用固定的模拟参数定义，不代表已接入真实 MKP 参数注册表。

## 11. 本地持久化与重置

Demo 使用浏览器 `localStorage` 保存状态，键名为 `supportease-preset-demo-v3`。

保存内容包括：

- 当前官方版本和官方参数值；
- 用户覆盖值 `overrides`；
- 冻结旧值 `hold`；
- 待处理更新 `updates`；
- 是否显示更多参数；
- 当前使用演示状态；
- 已发布到第几次模拟版本。

因此，刷新同一浏览器页面后，Demo 可以恢复上述状态。它不是服务器存储，也不是 SupportEase 应用数据目录的真实实现。

“重置 Demo”会清除该键并恢复最初的官方参数、版本、用户修改、冻结值和待处理更新。

## 12. 云端只有最新版时如何成立

这套交互不要求云端保存完整的官方历史版本：

- 云端/发布源提供当前最新版；
- 客户端在获取新版本时，比较当前官方参数值与新官方参数值；
- 对发生变化的参数，客户端在本地记录更新前的旧值，作为用户作决定前的临时保留值；
- 用户选择采用新值后，使用当前官方值；
- 用户选择保留旧值后，把旧值写入本地 `hold`；
- 用户覆盖值保存在本地 `overrides`。

需要注意：HTML Demo 只是用本地的 `RELEASES` 数组模拟发布，并没有实现真正的远程目录、下载、版本发现或文件校验。

真实程序要做到同样体验，必须明确规定：客户端何时拿到新官方内容、如何识别参数变化、何时把待处理状态写入应用数据，以及本地状态如何与预设文件的最终参数值衔接。不能直接把 Demo 的 `localStorage` 当成生产实现。

## 13. 当前 HTML 的边界

以下是当前 Demo 尚未实现或不应被误认为已实现的内容：

1. 没有真正连接云端官方源；发布是本地模拟。
2. 没有真实下载或安装流程。
3. 没有真正把参数应用到 MKP 生成、Bambu Studio 或 Orca。
4. 只有一个演示预设，没有完整的多预设身份、创建、删除、导入、重命名和切换流程。
5. “当前使用”是演示状态，没有完整的应用到实际运行目标的行为。
6. 没有实现服务端历史版本存储。
7. 没有实现真实的应用目录持久化；状态存放在浏览器 `localStorage`。
8. 参数列表及官方变更均为硬编码模拟数据。

## 14. 后续实现时必须守住的规则

1. 官方发布新版不得直接覆盖用户明确修改的值。
2. 不能把“当前官方值”与“用户最终生效值”混为一谈。
3. 官方发布与用户采用更新是两个不同动作。
4. 未处理的更新要有稳定的本地记录，避免重复发布时丢失更新前的参考值。
5. 用户选择保留旧值后，必须明确记录这个决定；不能在下一次官方发布时把它误判为“从未处理”并自动覆盖。
6. 用户选择采用官方新值后，必须清除该参数的用户覆盖和旧值冻结状态。
7. 恢复官方值指向当前官方最新版，不指向任意历史版本。
8. 这些状态必须由统一的应用持久化机制管理，不能让不同页面各自保存出多套真相。
9. Demo 中的固定模拟参数和浏览器存储只是验证交互的手段，不能直接复制为生产架构。
10. 在实现真实更新链路前，需要单独确定官方版本识别、参数比较、本地状态持久化、最终 MKP 产物生成的契约。

## 15. 验收场景

### 场景 A：用户没有改过参数

1. 发布官方新版。
2. 打开更新选择窗口。
3. 这些变更默认勾选。
4. 确认后，参数采用当前官方值，待处理状态清除。

### 场景 B：用户修改过一个参数

1. 用户把喷嘴温度从 `230` 改成 `225`。
2. 官方将喷嘴温度更新为 `235`。
3. 用户值仍为 `225`，更新选择默认不勾选该项。
4. 用户可以继续保留 `225`，也可以明确采用官方的 `235`。

### 场景 C：用户不采用官方新值

1. 某参数原官方值为 `320`，新版改为 `340`。
2. 用户不勾选该项并确认。
3. 该参数冻结为 `320`。
4. 官方之后再发布新版时，该参数仍保持冻结值，直到用户明确恢复/采用官方值或手动修改。

### 场景 D：用户采用官方新值

1. 官方参数从 `320` 更新到 `340`。
2. 用户勾选并确认。
3. 参数变为 `340`，覆盖、冻结和待处理记录清除。
4. 后续官方发布时，该参数可以再次进入待处理更新。

### 场景 E：连续发布多版但尚未处理

1. 官方第一次将参数从 `320` 改为 `340`。
2. 用户尚未处理。
3. 官方又将参数改为 `350`。
4. 更新记录保留旧值 `320`，官方当前值为 `350`。
5. 用户处理时面对的是“旧值 `320` → 当前官方值 `350`”，不需要云端提供中间版本。

### 场景 F：刷新与重置

1. 修改参数并发布新版。
2. 刷新浏览器，状态应恢复。
3. 点击重置 Demo 并确认，所有演示状态回到初始值。

## 16. 产品语义总结

**官方负责持续发布当前默认值；用户负责决定自己的参数何时采用官方变化。**

- 用户改过的值不会被官方直接覆盖。
- 官方更新先进入待选择状态，不立即改变当前值。
- 用户可以选择采用官方新值，也可以冻结当前值。
- 恢复官方值意味着采用当前官方最新版。
- 不需要为每次更新创建新的“我的预设”副本。

这份规则是从当前 HTML 行为整理出来的产品契约草案。真正进入 SupportEase 前，应先确认这套“待选择 + 冻结旧值”的交互就是希望长期保留的规则，再据此定义 Rust、IPC、前端状态与 MKP 产物之间的正式契约。
