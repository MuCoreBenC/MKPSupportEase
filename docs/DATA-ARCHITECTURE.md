# SupportEase 数据与文件架构总纲

> **这份文档是根规则：**每一个文件——无论已存在还是将来出现——必须属于四层之一，且每类数据恰好有一个**唯一主人**。
> **它管归属与流动：**谁产生、谁拥有、谁能改、往哪流、何时允许联网。
> **它不管实现：**工程约束查 `ARCHITECTURE.md`（两层数据根 / IPC / 原子写 / 权限），产品行为查 `PRESET-PRODUCT-RULES.md`（三状态 / SHA / 归档 / 状态流转）。
> 格式之争（TOML 还是 JSON）是第二层问题。**先把层定死，格式是这套架构自然产生的东西，不该反过来成为架构本身。**
> **现状对账单：**`docs/DATA-INVENTORY.md`——现有代码与文件按本总纲逐件归位的结果。
> **发布链的根规则：**`docs/PUBLISH-ARCHITECTURE.md`——唯一源 → 发布根 → 客户端消费
> （路径语义 / 薄 dist / 发布闸 / minVersion / PR 全程）。本文管**归属**，那份管**发布**。

---

## 0. 一张图，四层，单向流

```text
① 开发仓库（我们看得见，用户永远不该知道它长什么样）
   presets/*.toml 源 · presets/delivery 交付目录（入库） · workbench/ 工作态 · 测试夹具
        │  发布构建（唯一通道：把"厨房"做成"菜"）
        ▼
② 安装包（用户拿到的成品）
   程序本体 · catalog（说明书） · 内置资源（图标 / 模型 / BBS 配置）
        │  安装 / 首次运行（只释放运行时形态）
        ▼
③ 用户本地（程序管理的 Internal 根 + 用户自己的 User 根）
   catalog 运行时副本 · mkp/（下载/导入，初始为空） · archive/ · exports/ …
        │  用户主动需要（检查更新 → 点下载）
        ▼
④ 云端（只干两件事：告诉我有什么，给我文件）
   manifest（清单/版本/SHA/地址） · 文件本体
```

流动只能顺着箭头，不能跳层，不能逆流。**四条铁律：**

1. **开发文件不能直接成为运行时数据库。** ①的文件不许原样出现在③——运行时读的必须是构建产物，不是源文件。
2. **云端不能参与首屏。** 启动零网络，首屏数据全部来自③本地。
3. **用户没下载的东西，不提前塞进用户目录。** ②没带的、④没拉的，③里就不存在。唯一例外是 catalog 本身——它是软件说明书，属于软件本体，随安装释放。
4. **运行时只认自己的运行时数据。** 仓库、试验场、mock、别人的构建产物，都不是运行时的数据库。

## 1. 四层各是什么（白名单制：没列进去的就不允许）

### ① 开发仓库 —— 只给开发的人用

怎么拆都无所谓，方便 Git、方便改、方便 Review 就行。怎么拆都不会影响用户，因为用户看到的是②。

| 路径 | 是什么 | 入库 |
| --- | --- | --- |
| `presets/*.toml` | 源定义：`brands` / `machines/`×5 / `forbidden_zones/`×3 / `assets` / `bundles` / `layout_schema` / `registry/` | 是 |
| `presets/delivery/` | 交付目录（源与交付同树是 `workbench/paths.rs` 的刻意决定）。**入库**（2026-10-02 第十八刀改判）——main 上的正式远端交付面 | 是 |
| `crates/preset/assets/presets/` | **入库产物目录**：9 份交付预设的真字节，`BUILTIN_PRESETS` 编进二进制的就是它，判据测试锚着它 | 是 |
| `crates/preset` + 判据测试 | `BUILTIN_PRESETS` 与命名函数，判据保证与 `dist` 一份不差 | 是 |
| `crates/*/tests/fixtures/` | 判据资产（对照基线等，见 `ARCHITECTURE.md` §10.6） | 是 |
| `workbench/` | 工作台运行态（快照 / 草稿），是**工具的暂存区**，不是数据源 | 否（不入库、不进包） |
| `public/assets/` | 我们管的资产（**产品数据资源**）的**载荷源**：`bbs/` `icons/` `models/` —— 三类都已登记进 catalog、客户端按需下载 | 是 |
| `src/app/assets/` | **界面展示素材**：品牌 logo、机型整机图（`printers/`）、测试模型合影（`hero/`）。判据是"它是不是产品数据资源"而不是"文件是不是图片"—— 这些不进 catalog，随程序本体走（vite 资源管线）。**2026-10-01 起 `public/` 里不再有界面素材**，只剩台账管的载荷根与 BBS 页元数据 | 是 |

### ② 安装包 —— 把源做成成品

厨房里的几十个食材、调料、半成品，端给客人的是做好的菜。

| 允许 | 说明 |
| --- | --- |
| 程序本体 + 前端产物 | 二进制与 vite 产物 |
| **catalog**（说明书） | 发布构建**算出来**的唯一产物：有哪些机型 / 版本 / 参数 / 预设，每个文件的版本与 SHA。运行时只读它。格式另定（叫 catalog.json 只是占位），它是架构的自然产物，不是架构本身。**它不带云端地址** —— 见 §1④ 的分工 |
| 内置资源 | 图标、3mf 模型、BBS 切片配置——**必须在 catalog 里登记**（版本 / SHA），不许裸放。**登记后不再随前端产物分发**：它是"产品开发出来的资源"，与 MKP 预设一样走 catalog → Source → Delivery → `mkp/<kind>/…`（第三圈已收口：三类全部接进同一条管道） |
| 界面展示素材 | 品牌 logo、首页 / 校准页的测试模型合影——**随程序本体**（vite 资源管线，产物里带内容哈希）。**机型整机图 2026-10-03 从这里搬回数据侧**：文件在 `presets/assets/printers/`、台账里是 `delivery = 'bundled'` 的条目（工作台可管可换图），到客户端仍**随程序本体**（构建期复制），但**不进 catalog 的 files[]**、客户端不下载。边界由 `runtime::catalog::dest_of_asset` 的判据守着（**按交付档位拦**，不按类型拦） |
| 内置预设 | 随软件发布的成品内容（现 9 份，入库产物目录 `crates/preset/assets/presets`，判据锚定），在 catalog 里标"内置" |

| 禁止 | 理由 |
| --- | --- |
| `presets/` 源 TOML 原样进包 | 铁律 1：源不是运行时数据 |
| `workbench/`、快照、草稿 | 开发工作态 |
| mock / 假云端 / 测试夹具 | 模拟数据进成品是事故 |
| `workbench.html` 第二入口 | 已由构建开关保证（见 `vite.config.ts`），保持 |

### ③ 用户本地 —— 两根（承 `ARCHITECTURE.md` §4）

**Internal 根**（`appDataDir()`，程序管理）：

```text
<appDataDir>/
├── catalog.json   说明书运行时副本（首启从安装包释放 / 校验，程序只读）
├── mkp/           产品资源区：**从外部取得、由程序管理的原件**（云端下载的 + 外部导入的）。
│                  初始为空，下载了什么才有什么（铁律 3）。**按种类分层、不按来源分层**：
│                  mkp/presets/ · mkp/bbs/ · mkp/models/ … —— 新增一种资源就多一个 kind 与一个目录，
│                  不再出现"今天 assets/、明天 cloud/、后天 models/"那种各起一套
├── archive/       更新后旧版本的归档（不删）
├── index/         索引
├── logs/          按天滚动日志
└── run/           运行状态：`active-preset.json`（使用中指针）、`preset-source.json`（数据源地址）、
                   `draft-preset.json`（**编辑中的那一份**：临时文件。内容从下载区复制出来，
                   用户改的是它；点保存才另存进用户根。**不跟官方原件同目录** ——
                   `mkp/` 的判据是"盘上每个文件都在目录里登记"，塞 `.tmp` 进去就污染交付那一层）
```

**User 根**（`<appDataDir>/user/`，用户自己要看要拷的）：

```text
<appDataDir>/user/
├── presets-mine/  用户修改的预设副本（可自由改，与云端脱钩）
├── exports/       导出
└── reports/       报告
```

★ **两个根都住 `appDataDir`（作者 2026-10-05 拍，用户根由 `Documents/SupportEase` 搬来）**。
两条理由都是真机踩出来的：

1. macOS 的 `~/Documents` 受 TCC 保护 —— 程序第一次进去会弹「要访问你的文稿文件夹」，
   而这个程序**不需要用户的 Documents**（2026-10-05：用户点开预设页就被问了一次）；
2. 开了「桌面与文档」iCloud 同步后，Documents 里的文件会被驱逐成占位 stub ——
   读出来内容不对，会把 Preset 的 SHA 失效判定变成误报（见 §4）。
   **程序写的文件不放在一个会被系统悄悄搬走的地方。**

给③新增任何子目录，**必须先改这份文档**，再写代码。

#### catalog 的一生：**bootstrap → OTA → 当前**（2026-10-04 定，收口一个真事故）

catalog 是 OTA 数据，**随包那份只是起点，不是最终资源**。三段各有唯一主人：

```text
① 随包 bootstrap catalog（层②，编译期 include_bytes! 进二进制）
      只说"第一次启动时世界长什么样"——机型 / 版本 / 参数注册表 / 资产台账 /
      交付文件条目。它是**起点**，不是判据。
      │
      │ 启动：只铺空位（ensure_released）—— 盘上没有才写，有就一个字节不动
      ▼
② 当前 catalog（层③，<appDataDir>/catalog.json）—— **运行时唯一有效的那一份**
      首屏全部定义、下载校验的期望 SHA、Stale 判定，一律以它为准（铁律 4）。
      │
      │ 应用远端目录（apply_remote_update → release_bytes）：旧份归档，新份生效
      ▲
      │ OTA（check_remote_update 比 revision）
      ┌───────────────────────────┐
      │ ③ 远端 catalog（层④发布产物）│ —— presets/delivery/catalog.json（与 source.json 同源）
      └───────────────────────────┘
```

**三条硬规矩**：

1. **启动绝不覆盖 ②**。启动只问"盘上有没有"（`release::ensure_released`），不比较、不升级。
   用升级语义铺盘（曾经的 `release::release_catalog`）会让每次启动把用户 OTA 拿到的新目录
   换回随包那份 —— 于是下载永远拿旧 SHA 比云端新文件、永远 `SHA_MISMATCH`
   （2026-10-04 实测修掉，判据 `startup_never_overwrites_an_ota_catalog`）。
2. **期望值只来自 ②，不来自 ①**。`deliver` 的 SHA / size 校验、`file_status` 的 Stale 判定、
   `state::save_active` 的应用指纹、`mine::based_on` 的"官方换版了没"，读的都是 ②。
   ① 只在 ② 缺席时被铺成 ②，**它自己从不直接参与校验**。
3. **对不上时报"目录过期"，不报"文件坏了"**。目录停在旧 revision 时拿旧 SHA 比新文件必然不符，
   该做的是刷新目录（`sha_mismatch_message`：两个 revision 都摆出来 + 指路「检查更新」）；
   只有两个 revision 相同却字节不符，才是真的源头坏件。

**构建链的双身份（欠账，见 §4）**：`crates/preset/assets/presets/*.toml` 是 ① 的**构建输入**
（`gen-presets --write` → `gen-catalog` → `catalog.generated.json`），它**不是**"客户端内置的最终
MKP TOML"（落点 = `catalog.path`，铁律 3）。工作台生成的是 ③ 的交付根 `presets/delivery/mkp/presets/*.toml`，
两批字节不同**本身不构成下载失败** —— 真正的失败只来自 ② 落后于 ③。

#### 预设 TOML 的一生：**官方线 / 用户线，两条不许混**（2026-10-02 定）

这是 `mkp/` 与 `presets-mine/` 各自服务的那件事，也是后面几圈做 Preset 功能的**总模型**：

```text
官方线（云端 → mkp/ → archive/）              用户线（用户自己改出来的）
  云端发布 v1
      │ 下载
      ▼
  mkp/presets/A1MF_260701.toml  ← 官方原件，**永不直接编辑**
      │ 云端发布 v2
      ▼
  archive/mkp/presets/…（旧份留档，不删）      mkp/presets/A1MF_260701.toml
  mkp/presets/A1MF_260701.toml  ← 新官方 v2         │ 点「修改」
                                                   ▼
                                         临时文件（.tmp，不落进 mkp/）
                                                   │ 点「保存」（另存）
                                                   ▼
                    <appDataDir>/user/presets-mine/A1MF_260701（已修改）.toml
                                                   │ 再改也只改这一份
                                                   ▼
                                   **永远不回写官方原件**
```

四条不许破的：

1. **官方原件不可变**：下载下来的那一份，只有在"云端换版本"时被替换；
   用户打开编辑界面**不动它**。
2. **用户修改另存**：用户的改动发生在临时文件里，保存时**另存成用户自己那一份**
   （`presets-mine/`），从此与云端脱钩。
3. **什么都没改 = 什么都没发生**：浏览 / 使用 / 关闭 / 重开**不产生任何额外文件** ——
   "下载官方文件"本身不制造用户副本，只有"进去改了并保存"才产生。
4. **归档只服务官方线**：`archive/` 是**官方版本生命周期**的一部分（换版本时旧份进这里，保留最早一份），
   **不是用户修改历史**。界面上那一格说的是"这一份以前的官方版本还有几个"，不是"你改过几版"。

推论（判据怎么落）：

- 本地那份与目录登记的字节不一致时，**先问"这是不是我们发过的字节"，再问"云端有没有新版"** ——
  这是两个问题，混成一句「需更新」就都答不清（后者是比目录指纹，与本机字节无关）：

  ```text
  盘上这一份 vs 目录登记的当前版本
    ├─ 逐字节相同                     → 就是当前这一版
    ├─ 与 archive/ 里某一份相同        → 旧版本：认得出它是哪一版（旧官方）
    │   （或被归档的旧目录登记过它）       界面说得出来源，也说得清为什么旧
    └─ 哪儿都对不上                    → 异常：这台机器上查不出它属于哪一版
  ```

- **内容存疑的那两份（旧版本 / 异常）不许用**：不能应用、不能编辑、不能复制，
  **只能重新下载** —— 系统无法证明它还是当前这一版官方内容。三类动作各有一道入口闸：
  应用走 SHA 校验（`apply_active_preset`）、编辑走"取原文"那一处
  （`delivery::official_text`）、复制在界面上直接不给（这一层本来也没有复制命令）。
- **归档是判定"旧版本"的证据**：它的语义是"换版本时从盘上换下来的那一份"，
  被归档的旧目录（`archive/catalog.json`）是第二个证据来源（归档槽只有一份时，
  仍能认出更早那些版本）。
- **用户那份也是真 Preset，两条线都能成为"使用中"**（2026-10-02 作者定，第七层）：

  ```text
  官方线  云端 → mkp/…        只读（只有云端换版本能替换它）  ┐
                                                          ├─ 都能成为使用中（run/active-preset.json）
  用户线  另存 → presets-mine/ 用户可改、不属任何官方版本      ┘
  ```

  **"只读"是文件归属的属性，不是"能不能被使用"的属性。** 所以应用层不许有
  `if 官方 … else 用户 …` 两套 Preset 模型：指向同一份底账，只是**落点解析按各自的线**
  （官方线由目录给路径，用户线给 `presets-mine/…`）与**入口闸按各自的线**
  （官方：盘上字节与目录登记的当前版本逐字节一致；用户：在那一格里 + 是 TOML 预设）。
  **两条线上"字节漂了"的意思也不一样**：官方线是"它不是我们交付的那一版了"（可疑），
  用户线是"用户自己又改了那份"（正常 —— 那份是他的）。
- **元数据随文件走，运行状态才住 `run/`**（2026-10-02 作者定的判据，第七层）：

  ```text
  随 TOML 携带：它是什么（`# based_on*` 血统：从哪一份官方、哪一版拷出来的）
                加上文件本来就有的 `# machine:` / `# variant:` / `# release_time:`
  住 run/     ：程序现在怎么管它（编辑草稿 / 使用中指针 / 下载状态 …）
  ```

  于是"这份用户文件从哪来"**换一台电脑、换个程序也读得出来**，`presets-mine/` 里也不会
  多出程序写的第二份文件。血统一句一行（`# based_on: mkp/presets/A1-standard.toml`），
  **写在文件头注释块里、正文逐字节不动**（工作台建副本那条 K-O2 判据同一套形状）。
- **"官方换版了"不是"你那份坏了"**：用户那份基于旧版官方时，界面说清"官方：v2 / 我的：基于 v1"，
  它照常能看、能用、能改。
  **"把改动挪到新版官方"（合并）作者 2026-10-02 已降级：暂不做，不进当前主线** ——
  它会把 Preset 系统变成"版本迁移工具"（删除 / 新增 / 字段重构 / 冲突 / 生成第三份文件都很
  麻烦，收益却不大）；将来若做，也更可能是"以新版官方为基础重新修改"，让用户自己重新调，
  **而不是程序猜怎么把两个版本揉成一个**。
- **写用户根只有两条路**（2026-10-02 第八层）：

  ```text
  官方那份 ──改这份──▶ 临时文件 ──保存──▶ 另存：presets-mine/<原名>（已修改）<后缀>
  我 那 份 ──改这份──▶ 临时文件 ──保存──▶ 写回它自己（同一路径，不产生第二份）
  ```

  两条都不碰官方原件与下载区；区别只有"落点是谁"与"那三行血统从哪来"
  （另存从**来源**算；写回**照抄文件里原来那三行** —— 出处没变）。
  - **用户文件的管理只有三件：改名 / 另存为一份新的 / 删除**（2026-10-02 第十、十一层，
    范围由作者卡死）：
    **改名只动名字** —— 内容 / 血统 / TOML **一个字节不重写**；只换名字不换目录、后缀保持
    原样、不覆盖落点已有的东西；**正在使用的那份也能改**（`run/active-preset.json` 那条
    指针跟着改，指纹原样），**有草稿的也能改**（`run/draft-preset.json` 跟着改）。
    **另存为一份新的 = 我的文件 → 我的文件**（与"官方 → 我的文件"那条另存分开）：
    **字节复制**、那三行血统**原样带过去**（不重算 —— 来源已经是用户文件）；名字由用户
    明确指定（不预填、撞名就拒、**不自动改名**）；**一个状态都不碰**（不改使用中指针、
    不迁移草稿、不建草稿、不进 archive）。
    **删除就是真删** —— 用户根里没有垃圾桶、也没有归档（`archive/` 是官方版本更新的历史，
    不是用户的回收站）；**正在使用的不许删**、**还有没保存的草稿的不许删**。
    导入 / 批量 / 文件夹管理都不在这一层（导入留给第十二层）。
    - **导入 = 第三条"创建"路（第十二层）**：外部文件 → `presets-mine/`（其余两条：
    官方 → 我的文件、我的文件 → 我的文件）。入口是**通用的**——拖拽 / 文件选择器 /
    重名改名 / 边界检查共用一套（住在 App 层 `FileImportProvider` 与 `runtime::import`），
    **Preset 只是第一个消费者**（以后「备份与恢复」的 ZIP / 备份包复用同一套接收机制）。
    落点固定用户根、**内容按字节复制、不校验**（有血统原样带、没有不编造）、
    重名**不覆盖、不自动改名**（界面开改名流程）、**不碰任何状态**。
    **"导入不是安装 Preset，只是把外部文件纳入我的文件所有权范围"**（判据）。
    ZIP / 备份包现在不处理（注册表留了认领的口子，别让备份包提前污染 Preset 的文件语义）。
    - **外部管理只有「在 Finder 中显示」（第十三层）**：用户文件本来就是真文件，**"拿出去"
    不再造分享 / 导出**—— 右键打开系统文件管理器（Windows 上是文件资源管理器）**并选中**，
    之后复制 / 压缩 / 发人 / 备份全随用户，**不经过 SupportEase 的业务逻辑**；只给「我的文件」，
    读不出来的也能显示（文件管理同族），一个状态都不碰。**单文件导出暂缓**（将来真要做导出，
    是「设置 → 备份与恢复」的 ZIP 备份 —— 把多种运行数据打包，不是复制一个 TOML；
    到那时复用第十二层的通用导入入口）。
  - **两条线各自的"可信"判据不同；第九层只做文件级**（2026-10-02 第九层定的口径）：
   官方线要 **SHA**（盘上那份与目录登记逐字节一致才可信，见上一段）；
   用户线**只看文件级** —— 路径在 `presets-mine/` 里 + 能读 + 是 UTF-8 + **TOML 语法能解析**。
   **外部修改是正常事**（Finder / VS Code 改它不是异常），**不因 SHA 变化报警**；
   "读不出来"（编码 / 语法 / 指向用户根之外）才拦 —— 显示「文件无法读取」，不许应用 / 编辑。
   客户端**不复制 `mkpse-preset` 的 schema、不建第二套 Preset 真相**：
   **语义合法性**（"是不是一份合法 MKP Preset"：结构 / 参数）留给真正的 Preset 解析能力
   在"应用 / 编辑"这类真正要解析的入口上回答；这一层说不了的，就不说。
  - **现状**（2026-10-02）：这条线**接通到底了** —— 官方线（下载 / 已下载 / 旧版本 / 异常 /
   更新 / 归档可见 / 可信度）、用户线（能读 / 能列 / 能看正文 / **能被应用** /
   **能被改并写回自己** / **读不出来就拦在应用·编辑门口（文件级检查，不比 SHA）** /
   **能改名（字节不动、使用中指针与草稿跟着走）、能删（真删除；两道闸）、
   能另存为一份新的（字节复制、血统原样、不覆盖、不自动改名、不碰状态）**）、
   **三条"创建"路都通了（官方 → 我的文件 / 我的文件 → 我的文件 / 外部 → 导入）**、
   "临时编辑 → 保存（带血统）"、以及"我这份基于哪一版官方"的判定都在。
   整套生命周期已收口：**官方 → 我的文件 → 编辑 / 另存 / 改名 / 删除 / 应用 / 导入 →
  Finder 管理**。仍没做的：**「设置 → 备份与恢复」**（ZIP 备份 / 恢复，复用第十二层的
  通用导入入口）；**「分享」与「单文件导出」作者裁决不做 / 暂缓**。
   **登记一条边界**：语义合法性（TOML 能读、但不是一份 MKP 预设）客户端不判 ——
   等真正的 Preset 能力接到应用 / 编辑入口上再说（默认构建不编 `mkpse-preset` 的
   隔离纪律不为它破例）。

### ④ 云端 —— 只干两件事

1. **manifest**：有什么、什么版本、SHA 多少。
2. **文件本体**：用户点了下载才给。

它不解释业务、不算账、不做首屏、不认识没下载它的用户。

#### 地址这件事由谁负责（2026-10-01 定的分工）

**云端地址不写在 catalog 里。** `presets/` 是内容源，换 Gitee、换成自己的 CDN 是
部署的事，不该为了换服务器重新发布一次说明书。分工是：

```text
catalog         说：有一份文件，它在交付集合里的相对位置是 mkp/A1-standard.toml
run/preset-source.json  说：这台机器当前用哪个数据源（官方源 / Gitee / 自建 CDN）
下载地址        = 数据源的 baseUrl + catalog 的相对位置
```

于是"换源"只改 `run/preset-source.json` 一处；`path` 是 catalog 的既有字段，
schema 不为地址再长字段。地址可以有构建期注入的默认值（`MKPSE_PRESET_SOURCE`），
**没有就如实答"还没配置"，不许猜一个 URL 出来假装能下**。

程序可联网的代码只有一处（`runtime/net.rs`）：阻这件事由判据 2 的第①道闸盯着。

## 5. 判据：怎么知道没人违反

规矩先立在这里，实现顺序不拘（与 `write_discipline_scan` 同思路——能扫描的先扫描，能跑的再跑）：

1. **安装包扫描**：构建后扫产物目录，出现 `presets/` 源 TOML、`cloud/presets.json`、`workbench`、`.snapshots`、`*.draft` 即失败。
2. **启动零网络**：启动路径无网络调用。**已落地 2026-10-01（源码扫描）**：
   `npm run check:zero-network`，挂在 CI web job。三道闸——
   ① 网络字节只许住在 `runtime/net.rs`；② 程序的 `.setup()` 段不许联网；
   ③ `src/api/` 不许绕过 IPC 自己发 HTTP。干净过、种脏能抓（两方向实测）。
   **它不是运行时判据**：静态扫描抓不到"A 调 B、B 最终联网"的间接调用，那条以后补。
3. **下载区初始为空**：扩展现有 seed 测试——首启后 `mkp/` 零文件。（旧世界 seed 测试随 `client/` 退役；`runtime::release` 的 `mkp_dir_is_created_empty` 承担同一条）
4. **首屏唯一数据源 = catalog**：客户端清单加载只认 catalog，代码路径扫描钉住。（2026-10-01 落地：九条读命令的 DTO 构建只接受 `runtime::Catalog`，判据 `dto_builders_read_the_catalog_and_nothing_else` 钉死）
