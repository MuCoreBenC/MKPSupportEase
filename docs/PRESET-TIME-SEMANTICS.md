## 0. 一句话结论

预设页的时间乱，不是哪一处把数值记错了，而是**几种不同的时间被混进了三个字段**：软件目前只有一个"云端时间"（当前这代目录发布侧盖的 `publishedAt`），却让它同时顶了三个语义不同的位置；旧版本的时间干脆用的是"你动手那一刻"。规则应该立成一条：

> **时间跟着版本（字节）走，在事件发生那一刻定格，之后永远不变；不知道就照实说「未知」，绝不拿"现在"顶替。**

删除则是另一个极端：现在拦得太死。官方交付那份删了随时能从云端重下（字节有目录 SHA 锚定，零损失），没有任何理由禁删；归档旧版本删了确实找不回，但那是客户端自己留的档，删不删该由用户定，代价讲清即可。

## 2. 截图里的三个疑问，逐条对账

### 2.1 「下载时间 10:13，比云端更新 13:46 还早，怎么可能」

数值都没记错，但这两个字段**说的不是同一份货**：

- 「下载时间 10:13」= 你这份 `A1_MINI-fast.toml` 的字节落进本机的时刻。**10:13 那个时候，云端还是上一代目录。**
- 「云端更新 13:46」= **云端现在这一代**目录的发布时刻（发布侧 13:46 换的版）。
- 两个字段并排、都叫"时间"、没有版本限定，读起来就成了"这份文件的下载比它自己的云端更新还早" —— 荒谬感来自展示语义，不是数值。
- 旁边「云端版本 08e55a3…」也一样：那是云端**现在**的指纹，不是"你这份"的。详情面板里三个时间字段只有「下载时间」说的是你这份，另外两个说的都是云端 —— 面板没有把"你的"和"云端的"分开。

### 2.2 「旧版本的时间居然是现在的时间」

旧版本抽屉里那条 `2026-10-06 16:34` 的真实身份：**你点「更新」那一刻**。

- 更新的动作 = 把旧字节用 `atomic_write` 写进 `archive/`。原子写是新建临时文件再改名，**mtime 就是写入那一刻**（`delivery.rs:223-227` → `fsx/atomic.rs:43-53`）。你 16:34 点的「更新」，归档条目就盖 16:34。
- 因为归档槽"保留最早一份、不覆盖"（`delivery.rs:223` 的 `if !archive_target.exists()`），这个时间甚至不是"最后一次换下它的时间"，而是"这个槽第一次被写入的时间" —— 三种可能语义里最没用的一个。
- **而你要的那个时间（这一版云端发布时的时刻）数据其实是有的，只是没去查：**
  - 版本链 `archive/catalogs/<revision>.json` 里，**每一代被换下的目录都带着自己那一代的 `publishedAt`**（发布侧盖的，2026-10-06 加的链）；
  - 单槽 `archive/catalog.json` 同样带；
  - 归档旧字节的 SHA256 对到链里哪一代目录，那一代的 `publishedAt` 就是"这一版云端发布的时间"。
  - 现在只是**没读出来、没显示**。链建起来（2026-10-06）之前换过的版本查不到 —— 那就照实显示「未知（早于版本记忆）」，不该拿"现在"顶。

### 2.3 「必须是记录它当时的，不能云端一更新就显示云端的」—— 完全正确，这就是要立的规则

现状确实是你说的那个错法：T3（云端更新）、T4（云端版本）都是"云端现在"。应然：

- 你下载的那一份，永远显示**它下载那一刻**定格的事实：下载时刻、当时云端是哪一代（指纹）、那一代发布于何时。之后云端换一百版，这份的记录一个字不变。
- 云端最新的发布时刻是**另一个字段**，只在"有更新"的对比里出现，而且名字要带"最新"二字。
- 旧版本条目显示**它自己那一版**的发布时刻 —— 不是被换下的时刻，更不是现在。

这与项目里已有的两个先例是同一条路：我的文件的血统 `based_on_release_time`（T7）就是"跟着版本走的时间"；目录版本链就是"每一代的记忆"。官方线的下载，缺的正是同样的东西。

## 3. 应然：事件—时间总表

先立三条原则：

1. **时间跟着版本（字节指纹）走**，不跟着操作走、不跟着"云端现在"走。
2. **定格一次，永不再写**：每个时间戳在事件发生那一刻写定；之后任何操作（换版、归档、改名、云端更新）都不改写它。
3. **不知道就照实「未知」并说明为什么** —— 绝不拿"现在"或任何别的时刻顶替。

| 事件 | 时刻属于谁 | 定格时机 | 记在哪（现状 → 建议） | 显示位置与标签 |
|---|---|---|---|---|
| 云端发布（一代目录） | 那一代目录（revision） | 发布侧落盘那一刻 | `catalog.publishedAt`（已有）；版本链里每代各自的（已有，未读出用） | 云端表「云端更新」；本地详情「云端最新版发布于」；旧版本条目「云端发布」 |
| 本机下载（一份字节落盘） | 这份文件（路径 + 字节指纹） | 下载管道写盘那一刻 | 现在只靠 mtime（易被文件操作改写、且不含"当时是哪一代"）→ **建议落账**，见 §4.1 | 本地表「时间」列、详情「下载时间」 |
| 归档换下（旧份进 archive/） | 归档条目 | 换下写入那一刻 | 归档文件 mtime（够用，但要与"版本时间"分开显示） | 旧版本条目「换下于」（次要信息） |
| 修改（我改的） | 我的文件 | 保存那一刻 | mtime（够用） | 我的文件「修改时间」 |
| 复制 / 导入 | 出处账条目 | 记账那一刻 | `provenance.json`（已有，不显示） | 来源格「复制自 X / 导入」 |

## 4. 数据怎么记（建议，未实施）

### 4.1 唯一缺的账：下载事件

项目主线是"盘当底账"（扫盘、不记账），既有例外只有三个：血统三行（写在文件头）、目录版本链（每代目录落盘）、`provenance.json`（复制/导入出处）。**下载事件**属于同一类 ——"这份字节是 10:13 从当时的云端（第 N 代，发布于 …）拿来的"这件事，事后靠 SHA 反查只能答出一半（链建立之前的版本永远答不出），mtime 又随时会被复制、同步等文件操作改写，根本不是可靠账本。

建议：下载管道落盘成功时，追加一条

```
{ file, sha256, downloaded_at, catalog_revision, catalog_published_at }
```

进一本交付账（可并入版本链同层，或独立 `delivery.json`，与 `provenance.json` 同一定位：**附加信息，丢了不坏，界面照实退回**）。有这本账，§2.1 的两个时间就都"跟着版本走"了：你那份永远显示下载那一刻定格的一组数，云端换版不影响它。

### 4.2 旧版本条目补字段（数据现成，只差读出来）

`get_archived_files` 的 `ArchivedFileDto`（`ipc/catalog.rs:505` 附近）现在只有 mtime。补三个字段：

- `sha256` —— 扫盘时算一次就有；
- `published_at` —— 拿 sha256 反查版本链 + 单槽归档目录里登记同一指纹的那一代，取它的 `publishedAt`；查不到 = `null`，界面显示「未知（早于版本记忆）」；
- `archived_unix` —— 现 `modifiedUnix` 改名，明确它是"换下时刻"，不再冒充版本时间。

### 4.3 不可变规则

账一旦落下：文件改名条目跟走（`provenance.rs` 的 `repath` 已有先例）；文件删除条目随之删除或悬空（界面照实退回）。**任何路径都不改写已有时刻。** 归档"保留最早一份、不覆盖"的写侧策略维持不变 —— 那与"允许用户删"不冲突。

## 6. 删除策略

### 6.1 现状（限制在哪，代码出处）

1. **云端表没有删除** —— 客户端不能删仓库里的东西（`PagePresets.tsx:952`）。
2. **官方交付行不能删** —— `removeWhyNot`：「官方交付那份不在这里删 —— 盘上那份对不上目录时用『更新』修它」（`PagePresets.tsx:941`）。
3. **归档区完全不提供删除** —— 后端只读："不提供删除、不提供恢复"（`ipc/catalog.rs` 的 `get_archived_files`、`src/api/contract.ts:1312`、`src/api/bridge.ts:173`）；旧版本抽屉文案同（`ARCHIVE_WHY`，`presetTree.ts:610`）。
4. 我的文件可以删（真删、无垃圾桶），但"正在使用的那份"前后端都拦（`PagePresets.tsx:935`，后端还会再拦一次）。

### 6.2 逐类分析：能不能删、删了会怎样

| 类别 | 删了会怎样 | 结论 |
|---|---|---|
| 官方交付（本地表那份） | 状态回「未下载」，随时可从云端重新下载；字节由目录 SHA 锚定，零数据损失 | **应该放开** —— "删了我还可以从云端下"完全成立 |
| 归档旧版本 | 就没了：云端只有最新版，旧版不可再得。版本链（各代目录的记忆）是另一批文件，删单个归档文件不受影响 | **应该放开**，但确认框必须讲清代价："这一版删了就找不回" |
| 正在使用的那份（我的） | 「使用中」指向一份不存在的文件 | 可以放开：删除前自动撤下「使用中」（或在确认框说明后果，后端同步放行） |
| 云端表 | 那是仓库里的东西，客户端根本没有删除它的能力 | 维持无删除 —— 这不是"不让"，是"不能" |

### 6.3 建议方案

- 本地表官方交付行：给「删除」（危险色 + 二次确认），文案说明"删了可以从云端重新下载"；删除后该行回「未下载」。
- 旧版本抽屉：每条给「删除」（危险色 + 二次确认），文案说明"这一版删了就找不回（云端只有最新版）；不影响版本链的其余记忆"。
- 「使用中」那一份：删前先自动撤下「使用中」再删文件，确认框写明这一步。
- 后端：删除命令扩到交付区与归档区（都按份删、路径过 `resolve_in` 防穿越）；版本链与 `provenance.json` 不动。
