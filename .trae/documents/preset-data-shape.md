# 预设数据该长什么样（先对齐，不动代码）

这份文档只做一件事：把「现在是什么样 / 别人的软件是什么样 / 能不能更简单」摆到桌面上，
让你看完之后能直接拍板。**不是技术方案书**，看不懂的词我一个都不用。

---

## 一、先把你问的三件事答清楚

### 1. 那 9 条命令读的确实是本机文件，一共 13 份

客户端第一次启动时，会把 13 份定义文件铺进它自己的数据目录
（`~/Library/Application Support/com.mkpsupport.ease/presets/`）：

| 文件 | 大小 | 里面是什么 |
|---|---|---|
| `registry/param_registry.toml` | **56 KB** | 所有可调参数的注册表（最大的一份） |
| `layout_schema.toml` | 12 KB | 参数在界面上怎么分组、怎么排 |
| `assets.toml` | 8 KB | 有哪些可下载的文件（机型图 / 图标 / BBS 配置） |
| `bundles.toml` | 3 KB | 套餐 —— 哪个版本配哪几个文件 |
| `brands.toml` | 80 B | 品牌名 |
| `machines/` 5 份 | 各 1 KB | 一台机器一份：型号、版本、尺寸、禁区 |
| `forbidden_zones/` 3 份 | 各 1 KB | 一台机器一份禁区坐标 |

合计约 110 KB。**全都是本机文件，一条网络都不碰。**

### 2. 为什么是 13 份，而不是 1 份

因为这 13 份的切法，是**给后厨工作台**准备的：

> 工作台的数据要跟着 git 走、要能被 review。改成"一台机器一个文件"之后，
> 改 A1 就只动 `machines/A1.toml` 一个文件，diff 里干干净净。

这个理由对**工作台**成立。但客户端把它原样继承了 —— 于是客户端也变成
"打开要读 13 个文件、解析 110 KB 的 TOML"。

**这就是它的来源，不是它该有的样子。你的直觉是对的。**

### 3. 首屏为什么碰了网络

页面上有一列是「云端最新发布的那一份」，它的清单来自 `/cloud/presets.json`（108 KB）。
原来的代码把「画页面」排在了「读这份清单」后面 —— 所以要多等一次网络。

**这个已经修掉了**（改完先画页面，云端那份回来了再补那一列）。而且那一步只是读**清单**，
从来不是下载文件本体。但你说得对：**首屏压根不该碰网络。**

## 二、真正需要联网的软件，是怎么做的

按你说的去看了。三个真实例子，最后一个跟你的软件几乎一模一样。

### OrcaSlicer（3D 打印切片软件，最贴近你的场景）

- 默认预设就放在安装目录里：`resources/profiles/<厂商>/`，每个厂商还有一个索引 `profiles/<厂商>.json`。
- **打包期就进了安装包** —— 官方 wiki 的原话是这个目录的预设是 "distributed with the application"。
- 联网只发生在后台：`PresetUpdater` 启动后**在后台**去同步，下载到 `data_dir/ota/`，
  **弹个通知问你要不要装**，你点了才装。首屏不等它。
- 用户自己调的预设，另存到用户数据目录 —— 和随包的那份分开放。

### VS Code

- 内置扩展和默认主题跟着安装包走：`resources/app/extensions/`，比如默认深色主题就是其中一个文件。
- 它是**构建期**打包进去的。
- 联网是默认在后台查更新，可以关掉。**首屏从来不依赖网络。**

### Homebrew

- 索引**不进安装包**，但**也不是每次去解析 Ruby 源文件** ——
  是由官方定时任务在发布侧预先**生成好一份 JSON**（`/api/formula.json`），客户端直接读。
- 联网按需，现在默认 24 小时才自动更新一次，读到的 JSON 会缓存起来。

### 三个例子共同的套路

```
可维护的源（开发期）  ──构建期──▶  客户端读的产物  ──打进安装包──▶  首屏立刻显示
                                                                    │
                                              用户主动时 ───────────┘ 才联网看有没有新版
```

**没有一个是"打开先联网"的，也没有一个是"运行期去解析开发期源文件"的。**
业界习惯就是把「给人改的源」和「给机器读的产物」分成两样东西 —— 前者可读、可 diff，
后者快、不用解析。几百 KB 的数据，大家做的是**构建期预处理好**，而不是每次启动重新算。

## 三、那我们现在到底复杂在哪

| 现在有的东西 | 谁真正需要它 | 客户端需要吗 |
|---|---|---|
| 13 份 TOML 的目录切法 | 工作台（要 git diff 好看） | **不需要** |
| 运行期解析 TOML | 工作台（要能改一行、原地写回） | **不需要** |
| 把 13 份铺进用户数据目录 | 本来是为了让用户能下载 / 导入 | **要重新想**（见下面问题三） |
| 三层参数取值（出厂 → 机型 → 版本） | 页面要显示"哪几项和出厂不同" | **需要**，这个不是复杂，是业务本身 |
| 云端清单 | 显示"云端有没有新的一份" | 需要，但**不该卡首屏** |

一句话：**复杂的地方不在"功能"，在"客户端在做开发工具的活"。**

举个最直接的：`registry/param_registry.toml` 有 56 KB，
里面的内容对每一台机器、每一个版本其实是**算得出来的**（出厂 → 机型 → 版本三层取值）。
现在客户端每次都从头解析这 56 KB，再自己算一遍 —— 而这份结果完全可以**在打包时就算好**。

## 四、我建议的样子（方案 B）

```
仓库里的 presets/*.toml          ← 保持不动。工作台照旧改它、git 管它
        │
        │  构建期（打安装包的时候）跑一次转换
        ▼
一份 catalog.json                ← 客户端要的东西全在这
        │                          机型、版本、套餐、预设清单、
        │                          参数的三层结果、云端下载地址
        │  打进安装包（和 VS Code / OrcaSlicer 一样）
        ▼
客户端第一次打开                  ← 直接读，零 TOML 解析、零网络、零等待
        │
        └─ 用户点「检查更新」时 ──▶ 才联网拉一份新 manifest
```

和现在的差别只有两处：

1. **客户端不再解析 TOML**，只读一份已经算好的 JSON。
2. **首屏完全不碰网络**，云端只在用户主动时才拉。

**不建议动的：** 仓库里的 `presets/*.toml` 保持原样 —— 那是工作台的源，切法没问题。
用户下载回来的 `.toml` 预设文件也保持 TOML —— 那是给切片器吃的，是**产物**，不是元数据。

## 五、需要你拍板的四个问题

**问题一：客户端要不要"一份算好的 JSON"？**
- 要（推荐）：首屏零解析，和 OrcaSlicer / VS Code 一样。
- 不要：保持现在这样，只是把解析缓存起来（已经做了，现在是 61 毫秒）。

**问题二：这份 JSON 在什么时候生成？**
- 打安装包时生成（推荐）：最简单，和 VS Code 一样。
- 每次工作台点「发布」时生成：工作台改完就能看到，但要额外接一条链路。

**问题三：客户端还需不需要"把定义铺一份到用户目录"？**

这是我最想听你意见的一条。现在的做法是"铺 13 份文件到用户目录"，
初衷是让用户能往那儿放自己下载 / 导入的预设。但如果定义都算进 JSON 了，
那块目录里其实**只需要放用户自己下载回来的东西**（`mkp/`），不需要那 13 份定义。

- 改成：JSON 在内置里只读，用户目录只放"下载 / 导入的东西"（推荐，更简单）
- 保持：继续铺 13 份定义（好处是用户 / 高级用户能直接改文件看效果）

**问题四：云端清单要不要默认去拉？**
- 不拉，只在用户点「检查更新」时拉（推荐，最贴近 OrcaSlicer）
- 拉，但绝不卡首屏（就是刚才修完的样子）

---

## 六、这一轮要不要动

**建议分两步，你先定方向：**

- **第一步（小）**：只做问题四 —— 云端清单改成按需，首屏彻底离线。
- **第二步（大）**：做问题一 / 二 / 三 —— 构建期生成 `catalog.json`，
  客户端改成只读它。这一步会动后端的数据层（现在那 13 份铺文件的逻辑会删掉）。

第一步几乎不动结构。第二步是真正的简化，但要知道：**它会改掉现在刚合进去的那套东西**，
所以我想先听你拍板，再动手。

---

## 附：一句话总结

> 不是"要不要用一份 JSON"的问题，是**"客户端该不该在运行期干开发工具的活"**的问题。
> 你的直觉（构建期打包、首屏离线、云端按需）和 OrcaSlicer 这类真实软件的做法是一致的。
